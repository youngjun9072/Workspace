# 0. 한 장 요약 (발표 도입)

- **목표**: applylogdb 병렬 적용 시 **트랜잭션 간 충돌·순서를 코디네이터가 책임**지게 한다. 현 PoC의 `tranid % worker`(관련 트랜잭션도 동시 실행) 문제를 해결.
- **접근**: **MySQL 모델 차용** — "병렬 실행"과 "commit 순서 보존"을 분리.
- **관건 2가지**: ① 모든 시나리오에서 **correctness**(올바른 동작) ② **병렬성** 최대 지원.

# Part 1. 사전 지식 (컨셉 이해용)

> 흐름: 복제 일반 → **물리 vs 논리 복제** → CUBRID는 어디에 → 코디네이터 컨셉.
> (물리/논리 이해가 "왜 병렬화가 필요한가" "왜 MySQL 모델인가"의 토대가 된다.)

## 1-1. 복제란
- **복제(replication)**: master(원본) DB의 변경을 slave(복제본)가 따라 적용해 같은 상태로 유지. CUBRID HA의 핵심.
- master/slave = source/replica(MySQL) = publisher/subscriber(PostgreSQL)와 같은 개념.

## 1-2. 물리 복제 vs 논리 복제 (핵심 토대) ★

| | 물리(physical) 복제 | 논리(logical) 복제 |
|---|---|---|
| 무엇을 보내나 | 로그(WAL/페이지 변경)를 **그대로 복사·재생** | 변경을 **행 단위로 재실행**(INSERT/UPDATE/DELETE) |
| 비용/속도 | 레코드당 쌈, 단 **단일 스레드 재생** | 레코드당 비쌈(파싱·인덱스·제약 처리) |
| 유연성 | 낮음(통째·동일 버전·읽기 전용) | 높음(선택 복제·버전 간·이기종·쓰기 가능) |
| 병렬화 | 어려움(LSN·페이지 종속) | 상대적으로 쉬움(트랜잭션/행 단위) |

- **왜 많은 DB가 "논리 + 병렬"을 택하나**: 물리가 "레코드당 싸다"고 항상 빠른 건 아니다 — **단일 스레드**라 멀티코어 부하를 못 따라가고, 경직돼서 **못 하는 일(선택 복제·무중단 업그레이드·이기종)** 이 많다. 그래서 **유연한 논리**를 택하고, 논리의 약점인 적용 속도는 **병렬화로 메운다.** → **이 프로젝트(병렬 applylogdb)가 바로 그 방향.**

## 1-3. 로그와 좌표
- **복제 로그(repl log)**: master가 "무엇이 바뀌었나"를 기록. slave가 읽어 재현.
- **LSA (Log Sequence Address)**: 로그 안의 위치(번호표). "어디까지 처리했나"를 가리킴. (MySQL binlog position, PG LSN에 대응)

## 1-4. CUBRID는 어디에 위치하나 (코드 확인)
- **CUBRID applylogdb = 논리 복제 계열(행 재실행)** — worker가 slave에 INSERT/UPDATE/DELETE를 다시 실행(물리 페이지 복사 아님 → slave LSA ≠ master LSA).
  - → 1-2의 "논리라 레코드당 비싸다"가 그대로 적용 → **병렬화로 메우는 게 이 발표 주제.**
- **복제는 PK 기반** — 복제 로그 = `class + PK 값 + 변경종류`. → 복제 테이블 **PK 필수**, 충돌 키로 PK·class를 항상 쓸 수 있음.
- **CUBRID 용어** — **class** = 테이블. **copylogdb** = master 로그를 slave로 복사 / **applylogdb** = 읽어 적용(이 문서 대상).
- **현 PoC 병렬화 = `worker_idx = tranid % worker_count`** →
  - ❌ 관련 있는(같은 데이터) 트랜잭션도 동시 실행될 수 있음 ← **가장 큰 문제**
  - ❌ 독립 트랜잭션이 한 worker에 쏠릴 수 있음

## 1-5. 코디네이터 컨셉 (한 그림)
```
복제 로그 리더 → [코디네이터: 충돌/순서 판단 → 실행/대기 구분 → worker 선택]
   → worker pool(병렬 적용) → 순서 정리(committed_lsa를 commit 순서대로 전진)
```
- 핵심 질문: ① 앞선 것과 충돌? ② 충돌하면 어디까지 대기? ③ 실행 가능하면 어느 worker? (①② = correctness, ③ = 성능)
- 비유: 코디네이터 = "동시에 시켜도 되는 일 / 순서 지켜야 하는 일"을 나눠 일꾼(worker)에 배분하는 반장.

# Part 2. 타벤더 비교

## 2-1. 세 모델
| | MySQL | PostgreSQL(community) | EDB PGD(상용) |
|---|---|---|---|
| 의존성 판단 **위치** | **source**(binlog) 선계산 | — (자동 의존성 병렬 없음) | **apply 측(writer)** |
| 판단 **단위** | row write-set | — | 행(tuple) |
| 병렬 적용 | LOGICAL_CLOCK으로 독립 트랜잭션 병렬 | 단일 구독 내 **직렬** | writer 여러 개 병렬 |
| 순서 보존 | **SPCO**(commit 순서 강제) | 직렬이라 자동 | **위반 감지 → 롤백**(낙관적) |

## 2-2. 한 줄 요약
- **MySQL**: source가 "병렬 가능 여부"를 미리 계산 → replica가 병렬 실행 → SPCO로 commit 순서 보존. (병렬 실행 ↔ 순서 보존 **분리**)
- **PostgreSQL**: 단일 구독은 트랜잭션 직렬. 병렬은 초기 동기화·대형 트랜잭션 스트리밍에 한정. (자동 의존성 병렬 없음)
- **EDB PGD**: 멀티마스터. **apply 측 writer가 행 충돌을 보고** 순서 맞춤, 위반 시 롤백.

# Part 3. MySQL과 비슷한 차용을 한 이유

## 3-1. 왜 MySQL 모델인가
- MySQL의 **"병렬 실행(LOGICAL_CLOCK) ↔ commit 순서 보존(SPCO)" 분리** 가 CUBRID 코디네이터 구조와 **1:1로 맞는다**:
  - MySQL 분배(coordinator) ↔ CUBRID **코디네이터**
  - MySQL SPCO ↔ CUBRID **순서 정리 단계(committed_lsa 순서 전진)**
- "독립 트랜잭션은 병렬, 순서는 따로 보존"이라는 **목표가 동일**.

## 3-2. 왜 PG는 아닌가 / PGD는 어떻게 참고하나
- **PostgreSQL**: 단일 구독 내 자동 의존성 병렬이 없음 → CUBRID가 목표하는 "자동 의존성 병렬 + 전역 순서 보존"의 직접 모델로 부적합. (대신 "병렬 단위를 잘못 자르면 깨진다"는 반면교사)
- **EDB PGD**: 의존성/충돌 판단을 **apply 측**에서 한다 → CUBRID도 (1차안에서) 코디네이터가 slave 측에서 판단하므로 **PGD가 더 가까운 참고**. 단 PGD는 멀티마스터라 충돌 처리가 더 복잡.

## 3-3. 차이 한 가지 (중요)
- MySQL은 **source가 의존성을 미리 계산**해 내려보낸다. CUBRID는 **복제 로그에 그런 정보가 없다**(class + PK뿐) → **1차안은 applier(코디네이터)가 class 단위로 보수적으로 판단**. 정밀(row/key) 병렬은 후속(복제 로그 확장).

# Part 4. 시나리오 검증 (발표 핵심)

## 4-1. 검증 기준 2가지
1. **correctness**: 모든 시나리오에서 코디네이션 컨셉이 **올바르게** 동작하는가
2. **병렬성**: 병렬성을 **최대한** 지원하는가

## 4-2. 코디네이션 컨셉 (검증 대상)
**class-OID 충돌 판단 → 직렬/병렬 구분 → commit 순서 보존(순서 정리) → 재시작 멱등 skip**
- 같은 class 변경 → 직렬 / 서로 다른 class만 → 병렬 / schema·sysop·unknown → barrier

## 4-3. 시나리오 매트릭스
| 시나리오 | ① correctness | ② 병렬성 |
|---|---|---|
| 같은 class·같은 행 (lost update, unique·PK 재사용) | ✅ same-class 직렬 → 순서 보존 | 직렬(불가피) |
| 같은 class·다른 행 | ✅ 보수적 직렬(안전) | ❌ 손해 → 개선여지: **row/key 단위** |
| 다른 class·독립 | ✅ | ✅ **최대 병렬** |
| 다른 class·**FK 의존** | ✅ Phase1 commit 순서 보존 (applier가 FK 못 봐서 보수적) | Phase1 제한 → **Phase2 server 그룹핑으로 회복** |
| **상속** 계층 공유 unique | ✅ FK와 동일 (실무 빈도 낮음) | FK와 동일 |
| **파티션** | ✅ 스키마 규칙(파티션키 ∈ 인덱스키)으로 충돌 불가 | ✅ 파티션별 병렬 |
| **재시작/복구** | ✅ 멱등 skip(commit_lsa ≤ baseline) → 중복 없음 | — |
| **롱 트랜잭션** | ✅ 멱등 전제·복구비용 수용 | 단일 tx는 1 worker(제한) |

## 4-4. FK가 핵심인 이유 (시나리오 깊게)
- **applier(applylogdb)는 FK를 모른다** — 복제 로그가 `class + PK`뿐이라, 두 트랜잭션이 FK로 엮였는지 알 수 없음. FK 검사는 **server**가 한다.
- 그래서 자식(order_items)을 부모(orders)보다 먼저 적용하면 **server FK 검사 실패 → 복제 중단**.
```
master:  T1 commit INSERT orders(100)   →  T2 commit INSERT order_items(100, FK→orders)
slave 비순차 병렬: T2가 먼저 → 부모 없음 → FK 위반 에러 → 복제 중단
해결: 부모 먼저 커밋 후 자식 적용 (commit 순서 보존)
```
- **상속(계층 공유 unique 인덱스)도 같은 가족** — 다른 subclass에 같은 키 비순차 적용 시 공유 unique 위반.
- → **applier가 못 막는 cross-class 위험 = FK + 상속.** 둘 다 **Phase 1(보수적 commit 순서 보존)** 이 커버.

## 4-5. Phase 1 / Phase 2 (병렬성 확장)
- **Phase 1 (applier)**: same-class 직렬 + FK/순서 의존은 commit 순서 보존 + 독립은 병렬. (복제 로그·server 변경 없음, 안전 우선)
- **Phase 2 (cub_server)**: FK 관련 병렬화는 **FK를 아는 server가 그룹 처리**로. (applier는 FK를 모르므로, FK 아는 계층에서 푸는 게 자연스러움)

## 4-6. 결론 2줄
- **correctness**: 모든 시나리오 안전 — same-class 직렬 + FK·상속은 commit 순서 보존 + 파티션은 스키마 규칙 + 재시작은 멱등 skip.
- **병렬성**: 독립·파티션은 최대, FK/상속은 Phase 2로 확장, "같은 class 다른 행"은 row/key가 향후 개선.

# 부록 B. 발표에서 받을 만한 질문 (대비)
- "왜 commit 순서를 꼭 지켜야 하나?" → FK/상속을 applier가 못 가려서(보수적). server가 FK를 검사하므로 비순차면 에러.
- "재시작하면 중복 적용 안 되나?" → 멱등 skip(commit_lsa ≤ baseline)으로 이미 적용분 건너뜀. 기존 코드에도 있음.
- "파티션·LOB은?" → 파티션은 스키마 규칙으로 안전, LOB 데이터는 복제 안 됨(외부 저장).
- "class 단위면 병렬 손해 아닌가?" → 맞음(같은 class 다른 행). 후속 row/key 단위로 개선.
