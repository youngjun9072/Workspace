# 쉽게 읽는 MySQL 복제본 초기 구축 — Clone Plugin과 GTID

> 대상: **이 모듈을 담당하지 않는 팀원**도 이해할 수 있게 쓴 입문용 가이드.
> 상세·소스/공식 문서 근거가 필요하면 → `10.initial_provisioning_clone_gtid.md`(전문가용)를 보세요.

새 복제본(replica)을 만들 때 핵심은 두 가지다 — **(1) 원본 데이터를 한 번 통째로 채워 넣고, (2) "어디서부터 실시간으로 따라갈지" 책갈피를 정확히 맞추는 것.** MySQL 8.0은 (1)을 **Clone Plugin**(빠른 물리 복사)으로, (2)를 **GTID 자동 위치 맞춤**으로 거의 자동화한다.

---

## 0. 사전 지식 (먼저 읽기)

복제를 잘 모르는 분을 위한 기본 용어. 비유 중심으로 가볍게.

- **복제(replication)**: 원본 DB의 변경을 다른 DB가 **자동으로 따라 적용**해 같은 데이터를 유지하는 것. 목적은 읽기 분산, 장애 대비(HA), 백업 등.
  - **source(원본)** / **replica(복제본)**: 보내는 쪽 / 받는 쪽.
- **binlog(바이너리 로그)**: source가 "무엇이 바뀌었는지"를 시간순으로 적는 **변경 일지**. replica는 이 일지를 받아 그대로 따라 적용한다.
- **복제 좌표(position)**: replica가 "그 변경 일지를 **어디까지** 읽어 적용했는지"를 가리키는 **책갈피**. 연결이 끊겼다 다시 붙을 때 이 책갈피 다음부터 이어받는다. 책갈피가 틀리면 → 변경 누락(데이터 유실)이나 중복(무결성 깨짐).
- **GTID(Global Transaction ID)**: 모든 트랜잭션(커밋 한 건)에 붙는 **전역 고유 번호표**. "binlog 파일 몇 번, 몇 바이트" 대신 **"이 번호표들까지 처리했다"** 로 진도를 관리한다. → 원본 서버가 바뀌어도(failover) 책갈피가 안 꼬인다.
- **초기 구축(provisioning)**: 새 replica는 **텅 비어 있으니**, 원본의 현재 데이터를 한 번 통째로 채워 넣는 작업.
- **스냅샷(snapshot)**: 어떤 **한 시점**의 데이터 전체 사진.
- **물리 복사 vs 논리 백업**:
  - **물리 복사** = 디스크 파일을 통째로 빠르게 복사(내용을 해석하지 않음). 대용량에 빠름.
  - **논리 백업** = 데이터를 SQL/행으로 뽑아 다시 넣음(느리지만 유연).

> 한 줄 비유: 새 직원(replica)에게 **회사 위키 전체를 복사해주고(초기 적재)**, "여기까지 읽었다"는 **책갈피(복제 좌표/GTID)** 를 같이 줘서, 그 다음 페이지부터 알아서 따라 읽게 하는 것.

## 1. 문제 — 빈 복제본을 어떻게 채우나

새 replica엔 원본 데이터가 없다. 그래서 두 가지를 **동시에** 해결해야 한다.

1. **초기 적재**: 원본의 현재 데이터 전체를 복사해 넣는다.
2. **시작 책갈피**: "그 데이터가 **어느 시점**의 것인가"를 정확히 잡는다. 이게 틀리면 트랜잭션이 누락되거나 중복 적용된다.

핵심은 **"복사한 데이터의 끝점"과 "이후 실시간 복제가 시작하는 점"이 딱 맞물려야 한다**는 것(= 핸드오프).

---

## 2. 방법 3가지 (쉽게)

### ① Clone Plugin (8.0.17+) — "통째로 빠르게 + 책갈피까지 같이"
- 원본의 InnoDB 데이터를 **물리적으로 통째 복사**한다. 명령 한 줄:
  ```sql
  CLONE INSTANCE FROM 'rep_user'@'원본호스트':3306 IDENTIFIED BY '비밀번호';
  ```
- **데이터뿐 아니라 책갈피(binlog 위치 + GTID)도 함께** 가져온다 → 복사 끝난 시점이 자동으로 표시됨.
- 대용량에서 논리 백업보다 훨씬 빠르다.
- **주의**: InnoDB 데이터만 복사(MyISAM/CSV는 빈 테이블), binlog·서버 설정은 복사 안 함, 원본과 **같은 버전·플랫폼**이어야 함.

### ② mysqldump (논리 백업) — "느리지만 유연한 전통 방식"
- 데이터를 SQL로 뽑아 새 서버에 다시 넣고, 그 시점 책갈피를 설정한다.
- 느리지만 버전/부분 복사 등 유연. 소규모나 특수 상황에 사용.

### ③ GTID 자동 위치 맞춤 (`SOURCE_AUTO_POSITION=1`) — "책갈피를 알아서 맞춤"
- 사람이 "파일 몇 번, 몇 바이트"를 지정할 필요가 없다.
  ```sql
  CHANGE REPLICATION SOURCE TO SOURCE_HOST='원본', SOURCE_AUTO_POSITION=1;
  START REPLICA;
  ```
- replica가 원본에게 "**나 이 번호표(GTID)들 가졌어**" 하면, 원본이 **빠진 것만 골라** 보내준다.
- 원본이 바뀌어도(failover) 새 원본에 그대로 붙기만 하면 알아서 빠진 것만 받는다 → **운영이 단순**.

---

## 3. 전체 흐름 (한눈에)

```
① 적재:   Clone Plugin으로 원본 데이터 통째 복사 (+ 책갈피 GTID 함께 받음)
② 핸드오프: 복사 끝점 = 이후 복제 시작점으로 맞춤
③ 실시간:  GTID 자동 위치로 복제 시작 → 원본이 "빠진 것만" 보내줌 → 따라잡은 뒤 계속 동기화
```

즉 **"통째로 빠르게 적재 → 책갈피 맞춰 실시간 복제로 매끄럽게 인계"** 가 8.0의 표준이다.

---

## 4. 꼭 알아둘 주의점 (쉽게)

- **클론 직후 "빨리" 복제를 붙여라.** 복사 시점과 복제 시작 사이에 원본이 **오래된 binlog를 지워버리면(purge)**, replica가 따라잡을 일지가 없어 에러가 난다(`ER_SOURCE_HAS_PURGED_REQUIRED_GTIDS`). → 원본의 binlog 보존 기간(`binlog_expire_logs_seconds`)을 넉넉히 둘 것.
- **replica에 직접 쓰지 마라.** replica에서 로컬로 쓴 트랜잭션은 그 서버에만 있는 "미아 GTID(errant transaction)"가 되어, 나중에 failover 때 충돌·에러를 일으킨다. → replica는 `super_read_only`로 잠가두는 게 안전.
- **버전·플랫폼이 같아야 Clone 가능.** 다른 버전끼리는 Clone이 아니라 논리 백업 경로를 써야 한다.

---

## 5. 한 문장 정리

> 새 복제본 만들기 = **Clone Plugin으로 원본을 통째로 빠르게 복사하고(책갈피 포함), GTID 자동 위치 맞춤으로 그 책갈피 이후 변경만 자동으로 이어받아 실시간 복제로 넘어가는 것.** 단, 클론 직후 바로 붙이고(binlog purge 주의), replica엔 직접 쓰지 않는다.
