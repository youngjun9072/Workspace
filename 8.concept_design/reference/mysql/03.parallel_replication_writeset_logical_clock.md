# MySQL 병렬 복제: WRITESET vs LOGICAL_CLOCK vs commit order 보존

> 자료조사 메모 · 조사 시점 2026-06-02
> 출처: MySQL 8.0/8.4 공식 매뉴얼 (1순위)
> ※ 정리 구조는 추후 재검토 예정. 우선 Q&A 내용 그대로 보존.

## 핵심 질문

"logical_clock으로 병렬복제를 수행하면 writeset으로 순서 보장을 하는 건가?"

→ 질문에 두 개념이 섞여 있다. 결론: **WRITESET은 "순서 보장"이 아니라 "의존성(충돌) 판단을 정밀하게 해서 병렬성을 늘리는" 역할이다.** 그리고 두 설정은 서로 대체 관계가 아니라 **source/replica 양쪽에서 함께 동작**한다.

## 두 설정은 위치가 다르다

| 설정 | 위치 | 하는 일 |
|---|---|---|
| `binlog_transaction_dependency_tracking` (WRITESET / COMMIT_ORDER / WRITESET_SESSION) | **source(master)** | 트랜잭션 의존성을 **어떻게 계산해서 binlog에 기록할지** 결정. 결과를 `last_committed` / `sequence_number`(= logical clock 값)로 인코딩 [1] |
| `replica_parallel_type=LOGICAL_CLOCK` | **replica** | binlog에 적힌 `last_committed`/`sequence_number`를 **읽어서 병렬 실행 가능 여부를 판단** [2] |

즉:

- **source가 WRITESET으로 계산** → "어떤 트랜잭션끼리 row/key가 겹치지 않는지"를 보고, 겹치지 않으면 병렬 가능하다고 binlog에 표시.
- **replica가 LOGICAL_CLOCK으로 적용** → 그 표시(logical clock)를 보고 병렬 dispatch.

따라서 "둘 중 뭘로 순서 보장하냐"가 아니라, **WRITESET(계산) → logical clock(전달) → LOGICAL_CLOCK(적용)** 한 파이프라인이다. WRITESET은 source가 logical clock 값을 만드는 방식이고, LOGICAL_CLOCK은 replica가 그 값을 쓰는 방식이다.

## "순서"는 세 갈래로 나눠서 봐야 한다

1. **충돌 트랜잭션의 순서(correctness)** — 같은 row를 건드린 트랜잭션은 WRITESET이 의존성으로 잡아 같은/연속 logical clock을 주므로, replica에서 병렬로 안 돌고 순서가 지켜진다. → WRITESET이 보장 [1].
2. **독립 트랜잭션의 병렬성** — row가 안 겹치면 WRITESET이 "독립"으로 표시 → 병렬 실행. COMMIT_ORDER보다 더 많이 병렬화된다(WRITESET의 핵심 이점) [1].
3. **최종 commit 가시 순서(global commit order)** — 병렬로 돌린 독립 트랜잭션이라도 최종 커밋 순서를 source와 똑같이 맞추는 건 **`replica_preserve_commit_order`** 가 담당한다. WRITESET이 아니다 [2].

## 정리

- WRITESET = "누가 누구랑 충돌하나"를 정밀(row/key)하게 판단 → 충돌하는 것만 순서 강제, 나머지는 병렬 허용.
- LOGICAL_CLOCK = replica가 그 판단 결과(logical clock)를 읽어 병렬 적용.
- 전체 commit 순서 일치는 별도로 `replica_preserve_commit_order`.

질문을 정확히 다시 쓰면:

> "지금은 (source가) WRITESET으로 의존성을 계산하고, (replica가) LOGICAL_CLOCK으로 그 결과를 읽어 병렬 적용한다. 충돌(같은 row) 트랜잭션의 순서는 WRITESET 의존성으로 지켜지고, 전체 commit 순서는 replica_preserve_commit_order로 맞춘다."

## CUBRID 코디네이터와의 대응 (참고)

- CUBRID 1차안의 "class-level 충돌 판단"은 MySQL WRITESET을 **class 단위로 거칠게 한 버전**에 해당한다.
- "순서 정리 단계의 committed_lsa 갱신"은 MySQL **`replica_preserve_commit_order`** 에 해당한다.

## COMMIT_ORDER vs WRITESET — `last_committed`를 채우는 두 방법

`last_committed`(병렬 가능 여부를 정하는 watermark)는 **누가 만들든 결과는 같은 토큰**이고, 그 값을 *무슨 기준으로 채우느냐*가 두 갈래다. 9.x는 WRITESET으로 고정됐지만, 두 방법을 같이 봐야 "왜 충돌 기반인가"가 설명된다. (둘은 같은 층의 대체재고, `last_committed`는 그 위/아래의 *전달 토큰* — 어느 방법이든 결과로 이 값을 만든다.)

**① COMMIT_ORDER — 타이밍(lock-based logical clock) 기준 [baseline]**
- 원본에서 **서로 락을 안 막고 동시에 진행한(= commit 구간이 겹친) 트랜잭션**을 독립으로 본다(WL#7165). 행이 뭘 바꿨는지는 **안 본다** — 비교하는 "값"은 `last_committed`/`sequence_number` 같은 **타이밍 논리시계 정수**뿐.
- PK·스키마·행 데이터가 전혀 필요 없다(거의 공짜). 대신 병렬 폭이 **원본 동시성에 비례** — 원본이 순차로 commit하면 replica도 거의 직렬.
- 안전하지 않은 문장(DB 단위 DDL·`ALTER ... ADMIN_PARTITION` 등)은 **배리어**로 막아 이후를 직렬화(`is_trx_unsafe_for_parallel_slave`).

**② WRITESET — 충돌(키 해시) 기준 [정밀화]**
- 트랜잭션이 바꾼 **행 키(PK/unique)의 해시 집합**이 겹치는지로 의존을 본다. 비교하는 "값"은 **키 해시**(행 데이터 자체는 안 봄). 키만 안 겹치면 **원본 commit 순서와 무관하게** 독립 → 원본이 단일 스레드여도 병렬.
- PK/unique 필요. FK·DDL 등은 COMMIT_ORDER로 fallback.

**③ 둘의 관계 — 대체가 아니라 합성**: WRITESET은 COMMIT_ORDER baseline을 **`min`으로 더 낮추기만** 한다(병렬 확대). 정확성은 COMMIT_ORDER가 떠받치고 WRITESET은 병렬만 넓힌다 → **위험 방향으로는 절대 못 간다.** (코드·예시 → `04.writeset_concept.md` §5.1·§5.3)

**→ CUBRID 적용**: CUBRID는 `(class, PK)` 충돌을 마스터(cub_server, 스키마/FK 인지)가 계산하는 **WRITESET식**을 채택하고(설계 D.4), 그 결과를 `last_committed`류 토큰으로 전달한다. COMMIT_ORDER식(복제 로그 commit 순서/LSA 타이밍)은 **충돌 정보를 못 쓰는 구간의 안전 backstop**으로만 둔다 — "정확성=commit-order, 병렬=writeset"의 역할 분담을 그대로 가져오는 것.

## 흔한 혼동 정리 (예전 조사 노트 교정)

예전 조사에서 섞여 적힌 것들을 바로잡는다.

- **"같은 그룹(Logical Clock)으로 묶이는 기준"은 *모드별 대안*이지 동시 적용이 아니다.** `COMMIT_ORDER` = "source에서 **같이 commit된 묶음(group commit)**"을 독립으로, `WRITESET` = "**바꾼 행/키가 안 겹침(충돌 없음)**"을 독립으로 본다. 한 시스템에서 둘 중 **하나**만 활성이다. (예전 노트가 두 기준을 동시 조건처럼 적었는데, 실제론 모드 선택이다.)
- **"Logical Clock으로 묶인다"의 주체 구분.** *묶음을 결정*하는 건 source(위 모드)이고, `replica_parallel_type=LOGICAL_CLOCK`은 그 결과(`last_committed`/`sequence_number`)를 **읽어 병렬 적용**하는 replica 쪽이다.
- **group commit은 ON/OFF 스위치가 아니다.** MySQL 5.6부터 **항상 동작**하는 binlog 배칭 방식이고, `binlog_group_commit_sync_delay` 등으로 **배칭 정도만 튜닝**한다. `COMMIT_ORDER`에서만 그 배칭 크기가 replica 병렬 폭을 좌우했고, **`WRITESET`은 group commit과 무관**하다(행/키 충돌로 판단, "execution order independent").
- **버전.** `binlog_transaction_dependency_tracking`은 8.0.35부터 deprecated, **8.4·9.x는 변수 제거 → 항상 `WRITESET`**(9.7.0 소스에서 변수 제거 확인). 따라서 "group commit 기준" 자체가 옛 8.0 `COMMIT_ORDER` 한정이다. (변수 수명·기본값 반전·릴리즈 날짜 상세는 아래 "버전별 정리" 표 참조.)
- **`innodb_flush_log_at_trx_commit`(내구성)은 병렬화 메커니즘이 아니다.** commit마다의 redo flush/fsync 빈도(0/1/2)를 정하는 **내구성** 설정으로, 병렬 판단과 무관하다. 다만 *복제 적용 속도(lag)* 에는 영향이 커서(완화하면 apply가 빨라짐) 흔히 병렬 파라미터와 혼동되는데, **다른 축**이다(상세·실측은 `13.mts_performance_real_measurements.md`).

### 지난번 사내 공유자료 정정

지난번 공유자료에서는 이렇게 언급되어 있었는데 — *"병렬화 파라미터: `innodb_flush_log_at_trx_commit`; Logical Clock 방식 = master 커밋 시점(순서)을 **Logical Clock(GTID)** 값으로 부여, **Logical Clock 값이 같으면** slave 병렬·다르면 순차; 묶음 기준 = 충돌 없음 / group commit으로 같은 시점 커밋"* — 몇 군데 정정이 필요하다.

1. **`innodb_flush_log_at_trx_commit`는 병렬화 파라미터가 아니다** — 내구성 설정(위 항목).
2. **Logical Clock ≠ GTID.** Logical Clock은 binlog에 적히는 **`(last_committed, sequence_number)` 쌍**이고, GTID는 *별개*의 전역 트랜잭션 ID다. 공유자료에 첨부됐던 binlog 덤프 자체가 이를 보여준다 — 한 이벤트에 `Anonymous_GTID`(GTID 미사용=ANONYMOUS)와 `last_committed`/`sequence_number`가 **각각 따로** 찍힌다:
```text
... Anonymous_GTID  last_committed=8907  sequence_number=8911 ...
... Anonymous_GTID  last_committed=8907  sequence_number=8912 ...
... Anonymous_GTID  last_committed=8908  sequence_number=8913 ...
... Anonymous_GTID  last_committed=8908  sequence_number=8914 ...
```
즉 GTID(여기선 ANONYMOUS)와 logical clock은 같은 이벤트의 **다른 필드**다. "Logical Clock(GTID)"라는 등치는 부정확.
3. **병렬 기준은 "같은 Logical Clock 값"이 아니라 "같은 `last_committed`"** 다(정확히는 *내 `last_committed` 이하 sequence_number가 모두 commit되면 병렬*). 위 덤프에서 `seq 8911·8912`는 `last_committed=8907`로 같아 **slave에서 병렬 적용 가능**, `8913·8914`는 `last_committed=8908`이라 앞 그룹과 의존이 다르다. (`sequence_number`는 트랜잭션마다 1씩 느는 **고유 번호**라 "값이 같다"가 성립할 수 없다 — 묶는 키는 `last_committed`다.)
4. **"묶이는 기준" 두 줄은 동시 조건이 아니라 모드 택1**: `COMMIT_ORDER`(group commit으로 같은 시점) / `WRITESET`(충돌 없음). 8.4·9.x는 `WRITESET` 강제(위 버전 항목).

## 버전별 정리 — 의존성 추적 모드의 수명

`binlog_transaction_dependency_tracking`(source 측, `last_committed`를 무엇 기준으로 계산할지 고르는 변수)의 생명주기와, 우리가 분석에 쓰는 두 트리(8.0.46 / 9.7.0)가 어디 위치하는지.

| 버전 | 변수 상태 | 기본/강제 동작 | 모드 선택 |
|---|---|---|---|
| 8.0.1 | 도입(WRITESET 추가) | COMMIT_ORDER | 가능 |
| 8.0.35 | deprecated(경고, 정상 작동) | COMMIT_ORDER | 가능 |
| **8.0.46** | **존재 + deprecated** | **COMMIT_ORDER** | 가능(3값 다) |
| 8.4 LTS · 9.0~9.6 · **9.7 LTS** | **제거(없음)** | **WRITESET 강제** | 불가 |

- **deprecated ≠ 제거.** 8.0.46은 변수가 *살아 있고* `SET ... = WRITESET`이 동작한다(경고만 붙음). 8.4부터는 변수 자체가 없어 같은 SQL이 "Unknown system variable" 에러다.
- **기본값이 반전된다.** 8.0.46 기본은 `COMMIT_ORDER`(선택형)인데 8.4/9.x는 `WRITESET`을 강제한다 — 단순히 8.0 기본을 굳힌 게 아니라 동작이 뒤집힌다. 9.7.0 소스에서 `Transaction_dependency_tracker::get_dependency()`(`sql/rpl_trx_tracking.cc:336`)가 모드 분기 없이 `commit_order → writeset` 2단 합성을 **무조건** 실행함을 확인 — 즉 `04.writeset_concept.md` §5.1의 합성 알고리즘이 9.x에선 유일 경로다.
