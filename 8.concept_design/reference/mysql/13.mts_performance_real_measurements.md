# MySQL/MariaDB 멀티스레드 복제 성능 실측 — "워커 N개 = N배"인가

> 자료조사 · 조사 시점 2026-06 · 출처: Jean-François Gagné(Booking.com/MariaDB), Percona, MySQL 공식 블로그(1·2순위)
> 용도: "워커 N개면 최대 N배"라는 기대가 실측과 얼마나 다른지에 대한 근거 모음.
> 같은 폴더 `11.writeset_fk_dependency_tracking.md`·`12.rpco_benchmark_and_lag_measuring.md`와 짝.

## 요약

- **"워커 N개 → 최대 N배"는 이론적 상한(best case)** 일 뿐, 대규모 프로덕션 실측은 거의 항상 그보다 한참 낮은 **sub-linear**다 [1].
- Jean-François Gagné의 Booking.com 프로덕션 실측(MariaDB 병렬 복제): CPU-bound에서 **best ~2.1×**(고내구성 E2), 일부 **~1.56×**(E1), **내구성을 완화하면 <1.1×**(거의 없음), **IO-bound는 ~1.29×** [1].
- 핵심 병목은 **롱(대형) 트랜잭션** — 이게 병렬 파이프라인을 멈춰 세워 병렬화를 막는다 [1].
- Percona: 워커 16개로 따라잡되, **100-worker가 20-worker 대비 이득 없음**(명백한 diminishing returns) [5]. 병렬 가능 폭은 **소스(binlog)가 정하므로** 적용 전에 추정해야 한다 [6].
- 결론: **측정 없이 "N배"를 약속하면 안 된다.** 실제 배수는 워크로드(CPU/IO)·durability·소스 병렬성·코어 수에 묶인다.

## 본문 (실측 사실)

### 1. Jean-François Gagné — Booking.com 프로덕션 벤치마크 (MariaDB 병렬 복제)

가장 신뢰할 만한 대규모 프로덕션 실측이다. 백업을 복원하고 버퍼풀을 데운 뒤 **"프로덕션 24시간치 트랜잭션을 슬레이브가 처리하는 데 걸린 시간"** 을 측정, `slave_parallel_threads`를 1→다수로 바꿔 6개 구성(binlog·durability 조합)으로 비교했다 [1].

측정된 speedup [1]:

| 워크로드/구성 | speedup |
|---|---|
| CPU-bound, 고내구성 (E2) | **~2.10×** |
| CPU-bound, 고내구성 (E1) | ~1.56× |
| CPU-bound, 내구성 완화 | **<1.10×** (거의 없음) |
| IO-bound (E4) | ~1.29× |

- **병목 = 롱 트랜잭션**: 큰 단일 트랜잭션이 슬레이브의 병렬 파이프라인을 stall시켜 병렬화를 막는다 → "대형 트랜잭션을 쪼개는 것"이 후속 과제라고 결론 [1].
- 흥미로운 관찰: 코어가 24스레드뿐인데도 워커를 80~2560까지 늘리면 speedup이 더 오르더라 — 단 이는 CPU 병렬이 아니라 **replication prefetching**(워커가 캐시에 없는 데이터를 미리 디스크에서 읽게 하는) 효과로 해석된다(= 진짜 commit 병렬의 배수가 아님) [1][2].
- 저자 소회: CPU-bound에선 **병렬 복제를 켜는 것보다 durability를 완화하는 게 개선이 더 컸다** — "마스터 쓰기를 25% 더 받는 정도로는 장기적으로 부족"하다고 다소 실망 표현 [1].

### 2. Percona — 운영 관점 실측·도구

- 워커 16개면 따라잡지만, **100-worker 슬레이브가 20-worker 대비 이득이 없다**(워커를 무작정 늘려도 소용없음) [5].
- 병렬 가능 폭은 **binlog(소스)의 의존 구조가 결정**하므로, 적용 전에 "이 binlog가 얼마나 병렬 가능한지"를 추정하는 방법을 제시한다 [6]. → 워커 수를 늘리기 전에 *available parallelism*부터 봐야 한다.

### 3. MySQL 공식 / 기타 — writeset로 병렬 폭 넓히기

- source에서 **WRITESET 기반 의존성 추적**을 켜면 독립 트랜잭션을 더 많이 노출해 replica 병렬 폭이 커지고 lag이 준다(공식 블로그의 lag 감소 그래프) [7]. 단 이것도 "독립성이 있을 때" 얘기라 상한은 여전히 워크로드가 정한다.
- 같은 결론을 운영 사례로 보인 글: Airtable 엔지니어링(writeset로 lag 최적화) [8], Percona 커뮤니티(lag 줄이기) [9].

## 추론 / 유추 (※ 위 사실에 대한 우리 해석)

- "N개 워커 = 최대 N배"에서 **N은 도달하기 어려운 상한**이다. 근접하려면 *모든 트랜잭션이 독립 + CPU-bound + 코어 충분 + durability 느슨*이어야 하는데, 실제 워크로드는 그렇지 않다 → 프로덕션 ~2×, IO-bound ~1.3×가 현실값 (← [1][5]).
- sub-linear의 원인은 `12...md`의 분석과 동일: ① 소스가 만든 독립성 상한 ② 공유 자원/Amdahl ③ tx당 고정비 ④ 뚱뚱한 단일 tx(= [1]이 지목한 롱 트랜잭션 병목).
- **CUBRID PoC(약 3.4×)와의 비교 주의**: 우리 3.4×는 *단순 insert + dwb=0(내구성 완화) + `tranid%worker`로 의존성 무시* 라는 유리한/인위적 조건이라 [1]의 프로덕션 수치와 직접 비교 불가다. 의존성을 지키는 정식 코디네이터를 넣으면 배수는 줄 수 있다(본 설계 Q15). 즉 우리도 **"N배" 가정 없이 코디네이터 오버헤드 포함 실측이 필수**라는 같은 입장.
- **내구성은 병렬과 다른 축**: 위 "durability"는 주로 `innodb_flush_log_at_trx_commit`(commit마다의 redo flush/fsync 빈도, 0/1/2) 같은 설정을 가리킨다. 이건 *병렬화 메커니즘이 아니라* commit 비용을 줄여 apply를 빠르게 하는 **내구성 레버**다 — JFG가 CPU-bound에서 "병렬보다 내구성 완화가 더 효과적"이라 한 게 이 축이다. lag을 줄이는 두 축(병렬 vs 내구성)을 섞지 말 것(예전 조사에서 병렬 파라미터로 혼동됨).
- 회사 보고용 한 줄: *"워커 N개 = N배"는 상한값이며, 공개 프로덕션 실측은 1.1~2.1×(IO-bound 더 낮음)다. 실제 배수는 워크로드·소스 병렬성·durability·코어로 결정되므로 우리 워크로드로 측정해 제시해야 한다.*

## 미해결 / 자료 부족

- JFG의 프로덕션 수치는 **MariaDB 병렬 복제** 기반이다(개념은 유사하나 MySQL 5.7/8.0 LOGICAL_CLOCK·WRITESET과 구현 차이 있음). **MySQL 8.0 + WRITESET 환경의 동급 프로덕션 speedup 공개 수치**는 별도 확인 필요.
- 본 문서 수치는 원문 요약/1차 확인 기반이라, 회사 공식 보고에는 그래프·표 원문을 직접 인용 권장.
