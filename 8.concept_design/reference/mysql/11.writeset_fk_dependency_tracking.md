# MySQL WRITESET 의존성 추적과 외래키(FK) 처리

> 자료조사 문서 · 조사 시점 2026-06 · 출처: MySQL 공식 블로그·WorkLog(1순위), MySQL Bugs(참고)
> 용도: "master(source)가 트랜잭션별 의존 그룹을 미리 계산해 내려보내는" 방식(= CUBRID Phase 2 방향)의 근거.
> 같은 폴더 `03.parallel_replication_writeset_logical_clock.md`(LOGICAL_CLOCK 기초)와 짝.

## 요약

- MySQL은 source에서 트랜잭션마다 **writeset**(바꾼 행들의 키 해시 집합)을 만들어 의존성을 계산하고, 그 결과를 **logical clock(`sequence_number` + `last_committed`)** 으로 binlog에 실어 replica가 병렬 적용하게 한다 [1][2].
- writeset에는 **변경 행의 PK/unique 키 해시뿐 아니라, 경우에 따라 외래키(FK) 키 해시도 포함**된다 — 그래서 부모·자식 트랜잭션이 충돌로 묶여 순서가 보존된다 [1][2].
- 단 MySQL조차 FK를 완벽히 다루지 못한다: **FK·DDL·필터·savepoint가 끼면 WRITESET이 COMMIT_ORDER로 fallback**(sub-optimal)하고 [2], 같은 부모를 참조하는 자식들이 **false conflict로 과직렬화**되며(Bug #111146) [3], "FK를 writeset에 넣지 말자"는 논쟁도 있다(Bug #110071) [4].
- 시사점: master-side·FK-aware 의존 계산은 **정확성(부모→자식 순서)을 확보**하지만 FK 관련 쌍의 **병렬을 일부 잃는다** — 정확성과 병렬도의 트레이드오프가 FK에 집중된다.

## 본문

### 1. WRITESET이 푸는 문제

8.0의 기본 모드였던 `COMMIT_ORDER`는 source의 group commit 묶음(같이 commit된 트랜잭션)만 replica에서 병렬로 본다. 즉 "언제 같이 commit됐나"라는 *실행 순서*에 의존한다. `WRITESET`은 이를 *데이터 충돌*로 바꾼다 — 두 트랜잭션이 바꾼 행 집합이 안 겹치면, 설령 source에서 순차로 commit됐어도 replica에서 병렬 가능으로 표시한다 [1][2]. 8.4 LTS 이후에는 `binlog_transaction_dependency_tracking` 변수가 제거되어 source가 기본적으로 `WRITESET` 방식으로 의존성 정보를 만든다.

### 2. writeset 구성과 logical clock

- **writeset** = 트랜잭션이 바꾼 각 행을 식별하는 **해시 집합**. 행의 **PK(및 unique 키)** 해시가 들어가고, **필요한 경우 FK 등 추가 의존 키의 해시**도 포함된다 [1][2].
- source는 이 writeset을 직전까지의 history와 비교해 충돌 여부를 판정하고, 각 트랜잭션에 **`sequence_number`**(단조 증가 논리 순번)와 **`last_committed`**(이 트랜잭션이 기다려야 하는 가장 최근 선행의 sequence_number)를 매겨 binlog에 적는다.
- replica의 coordinator(`replica_parallel_type=LOGICAL_CLOCK`)는 `last_committed` 이하가 모두 끝났으면 병렬로 보낸다. **충돌(FK 포함)이 있으면 `last_committed`가 선행 쪽으로 올라가 직렬화**된다.
- 중요한 점: **writeset 자체는 binlog에 실리지 않는다.** source가 `last_committed` 계산에만 쓰고, replica엔 계산 결과(`sequence_number`/`last_committed`)만 전달된다 [1].
- 모드는 `binlog_transaction_dependency_tracking`(`COMMIT_ORDER`/`WRITESET`/`WRITESET_SESSION`)으로 정하고, writeset history 크기는 `binlog_transaction_dependency_history_size`로 제한한다 [1].

### 3. FK 처리의 실제 — 정확하지만 보수적

- **fallback to COMMIT_ORDER**: WL#9556은 "DDL, FK, filter, savepoint는 commit order로 되돌리는 sub-optimal 방식으로 처리하며, 추후 최적화 예정"이라고 명시한다 [2]. 즉 FK가 끼면 정밀 병렬을 일부 포기하고 안전한 commit-order로 떨어진다.
- **부모 INSERT 시 history clear**: 부모 테이블에 FK 관련 행을 넣으면 dependency tracking이 COMMIT_ORDER로 되돌고 `m_writeset_history`를 비운다는 동작이 보고된다 [2].
- **false conflict(과직렬화)**: 같은 부모를 참조하는 **서로 다른 자식 INSERT**는 동일한 FK 키가 writeset에 추가되어, 실제로는 독립인데도 replica에서 병렬 적용되지 못한다(Bug #111146) [3]. 이 때문에 "FK는 writeset에 넣지 말아야 한다"는 의견도 있다(Bug #110071) [4].

### 4. 정리 — master-side FK-aware 의존의 득과 실

| 측면 | 효과 |
|---|---|
| 정확성 | 부모→자식 순서가 의존으로 표현되어 보존됨(applier가 FK를 추측할 필요 없음) |
| 병렬도(독립 tx) | writeset 비교로 충돌 없는 트랜잭션은 최대 병렬 |
| 병렬도(FK 관련 tx) | fallback·false conflict로 **상당히 잃을 수 있음** |
| 비용 | source의 writeset 계산·history 메모리, binlog에 logical clock 추가 |

## 추론 / 유추

- CUBRID로 가져오면, master(cub_server)는 스키마(FK)를 알므로 **트랜잭션별 conflict key = {바꾼 PK} ∪ {참조한 FK 부모 PK}(+ cascade 영향 행)** 를 계산해 repl 로그에 logical clock(또는 conflict key 원재료)을 실을 수 있다 — applier가 FK를 못 가려 생기던 문제(슬레이브 측 보수적 처리·silent skip)를 근본적으로 없앤다 (← [1][2], CUBRID 설계 D.2/D.4).
- 다만 MySQL의 교훈상 **FK 쌍의 과직렬화·fallback은 CUBRID에서도 그대로 위험**이다. "FK를 conflict로 전부 넣을지(정확·과직렬), 진짜 부모-자식 쌍만 좁게 묶을지"가 설계 결정 포인트다 (← [2][3]).
- 롱 트랜잭션이 부모면 자식은 그 commit까지 기다려야 하는데, 이는 master-side 그룹핑으로도 사라지지 않는 FK 본질적 비용이다(대신 정확해짐) (← [3]).

## 미해결 / 자료 부족

- MySQL writeset에 FK 키가 **정확히 어떤 형태로**(참조 부모의 PK 해시 그대로인지, 별도 인코딩인지) 들어가는지의 소스 레벨 세부는 본 조사(블로그·WL·버그 리포트)만으로는 단정 못 함 — 필요 시 소스(`rpl_write_set_handler.cc` 등) 확인.
- `binlog_transaction_dependency_history_size` 기본값 등 수치는 버전별로 다를 수 있어 본 문서에선 단정하지 않음(공식 변수 페이지 재확인 권장).
- cascade FK(ON DELETE/UPDATE CASCADE)가 writeset에 어떻게 반영되는지는 미확인.
