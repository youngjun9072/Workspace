## 기초 (🟢 주니어)

### Q1. [Act A] LSA가 정확히 뭐고, 왜 슬레이브와 마스터의 LSA가 별개 값인가? — 🟢
**A.** LSA(Log Sequence Address)는 트랜잭션 로그 안의 위치를 가리키는 번호표로, 구조상 **로그 페이지 id(`pageid`) + 페이지 내 오프셋(`offset`)** 으로 이루어진다(`log_lsa.hpp:35`, pageid 48bit·offset 16bit). 즉 "몇 번 로그 페이지의 몇 바이트 지점"이다(로그 파일 번호가 아니라 페이지 id 기준). master와 slave는 **각자 자기 로그를 따로 가진다.** CUBRID는 논리 복제라 slave가 마스터의 변경을 "다시 실행"해 **자기 로그를 새로 쓰므로**, 같은 행을 복제하더라도 그게 기록된 위치(LSA)는 두 서버에서 독립적이다. (만약 물리 복제였다면 마스터 로그를 그대로 복사하므로 LSA가 일치할 것이다.) 그래서 applylogdb는 "마스터 로그를 어디까지 받아 반영했나"를 마스터 기준 LSA(`required_lsa`/`committed_lsa`)로 추적한다.

### Q2. [Act A] "로지컬(행 재실행) 복제"가 물리 복제랑 구체적으로 뭐가 다른가? — 🟢
**A.** 물리 복제는 마스터가 디스크에 쓴 **로그(페이지 변경 바이트)를 그대로 복사**해 슬레이브에 재생한다 — 슬레이브는 마스터와 똑같은 페이지를 만든다. 논리 복제는 변경을 **"이 테이블의 이 행을 이렇게 INSERT/UPDATE/DELETE했다"는 의미로 추출**해 슬레이브에서 다시 적용한다. CUBRID applylogdb가 후자다(정확히는 SQL 문자열이 아니라 변경된 행 이미지를 서버 내부 경로로 재적용). 그래서 슬레이브는 같은 결과 데이터를 갖지만 거기에 도달하는 과정(로그)은 마스터와 다르다.

### Q3. [Act A] 왜 복제 적용을 병렬화하나 — 마스터가 이미 처리한 걸 슬레이브가 따라 하는 건데 그게 왜 느리고, 느리면 왜 문제인가? — 🟢
**A.** 마스터는 여러 클라이언트가 멀티코어로 동시에 쓰지만, 슬레이브의 applylogdb는 (현재) 사실상 한 줄로 따라 적용하므로 마스터를 못 따라가 **복제 지연(lag)** 이 쌓인다. lag이 나쁜 이유는 두 가지다. ① 마스터 장애로 슬레이브가 대신 떠야 할 때, 뒤처진 만큼 데이터가 유실된다(failover RPO). ② 슬레이브를 읽기용으로 쓰면 오래된 데이터를 보게 된다. 그래서 슬레이브도 멀티코어를 써서 병렬로 따라잡으려는 것이다.

### Q4. [Act D] FK(외래키)가 뭐고, "applier는 FK를 모른다"가 왜 설계를 좌우하나? — 🟢
**A.** FK는 "자식 행이 부모 행을 참조한다"는 제약이다(예: `order_items.order_id`는 `orders.id`를 가리킨다 — 부모 주문이 없으면 자식 항목을 넣을 수 없고, 서버가 이를 막는다). 문제는 applier가 받는 복제 로그에는 `class + PK`만 있어서, 두 트랜잭션이 부모-자식으로 엮였는지 **알 수 없다.** 그래서 코디네이터가 둘을 "독립"으로 착각해 병렬로 보내고 자식이 부모보다 먼저 적용되면, 슬레이브 서버의 FK 검사에 걸려 **apply 에러가 나고 복제가 멈춘다.** 이 한 가지 사실이 "그럼 안전하게 순서를 지키자"는 설계 방향을 만들었다.

### Q5. [Act D] "commit 순서를 보존한다"는 게 결국 순차 실행이랑 뭐가 다른가 — 순서를 지킬 거면 병렬로 한 의미가 없지 않나? — 🟢
**A.** "병렬 실행"과 "commit 순서 보존"은 다른 층이다. 비유하면, 여러 일꾼이 **동시에 일은 하되**(병렬), "완료 도장"은 **접수 순서대로** 찍는 것이다. 서로 독립인 트랜잭션은 워커들이 동시에 적용하고, 진도(`committed_lsa`)만 마스터의 commit 순서대로 전진시킨다 — 이러면 병렬 이득은 얻으면서 외부에는 항상 마스터와 같은 순서로 보인다. 다만 FK처럼 순서가 진짜 중요한 쌍은 어쩔 수 없이 직렬이 되고, 그만큼만 병렬을 포기한다.

### Q6. [Act F] 재시작 후 "다시 적용해 중복"이라는데, 같은 INSERT를 또 하면 에러 나거나 덮어쓰면 되지 않나 — 왜 이게 병렬에서만 새로 생기나? — 🟢
**A.** 직렬로 적용하면 "어디까지 했다"는 진도(watermark)가 곧 **실제로 끝낸 지점**이라, 재시작 시 그 뒤만 다시 하면 깔끔하다. 그런데 병렬이면 뒤 트랜잭션이 앞 트랜잭션보다 **먼저 디스크에 commit**될 수 있다. 그러면 진도(commit 순서대로만 올라감)보다 앞서 커밋된 게 생기고, 재시작 시 "진도 이하는 건너뛴다"는 규칙이 그걸 못 걸러 **다시 적용**한다. 다시 적용한 INSERT가 중복키 에러를 내면 복제가 멈추고(Q5의 FK처럼), 운이 좋아 덮어써도 다른 문제가 생길 수 있다(→ Q15). 직렬이면 안 생기는, 병렬화의 부작용이다. (설계 결정: F.2에서 **워커의 durable commit 순서를 source 순서로 강제(MySQL SPCO식)**하여 out-of-order durable commit 자체를 막기로 정했다 — 이러면 진도 watermark 하나로 재시작이 정확해져 이 문제가 원천 차단된다.)

## 중급 (🔵 DB 3년차)

### Q7. [Act D.2] 복제 로그에 이미 PK가 있으니, class가 아니라 PK까지 키로 쓰면 로그 포맷 변경 없이도 Phase 1에서 행 단위 충돌 판단이 가능하지 않나? — 🔵
**A.** 기술적으로 맞다 — 단, **PK 단독이 아니라 `(class, PK)` 복합키**여야 한다. PK 값만으로는 어느 테이블의 행인지 구분되지 않기 때문이다(서로 다른 테이블이 같은 PK 값을 가질 수 있다). 다행히 복제 로그 항목(`LA_ITEM`)은 `class_name`과 PK(`packed_key_value`/`key`)를 **별개 필드로** 담으므로(`log_applier.c`의 `la_make_repl_item`이 `or_unpack_string_alloc`으로 class_name을, 이어서 packed_key_value를 따로 언팩), 둘을 합친 `(class, PK)`를 충돌키로 쓰면 로그 포맷 변경 없이 행 단위 판단이 가능하다(설계상 class 식별자는 OID 확정이므로 `class_name→OID` 해석 후 `(class OID, PK)`). 1차안을 class 단위로 둔 건 순전히 보수성·단순성 때문이다: 같은 class면 무조건 직렬이라 correctness 판단이 자명하고, `(class, PK)` 해시셋 비교·충돌 추적의 메모리/로직 부담이 없다. 다만 PK 정밀화를 해도 **cross-class 의존(FK)은 여전히 못 잡으므로**(그건 PK가 아니라 class 간 관계 문제) 가장 큰 위험은 그대로다. 그래서 "구조부터 검증"이 1차 목표였는데, 지적대로 **"Phase 1.5: same-class를 PK로 정밀화"(로그 무변경)** 는 충분히 합리적인 다음 스텝이다. 문서의 단계 구분을 그렇게 세분화할 가치가 있다.

> **🔎 재검토 (PK 정밀화의 함정 — same-class도 PK가 다르면 다른 워커로 병렬되는데, 그게 항상 안전한가):** `(class, PK)`로 정밀화하면 같은 class라도 PK가 다른 행은 독립으로 보고 서로 다른 워커에 병렬 분배된다 — 이것이 정밀화의 이득(실행 병렬도↑)이다. **그러나 `(class, PK)`는 PK 충돌만 잡고, PK가 아닌 same-class 충돌은 놓친다.** ① **보조 unique 제약**: `PK(id)` 외 `UNIQUE(email)`이 있을 때 `Tx1=(id=1,email=x)`/`Tx2=(id=2,email=x)`는 PK가 달라 병렬로 판단되지만 email unique에서 충돌 → 비순차 적용 시 서버가 중복키 에러 → 복제 중단. ② **FK·상속 공유 unique**: class 경계를 넘는 문제라 `(class, PK)`로는 당연히 못 잡는다(Q8/D.4). 즉 **1차안의 class 단위 직렬화가 "느리지만 안전"한 이유가 바로 이것** — 같은 class를 통째로 직렬화하면 PK 충돌이든 보조 unique 충돌이든 전부 자동으로 막히기 때문이다(D.2 146줄이 이 논리에 기댄다). → **정밀화로 갈 때는 충돌키를 `(class, PK)`가 아니라 `(class, PK + 모든 unique 키)`로 확장하거나, 보조 unique/FK가 걸린 class는 class 직렬화로 남기는 처리를 반드시 함께 설계해야 한다.** (commit 순서는 정밀화와 무관하게 전역 강제(A안)되므로 재시작 정합은 영향 없음 — 이득/위험 모두 "실행 병렬도" 층위.)

### Q8. [Act D.4] FK 관계는 슬레이브 `SM_CLASS`에 있는데, 코디네이터가 기동 시 FK 그래프를 한 번 읽어 두면 "보수적 전체 순서 보존"보다 훨씬 좁게 직렬화할 수 있지 않나 — 왜 거의 검토 안 됐나? — 🔵
**A.** 정확한 지적이고, 사실 D.4도 "별도로 스키마 FK 메타를 읽어 와야 한다"고 한 줄 언급은 한다 — 다만 약하게 다뤘다. FK는 "복제 로그에" 없을 뿐 슬레이브 스키마엔 있으니, 기동 시 FK 의존 그래프를 만들어 FK로 엮인 class만 직렬화하면 나머지는 병렬로 둘 수 있어 보수적 전체 순서보다 훨씬 낫다. 1차에서 비중을 낮춘 이유는 (a) FK 그래프 로드 + DDL 시 갱신·무효화 로직이 필요하고 (b) FK가 없는 앱-레벨 인과는 여전히 못 잡으며 (c) 우선 최소 구조를 검증하려 했기 때문이다. **이건 Phase 1의 유력한 개선안이라 문서에 정식 옵션으로 끌어올릴 가치가 있다.**(좋은 지적)

### Q9. [Act C.3 / D.5] MySQL은 source가 writeset으로 watermark를 미리 계산해 내려주는데 CUBRID는 그 계산을 apply 측 코디네이터가 한다 — 트랜잭션이 폭주하면 단일 코디네이터의 충돌 판단 자체가 새 병목이 되어 PoC의 3.4배가 깎이지 않나? — 🔵
**A.** 실재하는 위험이다. MySQL은 의존성 계산을 source에 분산시키지만, CUBRID 설계는 그 판단을 apply 측 단일 코디네이터(=LogReader)가 한다. class set 교집합 비교는 가벼운 편이지만(변경 class 수에 비례), 트랜잭션 폭주 + pending 재평가가 겹치면 단일 스레드 판단이 병목이 될 수 있다. 더 솔직히 말하면, **PoC의 3.4배는 의존성 판단이 아예 없는(`tranid%worker`) 수치**라, 코디네이터 오버헤드를 넣은 뒤 반드시 재측정해야 한다(→ Q14). 완화책은 판단 비용을 O(변경 class 수)로 낮게 유지하고 pending 재평가를 효율적 자료구조로 두는 것이다.

### Q10. [Act D.2] 현실 OLTP는 한 트랜잭션이 여러 테이블을 함께 바꾸는 경우가 흔한데(주문 = orders + order_items + inventory), 그러면 changed class 집합이 커져 후속과 자주 겹치고, class 단위 병렬화가 best가 아니라 worst에 가까워지지 않나? — 🔵
**A.** 타당하고, 사실 class 단위 방식의 가장 큰 약점이다. 한 트랜잭션의 changed class fan-out이 크면 후속 트랜잭션과 class가 겹칠 확률이 올라가 병렬성이 급격히 떨어진다. 문서가 "현실은 중간"이라 한 것은 다소 낙관적일 수 있고, **워크로드의 class fan-out과 hot class 분포에 따라 실제로는 worst에 가까울 수 있다.** 이것이 row/key 정밀화(D.5)가 필요한 핵심 동기이며, "class 단위로 충분한가"는 가정이 아니라 **실측으로 검증할 항목**이다(특정 워크로드에서 병렬 효과가 미달이면 Phase 2 트리거).

### Q11. [Act F.1] 재시작 시 중복 적용이라는데, INSERT는 unique 위반으로 막힌다 쳐도 `balance = balance - 100` 같은 비멱등 UPDATE는 중복 적용 시 값이 틀어지지 않나? — 🔵
**A.** 핵심을 짚었다 — 중복 적용의 위험은 "skip 누락"만이 아니라 **연산의 멱등성**에 달려 있다. 다행히 CUBRID applylogdb는 변경을 **행 이미지(after-image, 절대값)로 재적용**한다(A.2의 locator 복제 경로) — 즉 UPDATE도 "이 행을 이 값으로"라는 절대 결과를 적용하므로 다시 적용해도 같은 값이 되어 **값 자체는 멱등**이다. `balance = balance - 100` 같은 상대 연산이 그대로 로그에 남는 게 아니라 결과 행이 남는다는 전제다. 따라서 재시작 중복의 실제 위험은 주로 **INSERT 중복키/순서 위반(에러로 복제 중단)** 쪽이다. 단 "복제 로그가 항상 절대 이미지인지"는 코드로 한 번 더 못 박을 확인 항목이다.

### Q12. [Act E.2 / F.2] 대기 해제 기준을 "워커 완료"가 아닌 "순서 정리 완료"로 잡으면, 충돌 트랜잭션 하나가 느릴 때 그 뒤 파이프라인이 committed_lsa 전진을 기다리며 멈추는(head-of-line blocking) 것 아닌가 — lag을 줄이려는 목표와 충돌하지 않나? — 🔵
**A.** 맞다. 1차안이 안전을 위해 "순서 정리 완료까지 대기"를 택하면, 느린 트랜잭션 하나가 `committed_lsa` 전진을 막아 그에 의존하는 후속이 멈추는 head-of-line blocking이 생긴다. 다만 **영향 범위는 충돌 체인에 한정**된다 — 독립 트랜잭션은 계속 병렬 적용되고 진도만 뒤에서 따라온다. 그래도 correctness를 위해 성능을 일부 양보한 선택임은 분명하고, 그 영향(특히 hot class·긴 체인에서)은 측정으로 확인해야 한다. trade-off를 인정하고 들어간 부분이다.

## 의사결정·운영 (🟠 IT 5년차, 비DB)

### Q13. [Act D.2 / D.5] hot class에서 사실상 순차로 떨어진다고 본인들이 인정하면서, 왜 처음부터 row/write-set 정밀 병렬로 안 가고 굳이 class 단위를 1차로 결정했나? — 🟠
**A.** 단계적 리스크 관리다. row/write-set 정밀 병렬은 (a) 충돌 키 추적 자료구조·메모리, (b) 정밀도를 높이려면 결국 복제 로그 포맷 확장이 따라오고, (c) correctness 검증이 복잡하다 — 1차에 다 하면 변수가 너무 많다. class 단위는 로그 무변경·correctness 자명(보수적이라 안전)이라 **"코디네이터라는 구조 자체가 올바르게 도는지"를 가장 적은 변수로 먼저 검증**할 수 있다. 비용은 병렬성이 낮다는 것. 즉 "구조 먼저, 정밀도 나중"의 의도적 선택이며, 병렬성이 목표에 못 미치면 Phase 2(정밀화)로 넘어간다.

### Q14. [Act D.3] Phase 2를 "로그 포맷 변경이라 분량·기간 예측이 어렵다"고 미루는데, 예측 불가 작업을 로드맵에서 어떻게 관리하며 Phase 1만으로 운영 요구 성능을 충족하는지는 무엇으로 판단하나? — 🟠
**A.** 두 가지로 관리한다. 첫째, **Phase 1을 독립적으로 완결**시킨다 — 로그 포맷을 안 바꾸므로 그 자체로 운영에 올릴 수 있는 산출물이다. 둘째, Phase 2는 일정에 박는 대신 **"Phase 1 측정 결과 병렬성이 목표 미달일 때" 발동되는 조건부 과제**로 둔다(로그 포맷 변경은 마스터·슬레이브·복구 호환을 모두 건드려 분량 예측이 정말 어렵기 때문). Phase 1 완결 기준은 ① 목표 lag·처리량(운영 SLA) 충족, ② 정확성 시나리오 통과, ③ **재시작 정합(F.2) 해결**이다. 다만 "Phase 1 단독으로 목표 성능을 충족하는가"는 결국 실측에 달려 있다(→ Q15).

### Q15. [Act B.2 / E.2] PoC의 3.4배는 의존성 무시한 단순 분배 결과인데, 충돌·순서를 지키는 정식 코디네이터를 넣은 뒤 실제 병렬 이득이 얼마나 남는지는 어떻게 측정·검증할 계획인가? — 🟠
**A.** 옳은 지적이고, 솔직히 **현재 문서에 측정 계획이 약하다.** PoC 3.4배는 코디네이터 오버헤드(충돌 판단·pending 재평가·순서 정리 대기)가 전혀 없는 상한선이다. 정식 측정은 워크로드 축을 나눠서 해야 한다: ① 독립 트랜잭션 비율, ② 트랜잭션당 class fan-out, ③ hot class 집중도. 측정 지표는 처리량·lag뿐 아니라 **코디네이터 CPU 점유, head-of-line blocking 발생률, pending queue 길이**를 포함해야 ROI를 제대로 본다. 이 측정 설계를 문서에 명시하는 것을 follow-up으로 둔다.(좋은 지적)

### Q16. [Act F] 크래시로 out-of-order durable commit이 남아 재시작 중복이 발생하는 문제를 "정식 구현에서 결정"으로 미뤘는데, 이 정합성 깨짐을 운영 중 어떻게 탐지·복구하며, 미해결 상태로 Phase 1을 운영에 올릴 수 있나? — 🟠
**A.** 미해결 상태로는 **병렬 운영에 올릴 수 없다 — 이건 릴리즈 게이트다.** 탐지는 재적용 중 unique/FK 에러(복제 중단으로 드러남)나 마스터-슬레이브 행 수·체크섬 비교(checksumdb 류)로 가능하고, 복구는 현재로선 `fail_counter` + 수동 개입 수준이다. 그래서 F.2의 세 옵션 중 하나를 **Phase 1의 운영 투입 전 필수 조건으로** 닫아야 한다(특히 Q22의 "retire가 commit을 순서대로 수행" 방식이면 out-of-order durable commit 자체가 안 생긴다). 정직하게, 지금은 미해결이고 병렬 운영의 전제 조건이다.

### Q17. [한눈 요약 / Act A.3] 병렬화의 복잡도·재시작 리스크를 떠안기 전에, 단일 스레드 applier 자체를 더 빠르게(on-CPU 병목인 prior_lsa·lock·page 할당 최적화) 만드는 대안은 검토했나, 그리고 도입 후 복제가 깨지면 단일 스레드로 되돌리는 롤백 경로는 있나? — 🟠
**A.** 좋은 두 질문이다. (1) **단일 스레드 최적화는 유효한 보완책**이다 — PoC가 병목으로 지목한 on-CPU 경로(로그 생성 prior_lsa, lock, page/space 할당)를 튜닝하면 병렬화와 무관하게 효과가 있다. 다만 단일 스레드는 코어 하나의 천장에 막히므로, 멀티코어를 쓰는 병렬화가 더 높은 상한을 준다 — 둘은 배타적이 아니라 병행 가능하다. (2) **롤백 경로는 단순하다**: 병렬은 worker 수가 설정값이고, 이를 1로 두면 사실상 현재 develop의 단일 직렬 동작과 같아진다. 즉 문제가 생기면 worker=1로 폴백할 수 있다(단 Q16의 재시작 정합이 닫혀 있어야 폴백도 깔끔하다).

## 심층 (🔴 시니어 10년차, DB)

### Q18. [Act F] 재시작 해결 세 방안(applied set / 윈도우 bound / commit 순서 강제)을 정량 비교 없이 "정식 구현에서 결정"으로 미룬 건 핵심 미결 아닌가 — 특히 applied set은 set 영속과 워커 commit이 별 트랜잭션이라 원자성 갭이 있다. — 🔴
**A.** 맞다, F.2가 나열만 하고 비교를 회피했다. 정직하게 비교하면:
- **applied set 영속**: 지적대로 set 갱신과 워커 commit이 별개면 "commit 후 set 영속 전 크래시"에서 set에 없는 durable commit이 남아 **원자성 갭**이 생긴다. 닫으려면 set 갱신을 워커 commit과 같은 트랜잭션으로 묶거나, 재시작 시 슬레이브에 이미 적용된 PK로 set을 재구성해야 한다(추가 I/O·복잡도).
- **윈도우 bound**: 단순하지만 bound 크기만큼 잔여 중복 가능성이 남고(완전 해결 아님) bound가 병렬 폭을 제한한다.
- **commit 순서 강제**: out-of-order durable commit을 원천 차단해 완전하지만 병렬 commit 이득을 깎는다.

→ 트레이드오프는 *정합 완전성*(commit 순서 강제 > applied set > 윈도우 bound)과 *병렬 이득*(반대)이 상충한다. 현실적 1순위는 **"워커가 독립 commit하지 않고, 순서 정리(retire) 단계가 commit을 순서대로 수행(MySQL SPCO의 group flush 방식)"** 으로 보는데, 이러면 out-of-order durable commit 자체가 없어 문제가 사라진다. 이 비교를 문서에 정식으로 넣는 것이 옳다.(핵심 지적 수용)

### Q19. [Act E/D] cross-class 위험을 FK·상속 둘로 한정했는데, 글로벌 인덱스·CHECK 간접 의존·트리거가 만든 2차 변경의 순서 의존 등 "applier가 못 보는" 경로를 모두 열거했다고 증명할 수 있나? — 🔴
**A.** 증명할 수 없고, 그 열거는 *조사된 범위*의 결론이지 완전성 증명이 아니다 — 인정한다. 다만 **correctness는 열거의 완전성에 의존하지 않는다.** 1차안의 안전 논리는 "applier가 못 가리는 cross-class 의존은 **commit 순서 보존이라는 보수적 기본값이 덮는다**"는 것이다 — 순서만 마스터대로 지키면 의존의 *종류*(FK든, 글로벌 인덱스든, 미지의 인과든)와 무관하게 안전하다. 즉 **열거는 correctness가 아니라 "어디까지 안전하게 병렬화할 수 있나(최적화)"를 위한 것**이다. 열거에 실패하면 그 부분은 병렬을 못 할 뿐 틀리지는 않는다. 따라서 문서의 프레이밍을 "FK·상속만 위험"이 아니라 **"보수적 순서 보존이 미지의 cross-class도 backstop하고, FK·상속은 그중 *완화 대상으로 식별된* 것"** 으로 바꾸는 게 정확하다.(수용)

### Q20. [Act D/E] "자식 적용 시점에 부모가 이미 commit되어 보여야 한다"는 제약은 SPCO(최종 commit 순서만 보존)보다 강한데, 부모/자식을 구분 못 하는 1차안은 모든 cross-class 쌍에 이 강한 제약을 걸어 commit-order serialization을 넘어 apply-before-commit serialization으로 병렬도가 추가 붕괴하는 것 아닌가? — 🔴
**A.** 정확하다. FK 검사가 자식 INSERT 시점에 일어나므로, 부모가 그 시점에 *commit되어 보여야* 한다 — 이는 "최종 commit만 순서대로(SPCO)"보다 강하다. 그리고 1차안이 cross-class를 보수적으로 직렬화하면(부모/자식을 구분 못 하므로), 이 강한 제약이 cross-class 쌍 전반에 적용되어 병렬도가 추가로 떨어진다. D.4가 강한 제약을 말하면서 그 비용을 정량화하지 않은 건 맞다. 완화책은 Q8의 **FK 그래프 로드로 "진짜 FK 쌍"만 이 강한 직렬화를 걸고** 나머지는 풀어 주는 것이다. 그 비용·효과는 측정 대상이며, 문서에 "이 제약의 병렬도 영향"을 명시할 가치가 있다.(수용)

### Q21. [Act D.5] conflict key를 apply 측에서 계산하는 방향이 "자연스럽다"고 했지만, 마스터/슬레이브의 인덱스·collation·스키마 버전이 어긋나면 같은 PK라도 충돌 키가 달라져 apply 측 계산이 마스터의 실제 충돌과 불일치할 수 있다 — MySQL이 굳이 source에서 선계산하는 이유(권위 있는 단일 출처)를 뒤집는 위험을 어떻게 막나? — 🔴
**A.** 날카로운 지적이다. MySQL이 source에서 write set을 선계산해 결과만 내려보내는 것은 "충돌 판단의 권위 있는 단일 출처"를 두기 위함인데, apply 측 계산은 그 권위를 잃는다. CUBRID HA는 보통 슬레이브가 마스터의 복제본이라 **스키마가 동일하다는 전제**에서 위험이 작지만, **롤링 스키마 변경 중**(마스터/슬레이브 스키마가 잠시 다른 구간)에는 불일치 위험이 실재한다. 따라서 D.5의 "conflict key가 자연스럽다"는 단순화였고, 권위 문제를 고려하면 **watermark(source 선계산) 방향도 재고 가치가 있다.** 최소한 D.5에 "apply 측 계산은 스키마 동일 전제, 롤링 변경 시 정합 위험"을 명시해야 한다.(수용, D.5 보강)

### Q22. [Act D.1/D.2] barrier를 "스키마 변경·sysop·변경 class를 알 수 없는 작업"으로 정의했는데 "변경 class를 알 수 없는 경우"가 구체적으로 뭔지, "앞뒤를 끊는다"의 정확한 의미가 모호하다 — barrier 범위가 넓어지면 hot barrier가 hot class보다 더 심하게 전체를 직렬화하지 않나? — 🔴
**A.** 인정한다 — barrier 범위는 남은 쟁점에 "어디까지 잡을지 미정"이라 적어 둔 부분이다. "변경 class를 알 수 없는 경우"는 구체적으로 ① 부분 디코딩 실패, ② 미지원 연산, ③ statement-based 항목(→ Q23), ④ sysop 등이고, "앞뒤를 끊는다"는 **앞의 모든 pending 완료 대기 → barrier 단독 실행 → 그 뒤부터 재개**를 뜻하므로 그 구간은 전면 직렬화된다. 따라서 barrier 트리거가 잦으면(잦은 DDL, 많은 statement) hot class보다 더 심한 직렬화를 유발할 수 있다. → barrier 트리거를 최대한 좁게 정의하고(특히 statement 처리 방식, Q23) 그 빈도를 측정해야 한다.(수용)

### Q23. [Act A.2/E] statement-based 적용 경로(`la_apply_statement_log`)가 있는데, 문장 기반 항목은 어떤 행/class를 건드릴지 apply 전에 알 수 없어(비결정 함수·다중 class) changed class 집합 산출 전제가 깨진다 — 모든 statement를 barrier로 처리해야 하는 것 아닌가, 그 빈도는 가정에 반영됐나? — 🔴
**A.** 정확히 문서의 공백을 짚었다. class 단위 충돌 판단의 전제는 "리더가 commit 전에 changed class를 다 수집한다"인데, statement-based 항목은 문장이 어떤 행/class를 바꿀지 실행 전엔 불확정(비결정 함수, 한 문장이 다중 class)이라 그 전제가 성립하지 않는다. **따라서 안전 기본값은 statement 항목을 barrier로 처리하는 것**이다(Q22의 barrier 트리거에 포함). 빈도는 워크로드에 달렸는데, CUBRID 복제는 대부분 row-based이고 statement-based(SBR)는 일부 대량·특정 연산에서 쓰이므로, **SBR 비율이 높은 워크로드에서는 barrier가 늘어 병렬이 붕괴**할 수 있다. 이 점이 설계 가정에 명시돼 있지 않았던 건 맞고, 보강이 필요하다.(수용)

## 리뷰 종합 — 문서에 반영할 follow-up

리뷰에서 나온, 문서에 보강하면 좋을 항목(우선순위):

1. **재시작 정합(F.2) 비교 + 권장안 명시** — 세 옵션 트레이드오프 비교, "retire 단계가 commit을 순서대로 수행"이면 문제 소멸(Q18). 운영 투입 전 필수 게이트(Q16).
2. **cross-class 안전 논리 재프레이밍** — "FK·상속만 위험"이 아니라 "보수적 commit 순서 보존이 미지의 cross-class도 backstop, FK·상속은 완화 대상"(Q19).
3. **FK 그래프 로드 옵션 격상** — Phase 1의 정식 개선안으로(보수적 전체 직렬 → FK 쌍만)(Q8, Q20).
4. **측정 계획 명시** — 코디네이터 오버헤드 반영 ROI, 워크로드 축(독립 비율·class fan-out·hot class), head-of-line·코디네이터 CPU 지표(Q9, Q15).
5. **statement-based = barrier 처리 + 빈도 가정 명시**(Q23), **barrier 범위 정의**(Q22).
6. **apply 측 conflict key 계산의 스키마 동일 전제·롤링 변경 위험 명시**(Q21).
7. **재적용이 행 이미지(절대값) 기반이라 값 멱등임을 코드로 확인·명시**(Q11).
8. **Phase 1.5(PK 기반 same-class 정밀화, 로그 무변경) 단계 추가 검토**(Q7).

> 리뷰 방식: 4개 페르소나 에이전트가 독립적으로 문서를 정독하고 질문 생성 → 작성자가 응답 → 본 문서로 종합. 총 23라운드.
