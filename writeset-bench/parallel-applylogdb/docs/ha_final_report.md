## 0. 한 장 요약

이 브랜치는 슬레이브의 `applylogdb` 를 writeset 기반으로 **병렬화**한다.
`ha_apply_worker_count` 개의 워커가 서로 충돌하지 않는 트랜잭션을 동시에 적용한다.
이번 측정의 목적은 세 가지였다 — **(1) 병렬화가 실제로 효과를 내는가,
(2) 상한은 어디인가, (3) 새로 들어온 코드에 결함이 있는가.**

결론은 다음과 같다.

**① 병렬화는 동작한다.** 워커 1개 대비 4개에서 3.74배, 10개에서 5.60배 빨라진다.

**② 그러나 실용 상한은 워커 4~10 이다.** 10개에서 20개로 두 배를 넣어도 처리량은
10% 밖에 늘지 않는다. 워커 하나를 더 넣어 얻는 이득이 구간별로 16배 차이 난다
(1→4 구간 워커당 +125.6 tx/s, 10→20 구간 워커당 +7.9 tx/s).

**③ 주 병목은 applylogdb 가 아니라 슬레이브 cub_server 다.** 워커 스레드는
자기 코드를 도는 시간이 거의 없고, 작업 시간의 73~96% 를 **서버 응답 대기**
(`css_readn`) 로 보낸다. 워커를 늘려도 효율이 떨어지는 주된 이유는 applier 코드가
느려서가 아니라 서버 앞에 줄이 길어지기 때문이다.

**④ 고칠 가치가 있는 코드 결함 1건을 발견했다.**
`la_insert_applied_tx_marker()` 가 **파일 전역 뮤텍스를 쥔 채 서버 왕복을 수행**한다
(`src/transaction/log_applier.c:3807`). 모든 워커의 모든 커밋이 이 지점에서 직렬화된다.
워커 수에 대해 가장 빠르게 악화되는 비용이며 (0% → 1.9% → 3.6% → **12.4%**),
구조적으로는 워커 수와 무관한 처리량 천장이기도 하다.
이 병목은 [PR #8052의 hornetmj 리뷰](https://github.com/CUBRID/cubrid/pull/8052#pullrequestreview-5797924349)에서도 지적됐다.

**⑤ 메모리 누수 징후는 없다.** RSS 23~61 MB 로 안정적이다. 다만 VSZ 는 워커당
약 76 MB 씩 선형으로 늘어난다 (최대 32워커 환산 약 2.6 GB).

**⑥ 같은 샘플을 스레드별로 다시 나눠 보니 문제 5건이 더 나왔다 (8절, 2026-11-07).**

| 항목 | 스레드별 재분석에서 확인한 내용 | 이후 확인 |
|---|---|---|
| 문제 5 (8.3절) | 코디네이터가 pending 큐를 처음부터 반복 탐색. 워커 10개부터 유휴 샘플 0% | 고충돌 부하 B에서 워커를 늘리면 처리량 감소 (10절) |
| 문제 6 (8.4절) | 페이지 버퍼 캐시의 공용 뮤텍스 대기. 초기 20워커 샘플 4.5% | 재측정에서는 0.6% (9.6절) |
| 문제 7 (8.5절) | pending 태스크를 파킹할 때마다 malloc/free | 비용 비중 미산출 |
| 문제 8 (8.6절) | FK 부모·자식 적용 순서의 전용 검증이 TODO로 남음 | 성능 측정으로 정합성 결함을 확인한 것은 아님 |
| 문제 9 (8.7절) | trace 로그 뮤텍스가 워커·코디네이터 대기를 늘림 | trace를 끈 운영 기본 설정에서는 해당 대기 없음 |

초기 샘플에서 워커의 전체 락 대기는 marker 뮤텍스만 센 12.4% 가 아니라 **18.9%** 였다.

> **주의 (2026-11-07 저녁 추가):** 4·8절 측정은 pstack 이 applylogdb 를 매 샘플 1~2초씩 멈추고 trace 가 켜진 조건이라
> **처리량이 실제의 약 절반으로 나왔다.** 재측정(9절)에서 워커 4 = 1,010, 워커 10 = 1,630 tx/s.
> 원인은 pstack 이 매 샘플 applylogdb 를 1~2초 멈춘 것이다 (9.7). 깨끗한 측정의 배속은 **워커 4 = 2.78배, 10 = 4.69배,
> 20 = 4.98배** (9.8) — 아래 ①②의 3.74 / 5.60 배는 과대다. 실용 상한 워커 10 이라는 결론은 유지된다.
> marker 전역 락은 워커 10 기준 워커 시간의 **약 31%** 로 4절보다 훨씬 크고, 코디네이터의 주기적 진행정보 저장(문제 10)이
> 같은 락을 쥐어 워커 20 에서 굶음 20.8% 를 만든다. **9.6절의 바뀐 결론을 먼저 볼 것.**
> **고충돌 부하(시나리오 B, 10절)에서는 워커 4 에서 2배로 멈추고 워커를 더 늘리면 오히려 느려진다** (4: 449, 10: 413, 20: 340 tx/s).
> 실제 병렬도가 의존성 때문에 약 2.5 로 고정되는데, pending 선형 스캔(문제 5) 비용은 워커 수에 비례해 커지기 때문이다.
> **평상시 부하(11.1)에서는 워커 4 이상이면 A·B 모두 지연 1초 안팎으로 따라간다** (워커 1 은 2분에 34초 밀림).
> **재기동 정합성(11.2): 따라잡기 중 kill -9 13회 후에도 마스터·슬레이브 데이터 일치.**

## 1. 배경

### 1.1 무엇을 바꾼 브랜치인가

CUBRID HA 는 **논리 복제**다. 마스터의 트랜잭션 로그를 슬레이브가 받아서
**다시 실행**하는 방식이다. 기존 `applylogdb` 는 이 재실행을 **단일 스레드로 직렬
수행**했다 (`HB_DEFAULT_APPLY_WORKER_COUNT = 1`, `heartbeat.h:34`).
마스터가 아무리 병렬로 처리해도 슬레이브는 한 줄로 따라가므로, 쓰기 부하가
높으면 복제 지연이 쌓인다.

이 브랜치는 **writeset(트랜잭션이 건드린 키 집합)** 을 보고 서로 충돌하지 않는
트랜잭션을 식별해, 최대 32개 워커가 **동시에** 적용하도록 바꾼다.

관련 커밋:

```
bf560620e  slave: release every page fix a record takes, however long
fe230a932  slave: remove the re-apply safeguards the applied-tx marker replaced
72650ce0d  slave: skip the transactions a restart finds already applied
19e83a5d9  master: choose the slot a key waits for inside the history map
```

### 1.2 확인해야 할 것

1. **병렬화가 실제로 효과를 내는가.** 코드가 병렬로 돈다고 처리량이 느는 건 아니다.
   공유 자원에서 직렬화되면 워커만 늘고 속도는 그대로다.
2. **상한은 어디인가.** 운영에서 `ha_apply_worker_count` 를 몇으로 둘지 정해야 한다.
3. **새 코드에 결함이 있는가.** 특히 커밋 `72650ce0d` 가 도입한
   applied-tx marker 경로는 커밋마다 실행되는 신규 경로다.

## 2. 측정 방법

### 2.1 CUBRID HA 복제 경로 (용어 정리)

```
  [마스터 youngjun1]                      [슬레이브 youngjun2]

   cub_server                              copylogdb
   (트랜잭션 처리)  ──로그 전송──▶          (로그 파일을 디스크에 복사)
        │                                       │
        ▼                                       ▼
   트랜잭션 로그                          슬레이브 디스크의 복사본
                                                │
                                                ▼
                                          applylogdb   ← 측정 대상
                                          (로그를 읽어 SQL 로 재실행)
                                                │
                                                ▼
                                          cub_server (standby)
```

핵심은 **`copylogdb` 와 `applylogdb` 가 독립된 별개 프로세스**라는 점이다.
`copylogdb` 는 로그를 받아 디스크에 쓰기만 하고, `applylogdb` 는 그 디스크의
로그를 읽어 슬레이브 서버에 SQL 로 재실행한다. 이 분리가 2.4 의 측정 설계를 가능하게 한다.

> **참고:** `applylogdb` 는 독립 바이너리가 아니라 `cub_admin` 의 서브커맨드다
> (`util_cs.c:3379`). `ps` 에 `cub_admin applylogdb ...` 로 뜨므로 `pgrep` 이 아니라
> **`pgrep -f`** 가 필요하다.

### 2.2 pstack 샘플링 프로파일링

**원리.** 실행 중인 프로세스의 스택을 일정 간격으로 수십~수백 회 떠서,
각 함수가 나타나는 **빈도 분포**를 본다. 한 번 뜬 스택은 일화에 불과하지만,
충분히 반복하면 그 분포가 "시간을 어디에 쓰는가" 에 근사한다. 사실상 수동
샘플링 프로파일러다.

**검출할 수 있는 것** — 어디서 **막혀 있는가** (blocking point).
락 대기, I/O 대기, 네트워크 대기.

**검출할 수 없는 것** — 메모리 누수, FD 누수, 정확성 버그,
CPU 핫스팟(이건 `perf` 가 필요하다).

이번 측정은 3단계로 집계한다.

| 집계 | 의미 |
|---|---|
| [1] 최상위 프레임 | 스레드가 **무엇에** 막혀 있나 (`cond_wait` / `futex` / `poll` …) |
| [2] 최초 작업 프레임 | 대기 primitive 를 걷어낸 뒤 **무슨 일로** 막혀 있나 ← **해석에 쓰는 것** |
| [3] 스택 시그니처 | 상위 3 프레임 조합별 빈도 |

본 보고서의 분석은 전부 **[2]** 기준이다. `pthread_cond_wait` 같은 대기 원시함수는
"막혀 있다"는 사실만 알려줄 뿐 "무슨 일로" 는 알려주지 않기 때문이다.

### 2.3 처리량 지표

슬레이브의 `db_ha_apply_info` 뷰가 노출하는 **`commit_counter`** 를 쓴다.
applylogdb 가 실제로 적용 완료한 트랜잭션 누적 수다.

```sql
SELECT commit_counter FROM db_ha_apply_info;
```

측정 구간의 시작·끝에서 읽어 증분을 구간 길이로 나누면 **tx/s** 가 나온다.
"마스터가 몇 건 보냈나" 가 아니라 "슬레이브가 몇 건 소화했나" 를 재는 것이 중요하다.

### 2.4 왜 "백로그 따라잡기" 방식인가 ← **핵심 방법론**

#### 첫 시도와 그 실패

처음에는 자연스러운 방법을 썼다. **마스터에 부하를 걸고, 그 동안 슬레이브가
실시간으로 복제하는 속도를 재는 것**이다 (`ha_scale.sh`). 결과는 이랬다.

| 워커 | 처리량 | 워커 유휴율 |
|---|---|---|
| 1 | 214.4 tx/s | 0.0% |
| 4 | 281.1 tx/s | 28.6% |
| 10 | 134.6 tx/s | 63.9% |
| 20 | 193.2 tx/s | 65.0% |

확장성이 전혀 보이지 않았고, 심지어 **10워커가 1워커보다 느렸다.**
처음에는 "병렬화에 상한이 있다"고 해석했지만, **그 해석은 틀렸다.**

문제는 **워커 유휴율 63~65%** 다. 워커들이 놀고 있었다는 뜻이고,
놀았다는 건 **줄 일이 없었다**는 뜻이다. 즉 이 측정이 잰 것은
`applylogdb` 의 처리 능력이 아니라 **마스터의 로그 생산 속도**였다.
슬레이브는 한 번도 포화되지 않았으므로, 워커를 늘려도 처리량이 늘 수 없다.

**이것이 성능 측정의 전형적인 함정이다 — 측정 대상이 아니라 부하 공급원이
한계였던 것이다.**

#### 백로그 따라잡기 설계

로그 도착 속도를 변수에서 **제거**해야 했다. 2.1 에서 본 `copylogdb` /
`applylogdb` 분리를 이용한다.

```
1단계  슬레이브의 applylogdb 만 정지한다.
       copylogdb 는 계속 돌므로 마스터 로그는 슬레이브 디스크에 계속 쌓인다.

2단계  마스터에 부하를 건다 (60~180초). 슬레이브에는 백로그만 쌓인다.

3단계  부하를 끝내고 copylogdb 가 남은 로그를 다 받을 때까지 기다린다 (25초).

4단계  applylogdb 를 기동한다. commit_counter 가 바닥날 때까지의
       시간과 증분을 잰다.
```

4단계에서 **로그는 이미 슬레이브 로컬 디스크에 전부 있다.** 네트워크도,
마스터도 변수가 아니다. 여기서 측정되는 것은 **순수한 적용 속도**뿐이다.

applylogdb 만 따로 세우는 방법:

```bash
# 슬레이브에서. copylogdb 는 그대로 둔다.
cubrid heartbeat applylogdb stop  testdb youngjun1
cubrid heartbeat applylogdb start testdb youngjun1
```

heartbeat 는 **명시적으로 멈춘 applylogdb 를 자동 재기동하지 않는다** (확인함).
워커 수는 applylogdb 가 기동할 때 직접 읽으므로 (`log_applier.c:8967`),
`cubrid_ha.conf` 만 고치고 applylogdb 만 재기동하면 된다 — heartbeat 전체를
내렸다 올릴 필요가 없다. 측정 간 교란이 그만큼 줄어든다.

#### 측정 구간 보정

따라잡기 측정에는 양 끝에 **측정 대상이 아닌 구간**이 섞인다.

- **앞쪽** — applylogdb 가 기동해서 서버에 붙고 실제 적용을 시작하기까지의 지연
- **뒤쪽** — 이미 다 따라잡고 노는 구간 (완료 판정에 쓴 창)

자르지 않으면 **빠른 구성일수록 심하게 왜곡된다.** 실제로 1차 시도에서
워커 20이 4,059 tx/s 로 나왔는데, 따라잡기 전체가 보정 지연보다 짧아서 생긴
허수였다. 그래서 측정 구간을 **백로그의 2% 지점부터 98% 지점까지**로 한정했다.
따라잡기가 끝난 뒤의 pstack 샘플도 유휴만 담아 분포를 왜곡하므로
`find -newermt` 로 잘라냈다.

또 하나 — **부하가 없어도 슬레이브에 초당 1건 남짓 배경 트랜잭션이 들어온다.**
따라서 "따라잡기 완료" 를 `commit_counter` 증가 **정지**로 판정하면 영원히
끝나지 않는다. "최근 8폴 증가량 < 15건" 이라는 **증가율 바닥** 기준으로 판정했다.

| 부하 테이블 | `ha_t1` (10만 행), `ha_t2` |
| `ha_apply_max_mem_size` | 4096 (MB, **VSZ 기준**) |
| `ha_writeset_trace_level` | 1 (3은 처리량이 절반이 된다) |
| `force_remove_log_archives` | no |

**왜 optdebug 인가.** debug(`-O0`) 는 너무 느려서 타이밍에 민감한 동시성 문제를
재현하지 못한다. release 는 assert 커버리지가 없다. optdebug 는 release 수준
속도에 assert 가 켜져 있고 심볼이 들어 있어 pstack 분석이 가능하다.

**부하 시나리오 A (무충돌).** 세션 8개가 각자 겹치지 않는 키 범위를 담당한다.
워커 간 writeset 충돌이 없으므로 **병렬화가 가장 잘 드러나는 조건**이다.
본 보고서의 모든 수치는 시나리오 A 기준이다.

마스터의 부하 생성 능력은 약 **700 tx/s** 였다 (20초에 13,900 트랜잭션).

### 4.2 병목의 위치 — 프레임 분포

워커 스레드만 분리해 집계했다. applylogdb 의 스레드 구성은
**워커 N개 + main + heartbeat + sigusr1 = N+3 개**이므로,
워커-샘플 = 전체 스레드-샘플 ÷ (N+3) × N 이다.

| 워커 | 워커-샘플 | `css_readn` | `la_insert_applied_tx_marker` |
|---|---|---|---|
| 1 | 66 | ~100% | 0% |
| 4 | 160 | 95.6% | 1.9% |
| 10 | 390 | 89.5% | 3.6% |
| 20 | 660 | 72.9% | **12.4%** |

**`css_readn` 은 슬레이브 cub_server 의 응답을 기다리는 중이다.**
워커가 자기 코드를 도는 시간은 거의 없다 — 거의 전부가 서버 왕복 대기다.

워커의 동작은 사실상 이렇다:

```
  [SQL 전송] → [서버 응답 대기] → [SQL 전송] → [서버 응답 대기] → ...
                  ↑
            여기가 73~96%
```

따라서 전체 처리량은 대략 **(워커 수) × (1 ÷ 서버 왕복 시간)** 이고,
서버가 포화되면 왕복 시간이 길어져 워커를 늘려도 총량이 늘지 않는다.
4.1 의 포화 곡선은 이것으로 설명된다.

전체 집계 원본 (워커 20):

```

10.80%   82  la_insert_applied_tx_marker     ← 전역 뮤텍스 대기
 5.67%   43  la_task_queue_pop               ← 워커 유휴
 4.35%   33  css_platform_independent_poll   ← heartbeat 스레드
 4.35%   33  sigusr1_monitor_thread          ← 모니터 스레드
 2.37%   18  la_release_page_buffer
```

> `(전체 샘플 − 유휴 샘플)` 을 분모로 써서 heartbeat·sigusr1·main 스레드까지
> 포함한다. **해석에는 위 표(워커 전용)를 쓸 것.**

## 6. 코드 결함 상세 — 전역 뮤텍스를 쥔 채 서버 왕복

같은 문제는 [PR #8052의 hornetmj 리뷰](https://github.com/CUBRID/cubrid/pull/8052#pullrequestreview-5797924349)에도 기록됐다. 아래 수치는 그 지적과 별도로 수행한 pstack 측정 결과다.

### 6.1 문제 코드

`src/transaction/log_applier.c:3807`, `la_insert_applied_tx_marker()` —
**커밋마다** 실행되는 마커 INSERT 다.

```c
/* the execution compiles the statement again when the server asks for it, for example after the table size
 * changed a lot, so it runs under the compile mutex too */
pthread_mutex_lock (&la_sql_compile_mutex);
res = db_push_values (context->marker_session, 3, in_value);
if (res == NO_ERROR)
  {
    res = db_execute_and_keep_statement (context->marker_session, context->marker_stmt_id, &result);
    if (res >= 0 && result != NULL)
      {
        (void) db_query_end (result);
      }
  }
pthread_mutex_unlock (&la_sql_compile_mutex);
```

### 6.2 왜 문제인가

1. **`la_sql_compile_mutex` 는 파일 전역이다** (`log_applier.c:470`).
   워커별이 아니라 프로세스 전체에서 하나다.
   사용처: 3644, 3787, **3808**, 3844, 7037, 7083.
2. **그 안의 `db_execute_and_keep_statement` 는 서버 왕복을 한다.**
   슬레이브 `cub_server` 에 SQL 을 보내고 응답을 기다린다.
3. 따라서 **모든 워커의 모든 커밋이 "전역 락을 쥔 채 네트워크 왕복" 을
   직렬로 수행한다.** 워커가 몇 개든 이 구간은 한 번에 하나씩만 통과한다.

### 6.3 측정에서의 확인

| 워커 | 워커 작업시간 대비 뮤텍스 대기 |
|---|---|
| 1 | 0% (경합 상대가 없음) |
| 4 | 1.9% |
| 10 | 3.6% |
| 20 | **12.4%** |

10→20 에서 **3.5배**로 뛴다. **워커 수에 대해 가장 빠르게 악화되는 비용**이다.

서버가 부하를 받을수록 각 워커가 뮤텍스를 쥐고 있는 시간이 길어지므로,
경합은 워커 수에 대해 선형이 아니라 **초선형**으로 자란다.

### 6.4 구조적 상한

이 구간이 완전히 직렬이라는 것은, 마커 INSERT 왕복 시간을 **T** 라 할 때
**전체 커밋 처리량이 1/T 를 넘을 수 없다**는 뜻이다. 워커를 아무리 늘려도 그렇다.

측정된 850 tx/s 는 T ≈ 1.2 ms 에 해당한다. **아직 천장에 닿지는 않았지만,**
서버가 더 느려지거나 워커가 더 늘면 바로 닿는다.

### 6.5 개선 방향

주석이 밝히듯 이 뮤텍스의 목적은 **클라이언트측 파서 보호**다 —
"실행 중에도 서버가 요구하면 재컴파일이 일어날 수 있으므로 실행도 뮤텍스
안에서 돈다". 즉 **재컴파일이라는 드문 경우를 위해, 재컴파일이 일어나지 않는
일반적인 경우까지 전역 직렬화 비용을 물고 있다.**

→ **재컴파일이 실제로 발생할 때만 락을 잡도록** 바꿀 수 있다면 이 비용은 사라진다.

**단, 이 수정의 효과는 아직 측정으로 확인되지 않았다.** 7.2 참조.

> 참고: `la_insert_applied_tx_marker` 는 커밋 `72650ce0d`
> ("재시작 시 이미 적용된 트랜잭션 스킵") 에서 도입된 경로다.

## 7. 한계와 다음 단계

### 7.1 "슬레이브 서버가 병목" 은 추론이지 측정이 아니다

워커가 `css_readn` 에서 **서버 응답을 기다린다**는 것까지는 확실하다.
그러나 그 서버가

- **CPU 로 포화된 것인지**, 아니면
- **서버 내부의 락에 걸린 것인지**

는 구분하지 못했다. **둘은 처방이 완전히 다르다** — 전자는 튜닝 문제,
후자는 또 다른 코드 결함이다.

→ **다음 측정:** 따라잡기 중에 슬레이브 `cub_server` 도 같이 pstack 샘플링한다.
   소요 3~4분.

### 7.2 marker 뮤텍스 수정의 실제 효과는 미확인

12.4% 가 실제 처리량으로 돌아올지는 수정 후 재측정해야 안다.
실행 경로에서 락을 제거한 뒤 동일 조건으로 `ha_backlog.sh` 를 다시 돌리면 된다.

### 7.3 시나리오 A 만 측정했다

본 보고서의 모든 수치는 **무충돌 워크로드** 기준이다.
고충돌(B), 혼합(C), 대형 트랜잭션(D) 은 백로그 방식으로 재측정하지 않았다.
실제 운영 워크로드는 충돌이 섞이므로, 4.1 의 배속은 **상한에 가까운 값**으로
봐야 한다.

### 7.4 각 구성 1회 측정이다

4.1 의 곡선은 매끄럽고 단조롭지만 반복 측정은 하지 않았다.
공식 수치로 쓰려면 구성당 3회 반복이 필요하다.

### 7.5 메모리 누수 판정의 범위

110~201초 구간에서 RSS 가 안정적이었다는 것뿐이다. 장시간 누수는 이 방법으로
판정할 수 없다.

- `cubrid memmon <db>` 는 **`cub_server` 만 대상**이라 applylogdb 에는 못 쓴다.
- applylogdb 는 `/proc/<pid>/status` 의 VmRSS/VmSize 로 본다
  (`ha_pstack.sh` 가 자동 수집).
- 본격적인 누수 추적은 **ASan 별도 빌드**가 필요하다.

### 7.6 pending 큐의 길이와 파킹 사유 — 9.4절에서 확인됨

처음엔 측정 구간 trace 로그가 지워졌다고 판단했으나 **틀렸다** (대화 기록이 UTC 라 측정 시각을 잘못 읽었다).
측정 구간(슬레이브 시각 11/7 00:44~01:05)의 로그가 남아 있었고, 9.4절에서 pending 리스트를 재현해 측정했다.
남은 것은 헛스캔 비용의 직접 측정(`perf`)이다.

### 7.7 시나리오 A 에서는 게이트 경로가 거의 안 탄다

문제 5·8 은 충돌이 있어야 드러난다. 시나리오 B(고충돌)를 백로그 방식으로 워커 1/4/10/20 측정해야
writeset 게이트의 실제 비용이 보인다.

### 8.3 [문제 5] 코디네이터의 pending 큐 재스캔

applylogdb 는 워커 N개 + **코디네이터 1개**(로그를 읽고 워커에 분배)로 돈다.
코디네이터는 1개뿐이라 늘릴 수 없다.

**[측정]** 코디네이터 스레드가 하는 일:

| 워커 | **유휴** | pending/gate 스캔 | 로그 레코드 파싱 | 로그 페이지 읽기 | trace | 기타 |
|---|---|---|---|---|---|---|
| 1 | **95.5%** | 0% | 0% | 0% | 0% | 4.5% |
| 4 | **65.0%** | 22.5% | 10.0% (읽기 포함) | (파싱에 포함) | — | 2.5% |
| 10 | **0%** | 64.1% | 15.4% | 0% | 5.1% | 15.4% |
| 20 | **0%** | 42.4% | 21.2% | 6.1% | 15.2% | 15.1% |

- 기타 = 분류 안 된 프레임 + 코디네이터 자신의 서버 왕복 (워커 10: 5.1%, 워커 20: 3.0%) + 락 대기.
- 유휴 = `pthread_cond_timedwait` (줄 일이 없어 쉬는 상태). **워커 10개부터 한 장도 안 잡힌다** — 코디네이터가 여유 없이 돌고 있다.
- 로그를 순서대로 읽는 시간(페이지 읽기)은 6.1% 뿐이다. **순차 읽기 제약이 병목은 아니다.**
- 대부분은 pending/gate 스캔이다. 스택: `la_coordinator_drain_ready → la_pending_pop_ready (log_applier_pending.cpp:107) → la_gate_is_satisfied (log_applier_gate.cpp:328)`

**[코드]** `la_pending_pop_ready()` 는 하나 꺼낼 때마다 리스트를 **처음부터 다시** 훑는다:

```c
/* log_applier_pending.cpp:101 */
for (cur = la_Pending_head; cur != NULL; prev = cur, cur = cur->next)
  {
    if (la_gate_is_satisfied (&cur->task.dependency_seq) == false)
      {
        continue;
      }
    ...                 /* 하나 떼어내고 즉시 return true */
  }
```

```c
/* log_applier.c:737 — la_coordinator_drain_ready() */
while (!la_task_queue_is_full () && la_pending_pop_ready (&task))
```

pending 에 P개가 있고 K개를 꺼내면 O(K·P). drain 은 프론티어가 움직일 때마다,
그리고 새 커밋을 보내기 전마다 (`log_applier.c:7793`) 호출된다.

**[코드]** pending 에 들어가는 조건은 둘이다 (`log_applier.c:7799`):

```c
if (la_gate_is_satisfied (&task->dependency_seq) && !la_task_queue_is_full ())
  return la_coordinator_enqueue_task (task, LA_SCHED_DISPATCHED);
error = la_pending_push (task);      /* 의존성 미충족 또는 워커 큐 full */
```

- **워커 큐가 가득 차서** 들어간 것은 게이트가 이미 열려 있어 맨 앞에서 바로 꺼내진다 → O(1), 문제 없음.
- **의존성 때문에** 들어간 것이 앞쪽에 쌓이면 매번 그 앞부분을 다시 훑는다 → O(P), 문제.

**[추론 — 미확인]** 스캔 안에서 코디네이터가 자주 잡혔으니 리스트 앞쪽에 막힌 태스크가 쌓여
있었을 것으로 보이지만, **pending 큐의 길이와 파킹 사유는 직접 측정하지 못했다** (7.6절).

#### 실제 손실 — 워커가 일감을 못 받은 비율

**[측정]** 워커가 `la_task_queue_pop` 에서 대기(큐가 비어 받을 태스크가 없음)한 비율:

| 워커 | 1 | 4 | 10 | 20 |
|---|---|---|---|---|
| 일감 대기 | 0% | 0% | 1.0% | **6.5%** |

**[측정]** 워커 20 의 일감 대기 43건 중 **21건**은 그 순간 코디네이터가 trace 로그 뮤텍스에
막혀 있던 경우다 (문제 9). trace 를 끄면 남는 것은 **약 3.3%** 다.

→ **현재 손실은 작다.** 코디네이터는 여유가 0 이 된 상태로 간신히 맞추고 있고,
**워커를 더 늘리면 다음에 막힐 천장**이다. 워커 10개가 코디네이터 유휴 0% 가 되는 지점과 겹친다.

**[코드]** 덧붙여, 코디네이터의 레코드 파싱 경로에서 복제 아이템마다 테이블 이름을 문자열 비교한다
(`log_applier.c:4704`, `strcasecmp (item->class_name, CT_SERIAL_NAME)`). 코디네이터를 빠르게
만들 때 같이 볼 지점이다.

**개선 방향 (설계 검토 필요):** 게이트 판정은 `LSA_LE (dep, frontier)` 로 단조적이다.
pending 을 `dependency_seq` 기준으로 정렬해 두면 맨 앞만 보고 멈출 수 있다.
단 현재 주석이 "파킹 순서 유지"를 명시하므로, 그 순서가 정합성에 필요한지 먼저 확인해야 한다.

## 9. 재측정 (2026-11-07 저녁) — trace 끄고, 대상을 덜 멈추는 도구로

### 9.0 왜 다시 쟀나 — 4·8절 측정의 오염 두 가지

**(1) pstack 이 측정 대상을 멈춰 세웠다.** pstack(gdb) 은 덤프하는 동안 대상의 **모든 스레드를 정지**시킨다
(`/proc/<pid>/task/*/status` 의 State 가 `t`). 실측:

| 도구 | applylogdb 1회 정지 | cub_server(151 스레드) 1회 |
|---|---|---|
| pstack | **1.3~1.9초**, 13개 스레드 전부 | 약 6초 |
| eu-stack | 부하 중 중앙값 0.2~0.35초 (`-i -s`) | 스레드별로 잠깐씩만 붙잡음 — 200ms 간격 관찰에서 정지 스레드 0 |

4절 측정은 1초 간격으로 pstack 을 떴으므로 샘플 한 번이 약 3초, 그중 절반 가까이 applylogdb 가 멈춰 있었다.
그 상태에서 처리량을 같이 쟀다.

**(2) `ha_writeset_trace_level=1` 이 켜져 있었다** (8.7절). 코디네이터가 trace 한 줄마다 전역 std::mutex 를 잡는다.

이번 측정: **trace=0**, 처리량은 **샘플러 없이** 한 번, 스택은 **eu-stack** 으로 따로 한 번.
시나리오 A, 워커 4·10, 구성당 1회. 스크립트: `ha_backlog.sh` 에 `SAMPLER` / `SRV_INTERVAL` / `TRACE` 옵션,
샘플러 `ha_eustack.sh`.

### 9.4 pending 큐 실측 (trace 로그 재현) — 문제 5 의 추론 고리 확인

8절 측정 당시 trace 가 켜져 있어 `[WSET] reader schedule ... status=` (0 즉시 / 2 파킹 / 1 해제) 가 전부 남아 있었다

파킹/해제 이벤트로 pending 리스트를 그대로 재현하면, 해제된 태스크가 리스트 몇 번째에 있었는지가
`la_pending_pop_ready` 가 그 한 번에 훑은 노드 수다.

| 워커 | 파킹률 | 깊이 평균 / 최대 | 성공한 pop 의 스캔 길이 평균 / p90 / 최대 | 맨 앞에서 꺼낸 비율 | 파킹 시간 중앙값 |
|---|---|---|---|---|---|
| 1 | 0% | 0 / 0 | — | — | — |
| 4 | 99.5% | 3,618 / 3,761 | 141 / 363 / 421 | 8.8% | 7초 |
| 10 | 99.7% | 6,231 / 6,917 | 133 / 363 / 432 | 8.4% | 9초 |
| 20 | 99.7% | 5,054 / 5,503 | 135 / 340 / 412 | 8.0% | 6초 |

- **[측정] 따라잡기 중에는 거의 모든 태스크가 파킹되고 리스트에 수천 개가 쌓인다.**
- **[측정] 파킹 사유는 의존성이다.** 큐 full 로 파킹된 태스크는 게이트가 열려 있어 맨 앞에서 먼저 나가야 하는데,
  맨 앞 해제는 8% 남짓이다 — 앞쪽은 의존성이 안 풀린 태스크다. 파킹된 태스크는 전부 dependency 라벨이 있었다.
- **[코드] 상한이 워커 수에 비례한다.** 코디네이터는 커밋 순서 링이 찰 때까지 앞서 읽고, 링 크기는
  `LA_COMMIT_ORDER_CAPACITY = 워커 수 × LA_TASK_QUEUE_CAPACITY(1024)` (`log_applier_worker.hpp:47`).
  워커를 늘리면 pending 상한과 선형 스캔 비용이 같이 커진다.
- **[추론] 비용의 대부분은 꺼낼 것이 없는 헛스캔이다.** 성공한 pop 은 평균 135 노드로 싸다. 꺼낼 것이 없으면
  수천 노드를 끝까지 걷는데, drain 은 커밋을 읽을 때마다 불린다. 헛스캔 횟수는 로그에 남지 않아 세지 못했다
  → `perf record` 로 `la_pending_pop_ready` 의 CPU 시간을 직접 재면 확정된다.
- 실시간 복제처럼 코디네이터가 앞서 읽지 않는 상황에서는 리스트가 짧다. **로그가 밀렸을 때(재기동·장애 복구 후) 드러나는 문제**다.

### 9.9 [문제 10] 코디네이터의 주기적 진행정보 저장이 분배를 멈추고 전역 락을 쥔다

**[코드]** 코디네이터는 `ha_applylogdb_max_commit_interval_in_msecs` (기본 500ms) 마다
`la_coordinator_commit_apply_info()` (`log_applier.c:1605`) 를 **자기 스레드에서 동기로** 실행한다:

```c
res = la_update_ha_last_applied_info ();                       /* _db_ha_apply_info UPDATE */
...
if (la_delete_applied_tx_markers (&la_Info.committed_lsa) < 0) /* marker DELETE ... <= committed_lsa */
...
la_stat_store (&applier, la_update_query_execute_with_values); /* 통계 저장 */
return db_commit_transaction ();                               /* 커밋 — 로그 flush 대기 */
```

그리고 이 쿼리들이 지나는 `la_update_query_execute_with_values()` (`log_applier.c:7083`) 는
**marker 와 같은 전역 뮤텍스 `la_sql_compile_mutex` 를 쥔 채** `db_execute` (컴파일 + 서버 실행)를 한다.

**[측정]** 워커 20:

- 코디네이터가 이 저장 중인 샘플이 **38장 중 17장 (45%)** — 500ms 마다 평균 200ms 이상 걸린다는 뜻.
- 워커 굶음 158 건의 원인별 (그 순간 코디네이터 상태): **진행정보 저장 37%**, pending 스캔 35%, 로그 읽기·파싱 등 21%.
- 워커의 marker 락 대기 235 건 중 **36%** 는 코디네이터가 이 쿼리로 락을 쥐고 있던 순간이다 (워커 10: 12%, 워커 4: 0%).

**[추론] 비용이 처리량에 비례해 커진다.** 한 번에 지우는 marker 행 수 = 처리량 × 0.5초
(워커 20 이면 약 860 행). 워커가 넣은 marker 를 코디네이터가 지우는 구조라, **marker 설계가 두 번 비용을 낸다**
— 워커 쪽(INSERT, 전역 락)과 코디네이터 쪽(DELETE, 전역 락 + 분배 정지).

**개선 방향 (설계 검토 필요):**
1. 진행정보 저장을 코디네이터 밖(별도 스레드·연결)으로 빼서 분배가 멈추지 않게 한다.
2. 이 쿼리들은 서로 다른 연결/세션에서 실행되므로, 서버 실행 구간을 전역 뮤텍스 밖으로 뺀다 (문제 1 과 같은 수정).
3. marker DELETE 를 매 500ms 가 아니라 더 드물게, 또는 범위 단위로.

### 10.4 왜 워커를 늘리면 느려지나 — 정리

```
워커 수 ↑  →  링 용량(워커 × 1024) ↑  →  pending 깊이 ↑ (항상 꽉 참)
                                        →  헛스캔 1회 비용 ↑ (깊이에 비례)
                                        →  코디네이터 분배 속도 ↓
실제 병렬도는 의존성 때문에 약 2.5 로 고정  →  얻는 것은 없고 비용만 는다  →  처리량 ↓
```

**문제 5 (pending 선형 스캔) 가 B 에서는 처리량을 직접 깎는 1순위 원인이다.** A 에서는 실제 병렬도가 높아 가려져 있었다.
개선 방향:
1. pending 을 dependency 기준으로 정렬하거나, 프론티어가 움직일 때 해당 의존성을 기다리던 태스크만 깨우는 방식 (헛스캔 제거).
2. 미리 읽는 깊이(링 용량)를 워커 수에 비례시키지 않는다 — 실제 병렬도 이상 앞서 읽어도 이득이 없다.

### 10.6 pending 헛스캔의 원인 (코드 + perf, 2026-11-08)

**[측정, perf] 시나리오 B 워커 4, 따라잡기 구간 104초** (`perf record -F 999 -g`, 대상 정지 없음):

| 스레드 | CPU (1코어 기준) | 그중 pending 스캔 (`la_gate_is_satisfied` + `la_pending_pop_ready`) |
|---|---|---|
| 코디네이터 | 22.6% | **56%** |
| 워커 4개 | 각 4.6~4.8% | 0% |

스캔 비용의 호출 경로 (perf 호출 그래프): **`la_coordinator_collect_results` 경유 77%**, `la_coordinator_submit_task` 경유 23%.

**[코드] 원인 — 바뀐 것이 없는데도 매번 리스트 전체를 다시 훑는다.**

1. **drain 이 무조건 불린다.** 코디네이터 메인 루프는 로그 레코드를 하나 처리할 때마다 맨 위에서
   `la_coordinator_collect_and_retire()` → `la_coordinator_collect_results()` 를 부르고 (`log_applier.c:10364`),
   이 함수는 결과를 하나도 못 가져왔어도 끝에서 `la_coordinator_drain_ready()` 를 부른다 (`log_applier.c:918`):
   ```c
   while (la_result_queue_try_pop (&result) == NO_ERROR) { ... }   /* 0 건이어도 */
   la_gate_advance_frontier ();                                      /* 프론티어가 안 움직여도 */
   return la_coordinator_drain_ready ();                             /* 항상 전체 스캔 */
   ```
   링이 가득 차 슬롯을 기다리는 동안에도 같은 함수를 반복해서 부른다 (`la_coordinator_wait_for_commit_order_slot`, `:763`).
   새 커밋을 넣기 전에도 한 번 더 부른다 (`:7793`).
2. **프론티어가 안 움직였으면 꺼낼 것이 생길 수 없다.** 게이트는 `dep <= 프론티어` 일 때만 열린다 (`log_applier_gate.cpp:324`).
   프론티어는 워커 결과를 수거할 때만 전진한다 (`la_gate_advance_frontier`). 그러니 결과가 없었던 drain 은
   (워커 큐가 꽉 차서 못 넣고 남겨둔 경우를 빼면) **반드시 빈손**이다.
3. **빈손 스캔은 리스트 끝까지 간다.** `la_pending_pop_ready()` 는 맨 앞부터 노드마다 게이트를 확인하며, 멈출 조건이 없다
   (`log_applier_pending.cpp:101`). 노드는 하나씩 `malloc` 된 연결 리스트라 포인터를 따라가는 메모리 접근이다.
4. **리스트가 길다.** 코디네이터는 링(워커 수 × 1024)이 찰 때까지 미리 읽으므로 따라잡기 중 pending 은 항상 링 용량까지 찬다
   (10.3: 워커 10 이면 약 9,400).

→ **헛스캔 1회 비용 ∝ 워커 수, 헛스캔 횟수 ∝ 처리한 로그 레코드 수.** 실제 병렬도가 낮은 B 에서는 프론티어가 드물게 움직이므로
대부분의 drain 이 빈손이다. 성공한 pop 은 평균 1.5 노드만 보는데(10.3) 코디네이터 CPU 의 절반 이상이 스캔인 이유다.

**개선 방향 (위험도 낮은 순):**

1. **변화가 있을 때만 drain** — 결과를 1건 이상 수거해 프론티어가 전진했거나, 지난 drain 이 워커 큐가 꽉 차서 멈췄을 때만 스캔한다.
   `la_coordinator_collect_results()` 와 `submit_task` 의 drain 앞에 조건 하나. 동작(해제 순서)은 바뀌지 않는다.
2. **pending 을 의존성 순으로 색인** — 게이트가 프론티어 순서로 열리므로 dependency 기준 최소 힙(동률은 파킹 순)에 두면
   "맨 앞이 안 열렸으면 멈춤" 이 가능해져 drain 이 O(해제 건수) 가 된다. 해제 순서가 파킹 순에서 의존성 순으로 바뀌므로
   in-flight / 커밋 순서 링과의 관계를 설계 검토해야 한다.
3. **미리 읽는 깊이를 워커 수에 비례시키지 않는다** — 리스트 길이와 메모리(10.5 의 RSS 증가)를 함께 줄인다.

|---|---|---|---|---|
| B · 4 | 22.6% | 56% | 약 13% | 4.7% |

- **운영 권장:** 평상시 지연만 보면 워커 4~10 이면 충분하다. 장애 복구 후 따라잡기까지 생각하면 충돌이 많은 부하에서는 워커 4 (10.1).

### 11.2 재기동 정합성 — `scripts/ha_restart_check.sh`

이 브랜치는 재기동 때 "이미 적용한 트랜잭션" 을 marker 테이블(`ha_applied_tx_marker`)로 건너뛴다 (72650ce0d, fe230a932).
그 동작을 검증했다.

- 방법: 백로그를 쌓은 뒤 applylogdb 를 띄우고, **따라잡는 도중 `kill -9` 를 반복**한다. 끝까지 따라잡은 뒤 마스터·슬레이브의
  `ha_t1`(10만 행)·`ha_t2` 를 id 순으로 덤프해 줄 단위로 비교한다.
  부하에 `UPDATE ha_t1 SET seq=seq+1` (비멱등)이 섞여 있어, 한 트랜잭션이 **두 번 적용되거나 빠지면 값이 달라진다.**
- 매 회차 **측정 전에도 비교**해, 이후의 불일치가 이번 강제 종료 때문인지 가를 수 있게 했다. 워커 10, trace 0.

| 회차 | 시나리오 | 강제 종료 | 종료 시점 (따라잡기 중 적용 건수) | 측정 전 | 강제 종료 후 | fail_counter |
|---|---|---|---|---|---|---|
| 1차 | A | 3회 | 39.7k / 80.7k / 80.7k (2·3번째는 거의 다 따라잡은 뒤) | 일치 | **일치** (t1 100,000 / t2 9,549) | 0 → 0 |
| 2차 | A | 5회 | 29.5k / 39.7k / 48.3k / 57.1k / 66.0k | 일치 | **일치** (t1 100,000 / t2 10,924) | 0 → 0 |
| 2차 | B | 5회 | 7.0k / 9.6k / 11.7k / 13.8k / 15.9k | 일치 | **일치** (t1 100,000 / t2 9,678) | 0 → 0 |

- **[측정] 강제 종료 13회 모두 데이터가 일치했다.** heartbeat 는 매번 applylogdb 를 자동으로 다시 띄웠다 (1~2초).
- **[측정] marker 가 실제로 필요한 상황이 여러 번 있었다.** 재시작 로그의 `last committed LSA` (저장된 위치) 보다
  `last committed repl LSA` (실제로 적용된 위치) 가 뒤인 채로 재시작한 경우가 2차 구간 재시작 15번 중 7번이다.
  이때 저장 위치부터 다시 읽으므로, marker 로 건너뛰지 않으면 이미 적용한 트랜잭션이 다시 적용된다. 그런데도 일치했다.
- applylogdb 에러 로그에 같은 구간 ERROR 는 시작(-1038 "log applier started")·종료(-1036) 기록뿐, 적용 실패는 없었다.
- **한계:** applylogdb 프로세스 강제 종료만 검증했다. 슬레이브 cub_server 강제 종료, 노드 전환(failover), DDL 이 섞인 부하,
  시나리오 C/D 는 아직이다. 게이트 정합성(문제 8: FK, 부모/자식 순서)도 별개로 남아 있다.

## 부록 C. 측정 방법상의 함정

이번에 실제로 겪어 시간을 소모한 것들. 같은 측정을 반복할 사람을 위해 남긴다.

**① ssh 가 원격 자식의 stdout 을 쥐고 안 돌아온다.**
`ssh host "cmd" >/dev/null` 의 리다이렉트는 *로컬* 이다. 데몬을 띄우는 원격
명령은 **원격 쪽에서** 끊어야 한다: `ssh host "cmd </dev/null >/dev/null 2>&1"`.
`timeout` 을 걸어도 소용없다 — timeout 이 부모를 죽여도 자식이 파이프를 쥐고
있으면 ssh 는 계속 기다린다.

**② `pgrep -f <패턴>` 이 자기 자신을 잡는다.**
패턴이 자기 명령줄에 들어있기 때문이다. 셸이 단일 명령을 exec 최적화하면
안 걸리지만 복합 명령에서는 걸린다. `pgrep -f 'ha_back[l]og'` 처럼 문자
클래스로 깨뜨릴 것. **`pkill -f` 로 자기 자신을 죽이는 사고가 실제로 두 번 났다.**

**③ 루프 안의 ssh 가 스크립트의 stdin 을 먹는다.** `ssh -n` 필수.
폴링이 잦으면 `ControlMaster=auto` + `ControlPersist` 로 왕복 비용을 줄일 것.

**④ 부하가 없어도 슬레이브에 초당 1건 남짓 배경 트랜잭션이 들어온다.**
"따라잡기 완료" 를 증가 **정지**로 판정하면 영원히 안 끝난다.
"최근 N폴 증가량 < 임계치" 로 판정할 것.

**⑤ 측정 창의 양 끝을 잘라야 한다.** 2.4 참조.
자르지 않으면 빠른 구성일수록 심하게 왜곡된다.

**⑥ 따라잡기 완료 후의 pstack 샘플은 유휴만 담아 분포를 왜곡한다.**
`find -newermt @<완료시각> -delete` 로 잘라낼 것.

**⑦ csql 에서 `"..."` 는 식별자다.** 문자열은 홑따옴표.
`CREATE TABLE IF NOT EXISTS` 는 되지만 `CREATE INDEX IF NOT EXISTS` 는 안 된다.
