=================== 4489620911
marker 테이블이 DBA 소유의 일반 테이블이라 master에도 있고(master 노드의 applylogdb가 만듭니다), master에서 `DROP TABLE ha_applied_tx_marker;`를 실행하면 그 DROP이 slave로 복제됩니다. slave worker는 DROP을 적용한 뒤 같은 트랜잭션의 marker INSERT에서 실패해 롤백하고, 그 뒤로 아무것도 적용하지 못했습니다(2/2). 한 번은 재시작이 반복되었고, 한 번은 두 번 재시작한 뒤 프로세스가 살아 있는 채로 멈췄습니다. 절차는 본문에 있습니다.

marker를 `_db_` 시스템 클래스로 두거나, applier가 이 테이블을 대상으로 하는 복제 문장을 걸러 내는 것이 어떨까요. RENAME과 열을 바꾸는 ALTER도 같이 막힐 것 같고, TRUNCATE는 marker 행을 지워서 재시작 때 이중 적용이 될 수 있어 보입니다(둘 다 돌려 보지는 않았습니다).

@youngjun9072 `6bd39a696` 기준으로 리뷰했습니다. 머지 전에 손봐야 할 결함을 세 건 찾았고, 모두 HA 페어에서 재현한 뒤 해당 줄에 인라인으로 달았습니다.

master의 log lock 안에서 정하는 label, slave gate의 빈틈없는 frontier, commit이 성공한 뒤에만 보내는 결과, 데이터와 같은 트랜잭션에 넣는 marker처럼 설계의 중심부에서는 결함을 찾지 못했습니다. 세 건은 모두 그 가장자리에 있습니다.

### 머지 전에 고쳐야 할 것

| 내용 | 재현 |
|---|---|
| master에서 `DROP TABLE ha_applied_tx_marker;`를 한 번 실행하면 slave applier가 그 뒤로 아무것도 적용하지 못합니다. fail_counter는 오르지 않습니다. | 2/2 |
| 바깥 트랜잭션이 롤백된 INCR fragment가 앞선 commit을 기다리는 동안 applier가 재시작하면, 그 INCR이 slave에 적용되지 않습니다. 로그를 남긴 두 회차에서 적용 오류는 없었습니다. | 3/3 (test hook으로 앞선 commit을 붙잡음), 대조군 2건 유지 |
| `utf8_gen` CHAR 열에서 `'k1'`과 `'k1' \|\| CHR(1)`을 비교는 같은 키로, 해시는 다른 키로 봅니다. slave에서 행이 사라집니다. | 20/20 누락, workers=1 대조군 20/20 유지 |

세 건 모두 slave를 `ha_apply_worker_count=4`로 두고 돌렸습니다. 앞의 두 건은 기본값 1에서 돌리지 않았지만, 코드상 같은 경로로 봅니다.

marker 테이블 DROP 건은 marker 메커니즘이 아니라 테이블을 둔 자리의 문제로 봅니다. 재시작 뒤의 재적용을 marker로 바꾼 이유(statement와 키 변경은 두 번 적용할 수 없음)는 그대로 유효하므로, marker는 유지하고 사용자의 DDL이 닿지 않게 하는 쪽을 제안했습니다.

### 재 보면 판단할 수 있는 것

- 트랜잭션 슬롯이 키 벡터의 용량을 반납하지 않는 것 같습니다(인라인).
- history를 비우는 동안 서버의 log append가 기다릴 것 같습니다(인라인).
- barrier 뒤의 read-ahead가 메모리를 많이 쥘 수 있을 것 같습니다. ring 크기가 worker 수 × 1024이고 coordinator는 ring이 찰 때만 읽기를 멈추므로, DDL처럼 commit 순서를 강제하는 barrier 뒤에서 그만큼의 트랜잭션 item이 메모리에 머뭅니다. 999행짜리 트랜잭션에 item 200~250바이트로 가정하면 N=8에서 약 1.8 GB입니다. develop의 직렬 applier는 DDL 안에서 읽기를 멈췄으므로, applier의 메모리 한도(`ha_apply_max_mem_size`와 시작 시 크기의 2배 중 큰 값)를 넘는지 한 번 재 보면 좋을 것 같습니다.

### 그 밖에

- 라벨 없는 로그(업그레이드 전 backlog, slave를 먼저 올리는 rolling upgrade)는 [greptile 스레드](https://github.com/CUBRID/cubrid/pull/8052#discussion_r4415536908)에서 후속으로 남기신 것 확인했습니다. 그때까지는 serial과 INCR이 바깥 commit에 실려 commit 순서로 적용된다는 점을 PR 본문이나 매뉴얼에 운영 조건으로 적어 두면 좋을 것 같습니다.
- FK가 있는 스트레스([cubrid-testkit](https://github.com/cubrid-systems/cubrid-testkit)의 `ha-apply stress`, 작업 10가지, 8 client × 200 트랜잭션)에서 workers=1과 4 모두 일부 회차에서 fail_counter가 1~2 올랐습니다. 확인한 한 건은 자식 행 DELETE의 -711이었습니다. develop 대조군을 돌리지 않았고, 11-05에 develop에 머지된 #8026(CBRD-27464)이 이 head에 없어서 원인은 판단하지 않았습니다. develop을 다시 머지한 뒤에도 남는지 보면 좋을 것 같습니다.

### 재현 환경과 절차

[cubrid-testkit](https://github.com/cubrid-systems/cubrid-testkit)의 csb로 만든 HA 페어(master, slave, client 컨테이너)에서 release 빌드 `11.5.0.3048-6bd39a6`로 돌렸습니다.

- slave의 `cubrid_ha.conf`에 `ha_apply_worker_count=4`를 넣고 applylogdb를 다시 띄웠습니다. 기본값은 1입니다.
- applylogdb kill은 slave 컨테이너 안에서 했습니다.
- master 쪽 SQL은 `csql -u dba <db>@<master>`로, slave 쪽 SQL은 slave에서 `csql -u dba <db>@localhost`로 실행했습니다.
- fail_counter는 slave에서 `SELECT fail_counter FROM db_ha_apply_info;`로 봤습니다.
- applier 로그는 slave의 `$CUBRID/log/<db>@localhost_applylogdb_<db>_<master>.err`입니다.

<summary>marker 테이블 DROP</summary>

```sql
-- master
CREATE TABLE rv_t (id INT PRIMARY KEY, v INT);
INSERT INTO rv_t SELECT ROWNUM, 0 FROM db_class LIMIT 10;
-- slave에 10행이 보이면 slave의 fail_counter를 적어 두고, master에서

-- 5초 뒤 master에서

-- 120초 뒤 양쪽에서
SELECT COUNT(*) FROM rv_t;
```

두 번 모두 master 20행, slave 10행이었고, slave의 marker 테이블은 남아 있었고, fail_counter는 그대로였습니다.

- 첫 실행에서는 applier가 `Unknown class "dba.ha_applied_tx_marker". insert into [dba.ha_applied_tx_marker] ...`(-493)로 9번 재시작했습니다.
- 두 번째 실행에서는 -452(`Invalid XASL tree node content`) 한 번, -493 한 번 뒤에 프로세스가 살아 있는 채로 로그가 멈췄습니다.

두 번째 실행에서 멈춘 뒤 slave에서 `cubrid lockdb <db>`를 보면, worker 트랜잭션이 이름이 찍히지 않은 클래스에 SCH_M을 쥐고 있고 coordinator 트랜잭션이 같은 클래스의 SCH_S를 기다립니다. coordinator는 la_sql_compile_mutex를 쥔 채 문장을 실행하고, worker의 marker INSERT도 같은 mutex를 잡습니다. 그래서 `0563af0b5`가 막은 escalation 경로와 달리, DROP이 marker 테이블 lock을 먼저 잡은 순서에서 생긴 교착으로 보입니다. 다만 그 클래스가 marker 테이블이라는 것과 mutex 쪽은 추정이고, 스택은 보지 않았습니다.

복구 방법은 확인하지 못했으므로 시험용 페어에서만 돌리는 것이 좋겠습니다.

<summary>롤백된 INCR fragment</summary>

slave에서 hook을 켜고 HA를 다시 시작합니다. hook은 마지막으로 적용한 클래스가 `dba.blk`인 commit을 commit 직전에 60초 붙잡습니다. trace를 보려면 그 전에 slave의 `cubrid_ha.conf`에 `ha_writeset_trace_level=2`를 넣습니다.

```sh
export CUBRID_HA_TEST_BLOCK_CLASS=dba.blk CUBRID_HA_TEST_BLOCK_MSEC=60000
cubrid service stop; sleep 3; cubrid heartbeat start
```

master에서 준비합니다. slave에서 `SELECT COUNT(*) FROM big;`가 200000이 되면 5초 더 기다립니다.

```sql
CREATE TABLE a (id INT PRIMARY KEY);
CREATE TABLE blk (id INT PRIMARY KEY);
CREATE TABLE c (id INT PRIMARY KEY, hits INT);
INSERT INTO c VALUES (1, 0);
CREATE TABLE big (id INT PRIMARY KEY, v INT);
COMMIT;
INSERT INTO big SELECT ROWNUM, 0 FROM db_class a, db_class b, db_class c LIMIT 200000;
COMMIT;
```

master에서 세 세션을 아래 시각에 실행합니다(`--no-auto-commit`).

| 시각 | 세션 | SQL |
|---|---|---|
| t | 1 (백그라운드) | `INSERT INTO a VALUES (1); SELECT SLEEP(8); SELECT INCR(hits) FROM c WHERE id = 1; ROLLBACK;` |
| t+2초 | 2 | `UPDATE big SET v = v + 1; COMMIT;` |
| 세션 2가 끝나고 1초 뒤 | 3 | `INSERT INTO blk VALUES (1); COMMIT;` |

1. 세션 3을 commit하고 8초 뒤, master에서 `SELECT hits FROM c WHERE id = 1;`이 1인지 봅니다. 롤백되어도 INCR은 남으므로, 1이면 T가 끝난 것입니다.
2. 이때 slave applier 로그에 `ws_marker TEST block before commit ... class=dba.blk`가 있으면 hook이 세션 3의 commit을 붙잡고 있는 것입니다.
3. 3초 더 기다린 뒤, hook이 놓기 전에 slave에서 `pkill -9 -f 'cub_admin [a]pplylogdb'`를 실행합니다.
4. 80초 뒤 master에 `INSERT INTO a VALUES (2); COMMIT;`을 넣습니다. slave가 그 행을 적용하면 양쪽의 `SELECT hits FROM c WHERE id = 1;`를 비교합니다.

hook과 kill을 함께 한 3번 모두 master 1, slave 0이었습니다. hook만 켠 회차와 kill만 한 회차는 1로 같았습니다. 첫 줄은 kill 전에, 나머지는 재시작 뒤에 찍힌 trace입니다.

```

log applier: log applier started. required LSA: 8235|11520. last committed LSA: 8235|11432. ...
[WSET] coordinator complete_without_task lsa=8235|13664
[WSET] coordinator sysop_end trid=128 sysop_lsa=8235|13664 committed_lsa=8235|11520 items=0 action=defer labeled=1 long=0
```

이 hook은 TODO대로 지우실 예정인 것으로 알고 있습니다. 지우기 전에 이 건의 수정 확인에 쓰면 좋을 것 같습니다.

<summary>CHAR 끝의 weight 0 문자</summary>

`utf8_gen`은 de_DE locale을 컴파일해야 생깁니다.

1. `make_locale.sh -t 64bit -m release de_DE`를 실행합니다.
2. 모든 노드의 `cubrid_locales.txt`에 `de_DE`를 넣습니다.
3. DB 노드마다 서버를 멈추고 `cubrid synccolldb -f <db>`를 실행한 뒤 다시 시작합니다.

그러면 `SHOW COLLATION LIKE 'utf8_gen'`이 Built_in No, Expansions No로 나옵니다.

```sql
-- master
CREATE TABLE rv_ballast (id INT PRIMARY KEY, r INT);
CREATE TABLE rv_gen_trail (id INT PRIMARY KEY, u CHAR(12) COLLATE utf8_gen UNIQUE);
COMMIT;
-- 전제 확인: 두 번째 INSERT가 unique 위반으로 실패해야 합니다
INSERT INTO rv_gen_trail VALUES (-1, 'k0'); COMMIT;
INSERT INTO rv_gen_trail VALUES (-2, 'k0' || CHR(1));
COMMIT;
DELETE FROM rv_gen_trail; COMMIT;

-- 라운드 r = 1..20
-- 세션 1
INSERT INTO rv_gen_trail VALUES (r, 'k<r>'); COMMIT;
-- 세션 2
DELETE FROM rv_ballast;
INSERT INTO rv_ballast SELECT ROWNUM, r FROM db_class a, db_class b, db_class c LIMIT 20000;
DELETE FROM rv_gen_trail WHERE id = r;
COMMIT;
INSERT INTO rv_gen_trail VALUES (r + 100000, 'k<r>' || CHR(1));
COMMIT;

-- 끝나면 master에 빈 테이블(rv_end)을 만들고, slave의 db_class에 보이면 양쪽에서
SELECT COUNT(*) FROM rv_gen_trail;
```

workers=4에서 master 20행, slave 0행이었습니다. slave 로그에는 `failed to apply insert replication log. class: "dba.rv_gen_trail", key: "<r + 100000>", server error: -670`이 라운드마다 남았습니다. 같은 페어에서 workers=1로 바꾸면 20행 모두 유지되었습니다.
