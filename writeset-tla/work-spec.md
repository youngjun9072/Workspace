# writeset 병렬 applier TLA+ 모델링 작업 명세

## 1. 목적과 범위

PR #8052 writeset 병렬 applier의 순서 보장 설계를 TLA+로 기술하고, 모델 체커 TLC로 가능한 모든 실행 순서를 검사한다. 이미 확인된 결함 세 가지가 모델에서 반례로 재현되는지, 수정 설계를 넣은 모델에서는 반례가 사라지는지를 확인한다.

대상 결함은 다음 세 가지다.

- 라벨이 붙은 SYSOP_END에서 키를 잃는 문제
- failover 때 반영 위치에 빈틈이 생기는 문제
- 마스터의 키 발행 시점 때문에 커밋 순서가 역전되는 문제(sq_uniq)

범위에 넣는 것은 다음과 같다.

- 마스터: 행 변경과 키 수집, system operation의 시작과 종료(바깥 트랜잭션에 붙이는 종료, 라벨을 쓰는 종료), 라벨 기록, 커밋, 키 발행, 커밋 순서 기준선
- 슬레이브: 코디네이터의 태스크 배정, 의존성 대기, 워커 반영, 진행 위치 기록, failover와 재시작

범위에서 빼는 것은 다음과 같다.

- 해시 충돌, 페이지와 버퍼, 네트워크 지연의 구체 값, 복사 로그 파일 형식
- FK와 UNIQUE 해시 규칙. 1차에서는 키 하나로 추상화하고 2차 확장으로 미룬다.

## 2. 산출물

- `WritesetApply.tla`: 상태 변수, 동작, 불변식을 담은 본 명세
- 결함별 설정 파일 세 개. 결함마다 상수 크기와 켜는 동작을 다르게 둔다.
- 수정안 설정 파일. 같은 명세에 수정 플래그를 켜서 실행한다.
- 결과 노트. 반례 경로를 사람이 읽을 수 있게 풀어 쓴 것과, 모델의 각 동작이 어느 코드 함수에 대응하는지 적은 목록

## 3. 모델 구성

상수는 트랜잭션 집합(2~3개), 키 집합(1~2개), 워커 수(2), 결함과 수정안을 켜고 끄는 플래그로 둔다.

상태 변수는 다음과 같다.

- `mlog`: 마스터 로그. DML, SYSOP_END, LABEL, COMMIT 레코드가 순서대로 쌓인다.
- `wset`: 트랜잭션별로 아직 발행하지 않은 키
- `pendingRepl`: 아직 로그에 나가지 않은 복제 레코드와 그 상태(NEED_FLUSH 여부)
- `history`: 키마다 마지막으로 커밋한 위치
- `locks`, `mvccState`: 세 번째 결함에서만 쓴다.
- `tasks`: 슬레이브 코디네이터가 배정한 태스크와 의존 위치
- `applied`: 슬레이브에 반영된 순서열
- `slaveLsa`: 슬레이브가 기록한 진행 위치
- `mode`: 정상, 승격됨, 재시작 중

동작은 다음과 같다.

- 마스터: 트랜잭션 시작, 행 변경, system operation 시작, system operation 종료(바깥에 붙임), system operation 종료(라벨), 커밋, 키 발행, MVCC 완료(세 번째 결함용), 다른 트랜잭션의 행 삭제(세 번째 결함용)
- 슬레이브: 로그 읽기와 태스크 배정, 워커 반영, 진행 위치 기록, failover, 재시작

## 4. 불변식

- 충돌 순서 보장: 같은 키를 건드린 두 트랜잭션은 마스터 커밋 순서대로 슬레이브에 반영된다. 세 결함 모두의 기준이다.
- 키 유실 없음: 로그에 나간 복제 레코드의 키는 그 레코드를 담은 라벨의 의존성 계산에 반영됐거나, 아직 wset에 남아 있다. 첫 번째 결함용이다.
- 승격 시 빈틈 없음: 승격 순간, 기록된 진행 위치 이전에 커밋된 트랜잭션은 모두 반영되어 있다. 두 번째 결함용이다.
- 정확히 한 번: 재시작을 거쳐도 어떤 트랜잭션도 두 번 반영되거나 빠지지 않는다. 두 번째 결함용이다.
- 활성 성질(1차는 선택): 공정성을 가정하면 배정된 태스크는 언젠가 반영된다. 교착이 없다는 확인이다.

## 5. 진행 단계와 완료 기준

1. 환경 준비: Java 11 이상과 tla2tools.jar를 준비하고 작은 예제로 TLC 실행을 확인한다. 완료 기준은 예제 명세에서 불변식 위반 반례가 출력되는 것이다.
2. 뼈대 모델: 결함 없이 이상적으로 동작하는 마스터와 슬레이브를 기술한다. 완료 기준은 충돌 순서 보장이 모든 상태에서 성립하는 것이다.
3. 첫 번째 결함 재현: 바깥에 붙이는 종료와 라벨 종료를 현재 코드 동작(log_manager.c의 sysop 키 폐기) 그대로 넣는다. 완료 기준은 키 유실 없음 위반 반례가 나오고, 그 경로가 코드로 확인한 순서와 같은 것이다.
4. 첫 번째 결함 수정안 검증: 버릴 키를 그 SYSOP_END가 실제로 내보낸 레코드에 묶는 방식을 넣는다. 완료 기준은 같은 크기에서 위반이 없는 것이다. 이 수정 설계는 아직 미결이므로 이 단계의 결과가 설계 근거가 된다.
5. 두 번째 결함 재현과 수정안 검증: 워커가 커밋 순서와 다르게 끝나는 경우, failover, 재시작을 넣고, 이어서 DONE 게이트와 완료 마커를 넣는다. 완료 기준은 수정 전 반례가 나오고 수정 후 승격 시 빈틈 없음과 정확히 한 번이 모두 성립하는 것이다.
6. 세 번째 결함 재현과 수정안 검증: 락 없는 삽입, MVCC 완료와 키 발행 사이의 틈을 넣고, 이어서 락 해제 전에 발행하는 방식(CBRD-27034)을 넣는다. 완료 기준은 수정 전 반례가 나오고 수정 후 위반이 없는 것이다.
7. 정리: 반례 풀이 노트와 동작-코드 대응 목록을 작성한다.

## 6. 정할 것과 위험

- 환경: 현재 시스템 Java는 1.8이고 최신 tla2tools.jar는 Java 11 이상이 필요하다. 별도 JDK를 사용자 영역에 두는 방식으로 준비한다.
- 상태 폭발: 트랜잭션 3개, 워커 2개를 넘기면 검사 시간이 급격히 늘어난다. 크기를 키우기보다 결함별로 필요한 동작만 켜는 설정으로 나눈다.
- 모델과 코드의 거리: 모델에서 통과해도 코드가 모델과 다르면 의미가 없다. 동작-코드 대응 목록을 실제 함수 이름으로 적고, 코드를 고칠 때 함께 갱신한다.
- 우선순위: 첫 번째 결함의 수정 설계가 미결이므로 1~4단계를 먼저 진행하고, 두 번째와 세 번째 결함은 이미 수정된 설계를 사후 검증하는 순서로 진행한다.
