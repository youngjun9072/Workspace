# 1. 개요

## 1.1 왜 applylogdb를 병렬화하는가

현재 CUBRID applylogdb는 복제 로그의 트랜잭션을 사실상 하나씩 적용한다. 마스터가 로그를 만드는 속도보다 슬레이브의 적용 속도가 느리면 복제 지연이 계속 쌓인다. 장애 전환이나 재시작 뒤 최신 상태까지 따라잡는 시간도 길어진다.

이 설계의 목표는 **서로 영향을 주지 않는 트랜잭션을 여러 worker가 동시에 적용하는 것**이다. 단순히 worker 수만 늘리면 같은 행이나 제약조건을 건드리는 작업의 순서가 뒤집힐 수 있다. 따라서 마스터가 먼저 지켜야 할 순서를 계산해 복제 로그에 남기고, 슬레이브는 그 순서가 충족된 작업만 worker에 보내야 한다.

순서 판정에는 writeset을 사용한다. writeset은 트랜잭션이 건드린 PK·UNIQUE·FK 키를 짧은 해시값으로 모아 둔 집합이다. 두 트랜잭션에서 같은 충돌 키가 발견되면 앞 트랜잭션을 먼저 적용해야 한다고 판단하고, 겹치는 키가 없으면 동시에 실행할 수 있다고 판단한다. 기본 원리는 [2장](./2-writeset이란.md)에서 설명한다.

PK와 UNIQUE에는 이 판정이 그대로 통한다. 문제는 FK다. 같은 부모 행을 참조하는 자식 트랜잭션들은 실제로 서로의 데이터를 바꾸지 않는데도 같은 충돌 키를 남기므로, 단순 writeset은 이들을 하나의 사슬로 묶어 직렬화한다. MySQL은 여기에 더해 부모 테이블이 변경되면 이력을 통째로 비워 뒤의 모든 트랜잭션을 밀어낸다([3장](./3-mysql-writeset-처리와-한계.md)). CUBRID 설계는 이 문제를 키 접근을 두 종류로 나누어 푼다. 그 구분이 다음 절의 WRITE와 REF다.

## 1.2 왜 WRITE와 REF를 구분하는가

PK와 UNIQUE 값은 행이나 고유값의 생성·변경·삭제에 따라 상태가 바뀐다. 이 설계에서는 이런 키 항목을 **WRITE**라고 부른다.

자식 행의 FK는 부모 키가 존재한다는 사실을 전제로 사용한다. 자식이 부모 키 자체를 바꾸는 것은 아니므로 이 항목을 **REF**라고 부른다. REF는 일반적인 SELECT나 모든 읽기 작업을 뜻하지 않는다. 이 문서에서는 **자식 FK가 부모 키를 참조하는 관계**만 뜻한다.

부모 키 7을 예로 들면 다음과 같다.

```text
P0: 부모 키 7 생성               → WRITE
C1: 부모 키 7을 참조하는 자식 작업 → REF
C2: 부모 키 7을 참조하는 자식 작업 → REF
P3: 부모 키 7 삭제               → WRITE
```

필요한 순서는 간단하다.

- C1과 C2는 부모를 만든 P0가 끝난 뒤 실행해야 한다.
- C1과 C2는 같은 부모를 참조할 뿐 서로의 데이터를 바꾸지 않으므로 동시에 실행할 수 있다.
- 부모를 없애는 P3는 C1과 C2가 모두 끝난 뒤 실행해야 한다.

```text
       ┌─ C1 ─┐
P0 ────┤      ├──→ P3
       └─ C2 ─┘
```

WRITE와 REF를 한 종류의 이력으로 저장하면 C2가 C1을 기다리는 사슬이 생겨 자식끼리 직렬화된다. 반대로 REF를 전혀 기록하지 않으면 P3가 C1과 C2를 발견하지 못해 부모 작업이 먼저 실행될 수 있다.

이를 해결하기 위해 같은 부모 키 아래에 **마지막 변경 이력과 참조 이력을 따로 기록**한다.

- 현재 작업이 REF이면 같은 키의 이전 WRITE만 기다린다. 따라서 형제 자식끼리는 서로 기다리지 않는다.
- 현재 작업이 WRITE이면 같은 키의 이전 WRITE와 REF를 모두 확인한다. 따라서 부모 변경이 앞선 자식 작업을 건너뛰지 않는다.

문서에서 사용하는 `write_seq`는 마지막 WRITE의 COMMIT 위치이고, `read_seq`는 여러 REF가 남긴 COMMIT 위치 중 가장 큰 값이다. 이 두 슬롯의 계산 과정은 [6-1.3절](./6-1-cubrid-마스터-writeset-설계.md#6-13-write와-ref-history를-분리하는-이유)에서 단계별로 설명한다.

설계의 중심은 **필요한 부모·자식 순서는 지키고, 같은 부모를 참조할 뿐인 자식과 관계없는 트랜잭션은 동시에 실행하는 것**이다.

## 1.3 마스터에서 슬레이브까지의 처리 흐름

전체 처리는 다음 순서로 이어진다.

```text
마스터
행 연산에서 충돌 키 수집
→ 키를 WRITE 또는 REF로 구분
→ COMMIT 직전에 과거 이력과 비교해 기다릴 선행 COMMIT 결정
→ 계산 결과를 복제 로그에 기록
→ 본인 COMMIT 위치를 새 이력으로 게시

슬레이브
복제 변경·선행 조건·COMMIT을 transaction task로 묶음
→ 지금 실행할 수 있는지 판정
→ 실행 가능: worker queue로 전달
→ 아직 불가능: pending에 보관
→ worker의 DB COMMIT 결과 수거
→ 완료 상태 갱신 후 pending task 재판정
```

마스터는 COMMIT 직전에 전역 history를 조회해 현재 트랜잭션이 기다릴 위치를 정한다. 이 결과만 `WS_LABEL`에 기록하므로, 슬레이브가 해시나 제약조건을 다시 계산할 필요는 없다. 마스터 설계는 [6-1장](./6-1-cubrid-마스터-writeset-설계.md), 실제 함수 변경은 [8-1장](./8-1-cubrid-마스터-writeset-상세-설계.md)에서 설명한다.

슬레이브의 reader는 같은 트랜잭션의 변경 목록, `WS_LABEL`, COMMIT을 하나의 task로 묶는다. 선행 작업이 이미 끝났으면 task를 worker에 보내고, 아직 끝나지 않았으면 pending에 둔 뒤 다음 로그를 계속 읽는다. 앞의 한 작업이 막혀도 뒤의 독립 작업을 읽고 배정할 수 있으므로 reader 전체가 함께 멈추지 않는다. 슬레이브 설계는 [6-2장](./6-2-cubrid-슬레이브-병렬-적용-설계.md), 실제 호출 관계는 [8-2장](./8-2-cubrid-슬레이브-병렬-적용-상세-설계.md)에서 설명한다.

## 1.4 완료 순서가 바뀌어도 안전한 위치를 유지한다

여러 worker가 동시에 실행되면 마스터의 COMMIT 순서와 worker의 완료 순서가 달라질 수 있다.

```text
마스터 COMMIT 순서: C1 → C2 → C3
worker 완료 순서:   C3 → C1 → C2
```

C3이 먼저 끝났더라도 C1과 C2가 남아 있으면 C3까지 모두 적용됐다고 기록할 수 없다. 이때 C1·C2 앞의 빈 구간을 **홀**이라고 한다.

슬레이브는 두 상태를 구분해야 한다.

- **개별 완료**: 특정 트랜잭션 하나가 DB COMMIT을 끝냈는지 나타낸다.
- **연속 완료 경계**: 앞에서부터 빠진 트랜잭션 없이 모두 끝난 마지막 위치를 나타낸다.

reader가 읽은 위치는 worker보다 먼저 전진할 수 있다. 그러나 재시작에 사용하는 `committed_lsa`는 연속 완료 경계까지만 전진해야 한다. 역할 전환과 비정상 종료 뒤의 처리, LSA와 재시작 규칙은 [7장](./7-writeset-병렬화에-따른-lsa-관리-변화.md)에서 설명한다.

## 1.5 코드와 실측으로 확인한 것

MySQL은 writeset으로 병렬 적용 순서를 전달하지만, FK에서는 병렬성이 줄어드는 두 현상이 확인됐다.

- 같은 부모를 참조하는 자식들이 앞 자식의 순번을 이어받아 직렬 사슬을 만든다.
- 앞의 트랜잭션이 대기하면 coordinator도 그 위치에서 멈춰 뒤의 독립 트랜잭션 배정이 늦어진다.

MySQL의 키 수집·의존성 계산 코드와 실측은 [3장](./3-mysql-writeset-처리와-한계.md)에 정리하고, 원본 코드 근거는 [10.1절](./10-코드-및-실측-부록.md#101-mysql-writeset-코드-근거)에 보존한다.

CUBRID의 초기 시도에서는 자식끼리 병렬로 실행시키기 위해 자식 FK 참조를 이력에 남기지 않았다. 자식은 부모 생성만 기다렸지만, 뒤의 부모 DELETE가 앞선 자식 작업을 발견하지 못했다. 실제 실험에서는 다음 현상이 관측됐다.

- RESTRICT·NO ACTION에서 부모가 먼저 사라지고 자식이 잠시 남았다.
- CASCADE에서 부모 작업이 자식을 먼저 지워 뒤의 자식 DELETE가 부분 실패로 집계됐다.
- SET NULL에서 마스터에 없던 자식 FK의 NULL 상태가 잠시 나타났다.

원시 관측값과 실행 코드 근거는 [10.3절](./10-코드-및-실측-부록.md#103-cubrid-fk-액션별-슬레이브-실행-코드-근거)과 [10.4절](./10-코드-및-실측-부록.md#104-cubrid-fk-액션별-원시-관측값)에 있다. 이 결과 때문에 REF를 생략하지 않고 WRITE와 분리해 기록하는 현재 설계를 선택했다.

WRITE·REF 슬롯을 분리한 실측에서는 같은 부모를 참조하는 두 자식이 부모 완료 뒤 동시에 실행됐다. 독립 트랜잭션도 부모 작업과 겹쳐 실행되어 reader의 head-blocking이 없음을 확인했다. 이 결과는 [6-3 FK 병렬성 실측](./6-3.%20FK%20병렬성%20실측%20%28headblock%2C%202026-09-12%29.md)에 정리한다.

## 1.6 충돌 키로 쓰는 대상

이번 설계에서 충돌 키로 사용하는 대상은 다음과 같다.

- **PRIMARY KEY**: 행의 생성·변경·삭제 순서를 위한 WRITE
- **UNIQUE·REVERSE UNIQUE**: 고유값의 사용과 재사용 순서를 위한 WRITE
- **FOREIGN KEY**: 부모 키는 WRITE, 자식이 가리키는 부모 키는 REF

일반 INDEX와 REVERSE INDEX는 검색 경로를 제공하지만 중복이나 참조 무결성을 강제하지 않으므로 writeset 대상에서 제외한다. UPDATE는 키가 바뀌기 전 값과 바뀐 후 값을 모두 수집해 이전 값의 해제와 새 값의 사용 순서를 함께 보호한다.

NULL인 FK에는 참조할 부모가 없으므로 REF를 만들지 않는다. 자식 행의 PK·UNIQUE WRITE와 일반 복제 처리는 그대로 수행한다. 복합 FK는 부모 복합 PK 전체와 같은 충돌 키를 만드는 것이 정식 설계이며, 현재 구현 보강과 검증이 남아 있다.

문서 전체의 범위와 비범위는 [README](./README.md#범위)에 있다.
