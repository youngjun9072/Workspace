# MySQL writeset 추가 조사 — UNIQUE와 FK

## 1. 조사 범위

기존 MySQL writeset 조사에서는 writeset의 정의, `SEQ`·`LC` 계산, 전역 history, commit-order 폴백과 슬레이브의 LC/LWM 판정을 정리했다. 이 보고서는 그 내용을 반복하지 않고 다음 누락 항목만 보충한다.

1. PK가 달라도 UNIQUE 값 때문에 실행 순서가 필요한 이유
2. FK가 참조하는 부모 테이블을 변경할 때 MySQL이 commit-order로 폴백하는 코드 경로
3. 이 폴백이 누락되면 발생할 수 있는 부모·자식 순서 역전
4. 같은 부모를 참조하는 자식 트랜잭션이 서로 직렬화되는 이유와 실측

분석은 MySQL 9.7 계열 소스와 MySQL 9.7.2 실측을 기준으로 한다. 코드 경로와 실측 원자료는 `writeset_poc_v2`의 자료조사·FK 병렬화 문서를 함께 대조했다.

### 핵심 결론

- **UNIQUE도 해시해야 한다.** PK가 다른 행도 앞 트랜잭션이 UNIQUE 값을 제거하고 뒤 트랜잭션이 같은 값을 재사용하면 순서를 지켜야 한다.
- **WL#9556 FR13은 FK 부모를 변경한 트랜잭션을 `COMMIT_ORDER`로 되돌리고 writeset history를 초기화하도록 규정한다.** 현재 코드도 이 요구대로 writeset으로 `LC`를 낮추지 않고 commit-order 값을 사용한다. 이 보고서에서는 부모·자식 dependency 누락을 막는 이 동작을 **FK 부모 폴백**이라고 부른다.
- **폴백이 필요한 모든 구체적 사례를 설명한 단일 설계 문서는 찾지 못했다.** 부모·자식 dependency 누락 시 자식이 먼저 적용되어 FK 오류가 발생할 수 있다는 근거는 [4장의 Bug #109923과 #97836](#4-fk-폴백이-누락되면-생길-수-있는-문제)에서 설명한다.
- **자식 직렬화는 부모 폴백 자체가 아니라 자식 FK 해시의 history 갱신에서 생긴다.** [Bug #110071](https://bugs.mysql.com/bug.php?id=110071)이 보고한 것처럼, 같은 부모를 참조한 첫째 자식이 슬롯의 주인이 되고 둘째 자식이 그 순번을 기다리면서 형제 사슬이 만들어진다.

## 2. UNIQUE 해시가 필요한 이유

다음 두 트랜잭션은 서로 다른 PK를 사용하지만 같은 UNIQUE 값 `X`의 제거와 재사용 순서를 가진다.

```sql
CREATE TABLE account (
  id INT PRIMARY KEY,
  email VARCHAR(100) UNIQUE
);

-- ① T1: 기존 UNIQUE 값 X를 제거한다.
DELETE FROM account WHERE id = 1;            -- 기존 행: (1, 'X')

-- ② T2: 다른 PK로 UNIQUE 값 X를 다시 사용한다.
INSERT INTO account VALUES (2, 'X');
```

마스터에서는 T1이 먼저 `email='X'`를 제거하고 T2가 그 값을 재사용하므로 두 트랜잭션 모두 정상적으로 커밋된다. 문제는 이 순서가 dependency로 기록되지 않으면 슬레이브의 병렬 적용에서 T2가 T1보다 먼저 실행될 수 있다는 점이다. 그 순간 슬레이브에는 기존 `email='X'`가 아직 남아 있으므로 T2가 UNIQUE 위반으로 실패한다.

판정 과정은 다음과 같다.

1. **마스터:** T1이 `account(id=1, email='X')`를 삭제한 뒤, T2가 `account(id=2, email='X')`를 삽입한다. 마스터에서는 기존 값 `X`가 먼저 제거되므로 두 트랜잭션 모두 정상 커밋한다.
2. **PK만 비교한 로그:** T1의 `H(account.PRIMARY,1)`과 T2의 `H(account.PRIMARY,2)`가 다르므로 T2가 T1을 기다려야 한다는 dependency가 기록되지 않는다.
3. **슬레이브의 순서 역전:** worker가 T2의 `INSERT account(2,'X')`를 T1의 `DELETE account WHERE id=1`보다 먼저 실행할 수 있다.
4. **슬레이브 오류:** 이 시점에는 `account(id=1, email='X')`가 아직 남아 있으므로 T2의 INSERT가 `account.email` UNIQUE 제약에 걸려 실패한다.
5. **UNIQUE 해시로 순서 보존:** 두 트랜잭션에서 `H(account.email,'X')`가 일치하므로 `T2.LC=T1.SEQ`를 기록한다. 슬레이브는 T1이 `(1,'X')`를 삭제한 뒤에만 T2의 `(2,'X')`를 삽입한다.

즉 PK 해시는 **어느 행을 변경했는지**, UNIQUE 해시는 **어느 제약 값을 제거하거나 점유했는지**를 나타낸다. 두 종류를 함께 수집해야 행 식별자와 제약 값 재사용 순서를 모두 보존할 수 있다.

## 3. FK 부모 변경의 commit-order 폴백

### 3.1 자식 참조와 부모 변경은 다른 경로를 탄다

다음 스키마에서 `child.parent_id`는 `parent.id`를 참조한다.

```sql
CREATE TABLE parent (
  id INT PRIMARY KEY
);

CREATE TABLE child (
  id INT PRIMARY KEY,
  parent_id INT,
  FOREIGN KEY (parent_id) REFERENCES parent(id)
);
```

마스터가 먼저 `INSERT INTO parent VALUES (7)`을 커밋하고, 뒤에서 `INSERT INTO child VALUES (101,7)`을 커밋한다고 하자. 자식 행에서는 자기 PK와 FK가 각각 해시된다. 이 중 FK 해시는 자식 테이블의 키 공간이 아니라 참조 대상 부모 키 형식으로 만들어진다.

```text
T_PARENT의 writeset
└─ 부모 PK에서 생성: H(parent, PRIMARY, 7)

T_CHILD의 writeset
├─ 자식 PK에서 생성: H(child, PRIMARY, 101)
└─ 자식 FK에서 생성: H(parent, PRIMARY, 7)
                       └─ 부모 트랜잭션의 해시와 같은 값
```


반면 현재 변경하는 테이블이 다른 FK에서 참조되는 **부모 테이블**이면, MySQL은 이 해시를 이용해 dependency를 정밀하게 낮추지 않는다. 키 수집 단계에서 상태만 표시하고 실제 폴백은 COMMIT dependency 계산에서 수행한다.

### 3.2 코드 흐름

키 추출 단계의 핵심은 다음 상태 표시다.

```cpp
add_pke(table, thd, record):
    ...
    if table->s->foreign_key_parents > 0:
        ws_ctx->set_has_related_foreign_keys()
```

`foreign_key_parents > 0`은 현재 변경하는 테이블을 참조하는 FK가 존재한다는 뜻이다. 이 함수는 여기서 history를 비우지 않고 트랜잭션 상태만 남긴다.

COMMIT 경로의 `Writeset_trx_dependency_tracker::get_dependency()`가 이 상태를 확인한다.

> 전체 dependency 알고리즘과 `commit_order_parent`·`last_parent`·`last_committed` 계산은 Jira 문서 **[survey] writeset 상세 분석**을 참고한다. 여기서는 그 알고리즘에서 FK 부모 상태가 만드는 폴백 분기만 남긴다.

```cpp
can_use_writesets =
    row_format_and_other_conditions
    && !ws_ctx->get_has_related_foreign_keys()
    && !ws_ctx->was_write_set_limit_reached()

if can_use_writesets:
    calculate dependency from writeset history
else:
    last_committed = commit_order_parent
    history_start = current_seq
    history.clear()
```

참조되는 부모 테이블 변경의 결과는 다음과 같다.

1. `LC`를 writeset 충돌 위치까지 낮추지 않고 commit-order의 `commit_order_parent`를 사용한다.
2. 현재 트랜잭션의 해시를 history에 게시하지 않는다.
3. `history_start`를 현재 `SEQ`로 올리고 기존 history를 비운다.
4. 뒤 트랜잭션은 해시를 찾지 못해도 이 하한보다 과거로 `LC`를 낮출 수 없다.

이 네 단계는 [WL#9556의 FR13](https://dev.mysql.com/worklog/task/?id=9556)이 규정한 **FK 부모 변경 시 `COMMIT_ORDER` 폴백과 writeset history 초기화**에 해당한다. 이 보고서에서 말하는 안전 장치는 WorkLog의 기능명이 아니라, 이 동작이 뒤 트랜잭션의 `LC`가 부모 이전으로 내려가지 않게 막는다는 의미다. 소스 주석은 대표 이유로 FK cascade 가능성을 들지만, 실제 코드는 CASCADE·RESTRICT·SET NULL을 구분하지 않고 참조되는 부모 테이블을 변경하면 같은 폴백을 적용한다.

## 4. FK 폴백이 누락되면 생길 수 있는 문제

공식 WorkLog과 코드는 폴백 동작을 명시하지만, 이 보수적 정책이 필요한 모든 사례와 선택 배경을 하나의 설명으로 제공하지는 않는다. [Bug #109923](https://bugs.mysql.com/bug.php?id=109923)과 [Bug #97836](https://bugs.mysql.com/bug.php?id=97836)은 **부모·자식 dependency가 누락됐을 때 실제로 어떤 결과가 가능한지** 보여주는 근거다. 아래에서는 앞 절의 폴백 설명을 반복하지 않고 각 이슈에서 확인되는 누락 조건과 결과만 정리한다.

### 4.1 Bug #109923 — PK 없는 부모에서 폴백 표시 누락

[Bug #109923](https://bugs.mysql.com/bug.php?id=109923)은 부모의 보조 인덱스를 참조하는 FK에서 자식의 `last_committed`가 실제보다 작게 기록되어, 슬레이브가 자식을 부모보다 먼저 적용하고 `HA_ERR_NO_REFERENCED_ROW`로 SQL applier가 중단되는 문제를 보고했다.

원인은 `set_has_related_foreign_keys()` 호출이 PK가 있는 테이블만 들어가는 블록 안에 있다는 점이다.

```cpp
if table has a primary key:
    collect PK, UNIQUE and child FK hashes

    if table->s->foreign_key_parents > 0:
        set_has_related_foreign_keys()  // PK가 없으면 여기에 도달하지 못함
```

PK 없는 부모는 `missing-key` 때문에 자신의 dependency에는 commit-order 값을 사용할 수 있지만, FK 부모 전용 경로가 만드는 `history_start=current_seq`와 history 초기화는 놓칠 수 있다. 그 결과 뒤 자식의 `LC`가 부모 `SEQ`보다 과거까지 낮아질 수 있다.

원래 이슈의 비유니크 보조 인덱스 참조는 MySQL 9.7.2 기본 설정에서 신규 DDL이 제한된다. 그러나 **PK 없이 완전한 UNIQUE KEY만 가진 부모**는 허용된다. 같은 PK 게이트 문제가 현재 허용되는 구성에서도 남는지 다음 스키마로 확인했다.

```sql
CREATE TABLE parent_no_pk (
  did INT UNIQUE,
  name VARCHAR(10)
);

CREATE TABLE child_no_pk (
  id INT PRIMARY KEY,
  did INT,
  FOREIGN KEY (did) REFERENCES parent_no_pk(did)
);

CREATE TABLE independent (
  id INT PRIMARY KEY
);
```

1. `T_BASE(SEQ=1)`가 `independent(id=1)`을 삽입한다.
2. `T_PARENT(SEQ=2)`가 `parent_no_pk(did=7, name='c')`를 삽입한다.
3. `T_OTHER(SEQ=3)`가 `independent(id=2)`를 삽입한다.
4. `T_CHILD(SEQ=4)`가 `child_no_pk(id=101, did=7)`을 삽입한다.
5. 정상이라면 `T_CHILD.LC`가 부모의 `SEQ=2` 이상이어야 한다. 그러나 MySQL 9.7.2 실측에서는 `T_CHILD.LC=1`로 기록됐다. PK가 있는 부모 대조군에서는 `T_CHILD.LC=2`였다.
6. 슬레이브의 완료 경계가 1인 동안 부모 T_PARENT가 아직 실행 중이어도 `LC=1`인 T_CHILD는 worker에 배정될 수 있다. T_CHILD가 먼저 실행되면 `parent_no_pk.did=7`이 아직 없으므로 FK 오류가 발생한다.

즉 이 실측은 부모 폴백 표시가 누락되면 자식의 dependency에서 부모 트랜잭션이 빠질 수 있음을 보여준다. 실제 worker 순서에 따라 오류가 항상 발생하는 것은 아니지만, 순서 역전이 가능한 라벨이 기록된다는 점이 문제다.

### 4.2 Bug #97836 — 부모 키와 자식 FK 해시가 맞지 않는 경우

[Bug #97836](https://bugs.mysql.com/bug.php?id=97836)은 복합 PK `(a,b,c)`를 가진 부모를 자식 FK가 선행 접두사 `a`만 참조하는 비표준 구성에서, 그룹 복제 applier가 자식을 부모보다 먼저 적용해 FK 오류로 중단되는 사례다.

```sql
CREATE TABLE parent_composite (
  a INT,
  b INT,
  c INT,
  PRIMARY KEY (a, b, c)
);

CREATE TABLE child_prefix (
  id INT PRIMARY KEY,
  parent_a INT,
  FOREIGN KEY (parent_a) REFERENCES parent_composite(a)
);

-- T_PARENT: 부모를 먼저 생성하고 COMMIT
INSERT INTO parent_composite VALUES (7, 8, 9);

-- T_CHILD: 그 부모를 참조하는 자식을 뒤에서 생성하고 COMMIT
INSERT INTO child_prefix VALUES (101, 7);
```

```text
T_PARENT WRITE: H(parent_composite, PK, 7, 8, 9)
T_CHILD REF:    H(parent_composite, PK, 7)
                └ 값 개수가 달라 직접 일치하지 않음
```

마스터에서는 T_PARENT가 `(7,8,9)`를 삽입한 뒤 T_CHILD가 `parent_a=7`을 참조하므로 정상 커밋한다. 그러나 두 해시가 일치하지 않아 부모·자식 dependency를 만들지 못하면, applier가 T_CHILD를 먼저 실행해 참조할 부모가 없다는 FK 오류를 낼 수 있다.

이 이슈는 그룹 복제 경로이므로 비동기 복제의 FK 부모 폴백을 직접 증명하는 사례는 아니다. 다만 부모 변경과 자식 참조의 키 표현이 일치하지 않으면 dependency를 놓치고 자식 선행 적용과 FK 오류가 생길 수 있다는 위험을 보여준다. MySQL 8.4 이후 기본 `restrict_fk_on_non_standard_key=ON`은 이런 비표준 FK의 신규 생성을 제한하지만, 호환 설정이나 기존 스키마에서는 구분해서 봐야 한다.

### 4.3 해석 범위

두 이슈에서 직접 확인되는 사실은 **부모·자식 dependency가 누락되면 자식이 먼저 적용되어 FK 오류가 발생할 수 있다**는 점이다. 이를 근거로 보면 MySQL의 부모 폴백은 cascade와 비표준 키, 키 추출 경계처럼 단일 해시 매칭이 놓칠 수 있는 경우를 전역 commit-order 경계로 덮는 안전 장치로 해석할 수 있다. 이 해석은 코드·WorkLog·이슈를 종합한 것이며, MySQL이 모든 이유를 하나의 설계 문서에 명시한 것은 아니다.

## 5. 같은 부모를 참조하는 자식이 직렬화되는 이유

### 5.1 자식 FK 해시가 단일 history 슬롯의 주인이 된다

자식 FK도 PK·UNIQUE와 같은 `hash → last SEQ` history를 사용한다.

> 자식 FK 해시를 부모 키 형식으로 조립하는 `add_pke()` 경로와 `history.find()`·`last_parent`·슬롯 갱신 코드는 Jira 문서 **[survey] writeset 상세 분석**을 참고한다. 여기서는 그 코드가 같은 부모를 참조하는 자식들 사이에 만드는 결과를 설명한다.

3.1의 `parent`·`child` 테이블에서 부모 한 건과 그 부모를 공유하는 자식 두 건을 차례로 커밋한다고 하자.

```sql
-- T_PARENT
INSERT INTO parent VALUES (1);

-- T_CHILD_1
INSERT INTO child VALUES (101, 1);

-- T_CHILD_2
INSERT INTO child VALUES (102, 1);
```

부모 T_PARENT는 앞 절의 폴백 때문에 자신의 `H(parent,PRIMARY,1)`을 history에 게시하지 않는다. 따라서 부모가 history를 비운 뒤 같은 부모를 참조하는 T_CHILD_1이 부모 모양의 FK 해시 슬롯을 자신의 `SEQ`로 만든다. T_CHILD_2는 같은 슬롯에서 T_CHILD_1의 `SEQ`를 찾아 dependency로 사용하고, 다시 자기 `SEQ`로 덮어쓴다.

```text
T_PARENT: INSERT parent(id=1), SEQ=1
→ commit-order 폴백
→ history_start=1, history={}

T_CHILD_1: INSERT child(id=101,parent_id=1), SEQ=2
→ H(parent,PRIMARY,1) 없음
→ LC=history_start=1
→ history[H(parent,PRIMARY,1)] = 2

T_CHILD_2: INSERT child(id=102,parent_id=1), SEQ=3
→ history[H(parent,PRIMARY,1)] = 2 발견
→ LC=2
→ history[H(parent,PRIMARY,1)] = 3
```

두 자식은 `child.id=101`과 `child.id=102`라는 서로 다른 행을 삽입하므로 서로의 완료를 기다릴 데이터 변경은 없다. 두 트랜잭션이 공통으로 가진 것은 `parent.id=1`을 참조한다는 사실뿐이다.

슬레이브에서 T_PARENT가 끝나 `LWM=1`이 되면 T_CHILD_1은 실행할 수 있다. 그러나 T_CHILD_2는 `LC=2`로 기록됐기 때문에 T_CHILD_1의 `SEQ=2`가 완료될 때까지 기다린다. 필요한 순서인 `T_PARENT → {T_CHILD_1, T_CHILD_2}`가 `T_PARENT → T_CHILD_1 → T_CHILD_2`로 확대된 것이다. 이것이 [Bug #110071](https://bugs.mysql.com/bug.php?id=110071)이 보고한 과직렬화의 코드상 원인이다. 서로 다른 부모 값을 참조하면 FK 해시가 달라지므로 이 형제 사슬은 생기지 않는다.

### 5.2 MySQL 9.7.2 실측

부모 테이블은 `tbl_ws1(id PK, ...)`, 자식 테이블은 `tbl_ws2(id PK, parent_id FK → tbl_ws1.id, ...)`다. T_PARENT가 `tbl_ws1` 10만 행을 한 트랜잭션으로 삽입하고, T_CHILD_1과 T_CHILD_2가 `tbl_ws2`를 각각 5만 행씩 삽입했다. 마스터의 커밋 순서는 `T_PARENT → T_CHILD_1 → T_CHILD_2`다. 레플리카는 worker 10개, `LOGICAL_CLOCK`, commit-order 보존 활성 상태로 측정했다.

- **부모행 분리 대조군**: T_CHILD_1의 `id=1~50000`은 같은 번호의 `parent_id=1~50000`, T_CHILD_2의 `id=50001~100000`은 `parent_id=50001~100000`을 참조한다.
- **부모행 공유 실험군**: T_CHILD_1과 T_CHILD_2의 10만 행이 모두 `tbl_ws1.id=1`을 참조한다.

| 트랜잭션 | 부모행 분리 | 부모행 공유 |
|---|---:|---:|
| T_PARENT: `tbl_ws1` 10만 행 (`SEQ=1`) | `LC=0` | `LC=0` |
| T_CHILD_1: `tbl_ws2.id=1~50000` (`SEQ=2`) | `LC=1` | `LC=1` |
| T_CHILD_2: `tbl_ws2.id=50001~100000` (`SEQ=3`) | **`LC=1`** | **`LC=2`** |

| 트랜잭션 | 부모행 분리 | 부모행 공유 |
|---|---|---|
| T_PARENT | W1, 0.000~4.228초 | W1, 0.000~6.052초 |
| T_CHILD_1 | W1, 4.235~10.572초 | W1, 6.071~13.919초 |
| T_CHILD_2 | **W2, 5.315~12.814초** | **W1, 13.922~19.160초** |

부모행 분리에서는 T_CHILD_1과 T_CHILD_2의 `LC`가 모두 1이고 서로 다른 worker에서 약 5.26초 겹쳐 실행됐다. 부모행 공유에서는 T_CHILD_2의 `LC`가 T_CHILD_1의 `SEQ=2`로 올라갔고, T_CHILD_1이 13.919초에 끝난 직후 T_CHILD_2가 13.922초에 시작해 실행 구간이 겹치지 않았다. 이 비교는 한 번의 통제 실험이므로 절대 시간은 일반 성능 수치로 사용하지 않는다. 다만 `parent_id` 공유 여부만 바꾼 조건에서 `LC=1→2`와 비중첩 실행이 함께 나타나 FK 해시가 만든 형제 사슬을 확인할 수 있다.

## 6. PoC 설계에 반영할 점

1. PK만 해시하지 않고 UNIQUE의 생성·변경·삭제 순서도 충돌 키에 포함해야 한다.
2. UPDATE는 변경 전과 변경 후 키를 모두 수집해야 한다.
3. FK 부모 폴백을 제거하려면 부모 WRITE와 자식 REF가 모든 지원 스키마에서 같은 키로 만나는지 먼저 보장해야 한다.
4. FK 해시를 추가하더라도 REF가 단일 history 슬롯의 주인을 덮어쓰게 하면 같은 부모를 참조하는 자식이 다시 직렬화된다.
5. 따라서 CUBRID PoC는 같은 해시 안에서도 WRITE 이력과 REF 이력을 분리하고, REF끼리는 서로 dependency를 만들지 않도록 설계해야 한다.
