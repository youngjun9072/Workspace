# C8. 새 로그 레코드 타입 53이 구 바이너리의 상한값과 같음

## 1. 메타
| 항목 | 내용 |
|---|---|
| 등급 | 종합 문서 Medium → **정책 판단(수정 안 함)** |
| 상태 | 판정 완료(10-23). 버전이 다른 노드를 섞은 HA는 고려하지 않는다 |
| 판정 | 사실은 확정(코드). 같은 버전끼리의 HA에서는 생기지 않는다 |
| 신규/기존 | 신규. 원인 커밋 `fb82b7db69`(master writeset 생성) |
| 관련 | [C7](C7_ha_apply_info_columns_no_migration.md)(같은 판단) |
| 지적한 리뷰어 | 5명(종합 문서 2절) |
| 코드 기준 | `a361cca24` |

## 2. 문제
```c
/* log_record.hpp:140 */
  LOG_SUPPLEMENTAL_INFO = 52,
  LOG_DUMMY_WSET_LABEL = 53,	/* 이 브랜치가 추가: 트랜잭션의 writeset 의존 라벨, 커밋 레코드 바로 앞에 기록 */
  LOG_LARGER_LOGREC_TYPE	/* 상한값. 이 브랜치에서는 54, develop에서는 53 */
```
- master는 커밋마다 타입 53 레코드(writeset 라벨)를 로그에 남긴다.
- develop 바이너리에서 53은 `LOG_LARGER_LOGREC_TYPE`(타입 검사용 상한)이다. 구 바이너리가 이 로그를 읽으면 범위를 벗어난 잘못된 레코드로 판단한다.

## 3. 언제 생기나
| 경우 | 결과 |
|---|---|
| master와 slave가 같은 버전 | 문제없음 |
| 새 버전 master + 구 버전 slave (롤링 업그레이드 도중 등) | 구 버전 slave의 copylogdb/applylogdb가 라벨 레코드를 잘못된 레코드로 판단(추정, 실측 안 함) |

새 로그 레코드 타입을 추가하면 항상 생기는 로그 형식 변경이다. 종합 문서가 High에서 Medium으로 낮춘 이유다.

## 4. 판단
- 이 기능은 다음 버전으로만 나가고 하위 버전으로 포팅하지 않는다(사용자 결정, 10-23). 버전이 다른 노드를 섞은 HA는 고려하지 않는다.
- 그래서 타입 번호를 바꾸거나 구 버전 호환을 넣지 않는다.
- 리뷰에서 함께 나온 "master 쪽 writeset 생성을 끄는 스위치가 없다"(syseng_10y)도 혼합 버전 HA를 위한 것이라 같은 판단으로 둔다.

## 5. 열린 질문
1. qa_10y가 지적한 "`log_dump_record`에 타입 53 case가 없어 로그 덤프가 첫 라벨에서 멈춘다"는 확인하지 않았다. 같은 버전 안의 진단 도구 문제라 이 판단과 별개다.
