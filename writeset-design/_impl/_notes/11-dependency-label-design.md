# 11. dependency 라벨과 gate 판정 재설계 — A1 / A2 / A3

## 11.1 문제

master는 트랜잭션이 쓴 키마다 history에서 "그 키를 마지막으로 쓴 트랜잭션의 커밋 LSA"(선행 후보)를 얻고, 그 가운데 **최댓값 하나**만 라벨 `dependency`에 적는다(`writeset.cpp` `wset_find_dependency_in_range`). slave gate는 그 값이 WRITE 출처(`is_ref=0`)이면 completed set에서 그 LSA **하나**를 찾아 통과시킨다(`log_applier_gate.cpp` `la_gate_is_satisfied`). 선행 후보가 둘 이상이면 최댓값이 아닌 후보는 라벨에서 사라지고, slave는 그것을 기다릴 수단이 없다.

2026-10-08 SYSOP_END 없는 부하에서 이 결함으로 순서 역전 1건과 applier 워커 간 행 lock 데드락 1건이 생겼다. 경위와 근거는 [원인 분석 보고서](dependency-root-cause-20261008.md)와 [no-sysop 테스트 보고서](no-sysop-test-20261008.md)에 있다. 이 문서는 수정안 세 가지를 같은 틀로 적고, 결정에 필요한 근거를 모은다.

## 11.2 용어

| 용어 | 어디서 나오나 | 뜻 |
|---|---|---|
| 선행 후보 | master, probe | 트랜잭션이 쓴 키마다 history에서 얻은 직전 작성자의 커밋 LSA. 키가 여럿이면 후보도 여럿 |
| `dependency` | master → 라벨 | 선행 후보 중 최댓값 LSA. 현재 라벨에 있는 값 |
| `완료 범위 상한` | master → 라벨 | 최댓값을 뺀 나머지 선행 후보(REF 출처 포함) 중 최댓값 LSA. A3에서 추가. 이름은 가칭 |
| completed set | slave | 끝난 작업의 커밋 LSA 집합. "이 LSA 하나가 끝났는가"에 답한다 |
| frontier | slave | completed set에서 커밋 순서대로 훑어 처음 빈틈을 만나기 직전의 LSA. "이 LSA 이하가 전부 끝났는가"에 답한다. master에는 없는 값이다 |

라벨의 두 값은 master가 history에서 얻은 숫자다. slave는 `dependency`를 completed set에서 찾고, `완료 범위 상한`은 자기 frontier와 비교한다. 상한 이하의 선행 후보는 모두 상한보다 작으므로, 상한이 frontier 이하이면 그 후보들은 전부 끝난 것이다.

## 11.3 현재 gate 판정과 지름길

```text
1. dependency 없음                    → 통과
2. dependency ≤ frontier              → 통과
3. is_ref = 1                         → 대기 (frontier가 닿을 때까지)
4. dependency ∈ completed set         → 통과
```

4번을 이 문서에서는 **지름길**이라 부른다. dependency 트랜잭션이 frontier 위에서 먼저 끝났으면 frontier를 기다리지 않고 보내는 판정이다. 지름길은 "라벨 하나 = 선행 하나"일 때만 옳다. REF 출처는 `ref_seq`가 최댓값만 남기므로 설계가 3번으로 지름길을 막아 두었지만, WRITE 출처도 키가 여럿이면 같은 처지라는 점이 빠졌다.

### 지름길이 이득을 내는 시나리오

```text
master 커밋 순서:   B(롱, 관계없음)   A(짧음)   Achild (dependency = A)

slave
  t0   B 시작, A 시작
  t1   A 끝남. B는 실행 중
       frontier = B 앞 (B가 빈틈)        completed set = {A}
       Achild 판정
         frontier만:  A ≤ frontier?  아니오 → 대기
         지름길:      A ∈ completed set → 출발
  t2   B 끝남 → frontier가 A까지 전진 → frontier만 쓰면 이때 출발
```

이득은 t2 − t1, 곧 의존 대상보다 **먼저 커밋된** 관계없는 트랜잭션이 의존 대상보다 얼마나 늦게 끝나느냐다. 의존 대상 **뒤에** 커밋된 트랜잭션은 frontier 판정에 들어가지 않으므로 지름길과 무관하다.

no-sysop 실행(2026-10-08)에서 dependency가 있는 배정 263건의 통과 경로:

| 통과 경로 | 건수 |
|---|---|
| `dependency ≤ frontier` | 224 |
| 지름길 (dependency가 frontier 위) | 39 |
| 그중 선행 후보가 하나 (지름길이 옳음) | 7 |
| 그중 선행 후보가 둘 이상 (라벨이 나머지를 숨김) | 32 |

지름길이 쓰일 때 frontier와 dependency 사이의 실행 중 트랜잭션은 중앙값 2개, 최대 16개였다. 설계 문서의 정형 실험(6-3 FK headblock, 11장 UPDATE·INSERT·FK child wave, PoC 7 병렬화)에서는 의존 대상이 끝나는 순간 frontier도 거기 닿아 있어 지름길이 쓰이지 않았다. 지름길의 이득은 크기가 섞인 부하에서 나타난다.

### 지름길이 순서를 꼬는 시나리오 (실측에 1823을 더한 예)

위 시나리오의 반대편이다. 실측의 1806·1824·1861에 가상의 1823을 하나 더한다. 1823은 355|2690에 커밋했고 행 100008을 UPDATE했다.

master에서 각 행이 바뀐 순서(= 지켜야 할 순서):

```text
행 100008:  1806 → 1823 → 1861
행 100031:  1806 → 1861
행 100009:  1824 → 1861
```

master가 각 트랜잭션에 적은 라벨(현재 규칙, 선행 후보 중 최댓값 하나):

| trid | 커밋 LSA | 선행 후보 (행 → 직전 작성자) | 라벨 `dependency` |
|---|---|---|---|
| 1806 | 352\|8608 | 100008 → 1791 외 | 1791 |
| 1823 | 355\|2690 | 100008 → 1806 | 1806 |
| 1824 | 355\|2696 | (1806·1823과 무관) | 342\|13792 |
| 1861 | 359\|1216 | 100008 → 1823, 100009 → 1824, 100031 → 1806, 100045 → 1198 | **1824** |

1861의 라벨에는 1824만 남았다. 그런데 1824는 1861이 쓴 행 가운데 100009에만 관계가 있고, 100008과 100031의 선행인 1823·1806과는 아무 관계가 없다.

slave 진행(현재 규칙):

```text
①  1791 실행 중.  1806은 라벨(1791) 때문에 대기.  1823은 라벨(1806) 때문에 대기.
②  1824 끝남.  frontier는 1791 앞에 멈춰 있음.  completed set = {…, 1824}
③  1861 판정:  1824 ≤ frontier?  아니오.  1824 ∈ completed set?  예 → 출발   ← 지름길
    1861이 100008, 100031, 100009, 100045를 바꾸고 커밋.  1806·1823은 아직 시작도 안 함.
④  1791 끝남 → 1806 출발 → 100008, 100031을 1861보다 오래된 값으로 덮어씀.   (역전 1)
⑤  1806 끝남 → 1823 출발 → 100008을 1861보다 오래된 값으로 덮어씀.           (역전 2)
```

꼬이는 이유는 한 가지다. **1861의 라벨이 "1824 뒤"라고만 말했고, 1824는 100008·100031 사슬 위에 없다.** 1824가 끝났다는 사실은 1806·1823이 끝났다는 것과 아무 관계가 없는데, 지름길은 1824 하나만 확인했다. 1823 자신의 라벨에 1806이 들어 있어 1823 → 1806 순서는 지켜지지만, 1861 → 1823·1806 순서를 지켜 줄 정보가 1861의 라벨에 없다.

같은 상황을 세 안으로 보면:

| 안 | 1861의 판정 | ②에서 1861이 출발하나 | 출발 시점 |
|---|---|---|---|
| 현재 | 1824 ∈ completed set | 출발 (꼬임) | ② |
| A1 | 1824(355\|2696) ≤ frontier | 아니오 | 1791·1806·1823·1824가 모두 끝나 frontier가 355\|2696을 지난 뒤 |
| A3 | 1824 ∈ completed set 그리고 1823(355\|2690) ≤ frontier | 아니오 | 1791·1806·1823이 끝나 frontier가 355\|2690을 지난 뒤 |

A1과 A3 모두 ②에서 1861을 막는다. 차이는 A3가 1824 자체는 지름길로 보고 그 사이의 관계없는 트랜잭션은 안 기다린다는 것뿐인데, 이 예에서는 1823과 1824 사이에 관계없는 트랜잭션이 없어 둘의 출발 시점이 같다.

## 11.4 세 가지 안

세 안 모두 master의 충돌 판정(`write_seq`/`ref_seq` 슬롯, probe, 게시)은 바꾸지 않는다. 바뀌는 것은 라벨에 적는 값과 slave gate의 비교뿐이다.

### A1 — 지름길 제거 (frontier만)

- 라벨: 그대로. `is_ref`는 의미가 없어지므로 제거하거나 무시해야 한다.
- gate: `dependency ≤ frontier`면 통과, 아니면 대기. 3번·4번 판정을 없앤다.
- 보장 근거: frontier 이하는 전부 끝났으므로 최댓값 이하의 선행 후보는 모두 끝났다.
- 비용: 의존 대상보다 먼저 커밋된 관계없는 트랜잭션까지 기다린다(11.3의 t2 − t1).

### A2 — 선행 후보 전부 전달

- 라벨: WRITE 출처 후보 LSA 전부(중복 제거) + REF 출처 후보의 최댓값. 길이가 가변이다.
- gate: WRITE 후보마다 `≤ frontier` 또는 `∈ completed set`. REF 최댓값은 `≤ frontier`.
- 보장 근거: 선행 후보를 하나씩 확인한다.
- 비용: 라벨 길이 가변(no-sysop 실행 중복 제거 후 1개 43%, 최대 12개). gate가 후보 수만큼 반복한다.

### A3 — `dependency` + `완료 범위 상한`

- 라벨: `dependency`(최댓값) + `완료 범위 상한`(나머지 WRITE 후보와 REF 후보의 최댓값). LSA 하나 추가, 길이 고정. `is_ref` 플래그는 "어느 칸에 들어 있느냐"로 대체된다.
- gate: `la_gate_is_satisfied (dependency, false)` **그리고** `la_gate_is_satisfied (상한, true)`. 두 조건을 모두 만족해야 출발한다. 판정 함수 자체는 바뀌지 않고 호출이 두 번이 된다.
- 보장 근거: 최댓값은 지름길로 그 하나를 확인한다. 나머지 후보는 모두 상한 이하이고, 상한 ≤ frontier이면 frontier 이하가 전부 끝났으므로 나머지도 끝났다.
- 비용: 라벨 LSA 하나, gate 비교 하나. 상한이 frontier 위에 있으면 그 사이의 관계없는 트랜잭션을 기다린다(A1보다 기준점이 낮다).

### 세 안의 1861 예시

1861의 선행 후보: 1806(352|8608), 1824(355|2696), 1198(298|9768). 1824는 frontier 위에서 끝났고 1806은 실행 중이다.

| 안 | 라벨 | 판정 | 결과 |
|---|---|---|---|
| 현재 | 1824 | 1824 ∈ completed set | 출발 → 1806을 앞질러 역전 |
| A1 | 1824 | 1824 ≤ frontier? 아니오 | 1806과 그 앞의 관계없는 트랜잭션까지 끝나야 출발 |
| A2 | 1806, 1824, 1198 | 셋 각각 확인. 1806 미완료 | 1806이 끝나면 출발 |
| A3 | 1824 / 352\|8608 | 1824 ∈ completed set ○, 352\|8608 ≤ frontier ✕ | 1806이 끝나 frontier가 352\|8608을 지나면 출발 |

## 11.5 MySQL은 A1을 어떻게 처리하는가

MySQL writeset(`LOGICAL_CLOCK`)은 라벨이 `last_committed` 하나이고 slave 판정이 `last_committed ≤ LWM` 하나다. LWM은 GAQ(트랜잭션 그룹을 커밋 순서로 적고 완료 여부를 표시하는 장부)의 앞에서부터 완료를 확인하다 처음 끊기는 위치로 계산하는 연속 완료 경계이며, 우리 frontier와 같은 개념이다. completed set 멤버십으로 통과시키는 판정은 없다. 즉 MySQL은 A1이다. 코드 위치와 흐름은 [3.4절](../../3-mysql-writeset-처리와-한계.md#34-슬레이브--의존성-라벨을-소비하는-과정), 실측은 [3.6절](../../3-mysql-writeset-처리와-한계.md#36-두-한계를-함께-확인한-mysql-실측)에 있다. 실측에서 Achild2는 `LC=2 > LWM=1`이라 Achild1 완료(5.698초)까지 기다렸다(5.727초 시작).

MySQL에는 A1과 별개의 한계가 하나 더 있다. 코디네이터가 relay log를 한 건씩 읽다 현재 트랜잭션이 gate에 막히면 다음 로그를 읽지 않는 head-blocking이다([3.5절](../../3-mysql-writeset-처리와-한계.md#35-슬레이브-측-한계--코디네이터-head-blocking)). 실측에서 `LC=1 ≤ LWM=1`로 실행 자격이 있던 B·C·D가 4.8~7.5초 늦게 시작한 원인이 이것이다. 우리 설계는 막힌 작업을 pending에 두고 reader가 계속 읽으므로([6-2.6절](../../6-2-cubrid-슬레이브-병렬-적용-설계.md#6-26-막힌-task-뒤의-독립-task)) 이 한계는 없다. 따라서 A1을 택해도 MySQL보다는 병렬성이 높고, 아래 비교의 A1 수치는 head-blocking 없이 gate 규칙만 MySQL과 같게 한 값이다.

PoC S2(2026-07-06, 커밋 901cf4fbd)는 "LWM은 촘촘한 번호 전제의 최적화이고 띄엄띄엄한 LSA에는 집합 멤버십이 등가"라고 보고 지름길만으로 gate를 만들었다. LWM은 최적화가 아니라 라벨이 하나로 줄어든 것을 보상하는 정확성 장치이고, 멤버십은 그보다 약한 조건이다. 이 판단이 결함의 출발점이다.

## 11.7 비교와 결정 기준

| | A1 | A2 | A3 |
|---|---|---|---|
| 정확성 | 보장 | 보장 | 보장 |
| 라벨 | 그대로 (`is_ref` 제거 가능) | 가변 길이 | LSA 하나 추가, 고정 길이 |
| gate | 판정 두 줄 삭제. completed set은 frontier 계산에만 남음 | 후보 수만큼 반복 | 같은 판정 함수 호출 두 번 |
| 혼합 부하 병렬성 (재생) | 가장 낮음 | 가장 높음 | A2와 0~5% 차 |
| 정형 wave 부하 | 셋 다 같음 | | |
| 설명 난도 | "frontier가 닿을 때까지" 한 문장 | 후보 열거 | 지름길 + 상한, 두 문장 |

결정은 두 기준 사이에 있다.

- **gate 복잡도를 줄이라는 리뷰 지적을 우선하면 A1.** 지름길과 `is_ref` 분기가 사라져 gate가 가장 단순해지고, 지름길이 만든 결함의 종류가 통째로 없어진다. MySQL과 같은 gate 규칙이므로 설명도 쉽다. 대가는 혼합 부하에서 재생 기준 20% 이상의 병렬성이다.
- **병렬성 극대화라는 설계 목표를 우선하면 A3.** 지름길의 이득(11.3)을 최댓값 선행에 대해 그대로 유지하면서 결함을 막는다. 대가는 라벨 LSA 하나와 gate 비교 하나다.
- A2는 A3보다 병렬성이 조금 높지만 라벨 길이가 가변이 되므로, 두 안의 차이(0~5%)가 그 비용을 정당화할 때만 고려한다.

## 11.8 결정 (2026-10-08)

**A1을 채택한다.** 근거는 두 가지다. 첫째, gate 복잡도를 줄이라는 리뷰 지적에 직접 답한다. 지름길과 `is_ref` 분기가 사라져 gate 판정이 `dependency ≤ frontier` 하나가 되고, completed set은 frontier 계산 내부에만 남는다. 둘째, 지름길이 만든 결함의 종류가 통째로 없어진다. 라벨 형식은 바꾸지 않는다.

A1으로 바뀌는 것:

| 위치 | 변경 |
|---|---|
| slave `la_gate_is_satisfied` | 3번(`is_ref` 대기)·4번(completed set 멤버십) 판정 제거. `dependency` 없음 또는 `dependency ≤ frontier`면 통과, 아니면 pending |
| slave completed set | gate 판정에서는 쓰지 않는다. frontier 전진 계산(`la_gate_advance_frontier`)과 prune에만 쓴다 |
| 라벨 `is_ref` | 판정에 쓰지 않는다. 필드는 당분간 유지하고 기록만 한다(A3 TODO에서 다시 쓸 수 있다) |
| master `wset_find_dependency_in_range` | 변경 없음. `prev_commit_lsa` 하향은 조각이 게시될 때만 라벨을 틀리게 만든다(원인 B). SYSOP_END를 commit-order 폴백으로 처리하는 동안([10장 13.7](10-sysop-end-investigation.md#137-결정-변경-2026-10-08--commit-order-폴백을-먼저-조각은-최적화-todo)) 조각 게시가 없어 no-op이고, 조각을 되살릴 때 기준값 변경과 함께 고친다 |
| 설계 문서 6-2.4, 8-2.4 | gate 판정 순서를 A1으로 고치고, completed set의 역할을 "frontier 계산용"으로 한정해야 한다 |

## 11.11 어느 안이든 함께 해야 하는 것 (참고)

1. **master 불변식 확인.** 세 안 모두 "선행 후보가 빠짐없이 history에서 나온다"를 전제한다. history 게시가 row lock 해제보다 먼저이고 probe가 lock을 쥔 상태에서 일어나는지 `log_commit_local` 경로에서 확인해야 한다.
2. **`prev_commit_lsa` 하향 제거.** 현재 `min (최댓값, prev_commit_lsa)`는 "바로 앞 커밋의 개별 완료가 안전한 하한"이라는 가정인데, 같은 이유로 성립하지 않는다. A1에서는 frontier 비교라 무해하지만 의미가 없고, A3에서는 제거해야 한다. 조각 LSA는 후보 그대로 싣는다. 전제로 slave가 조각 작업의 완료를 조각 LSA로 completed set에 등록하는지 확인해야 한다.
3. **같은 trid 조각 사이의 순서** (설계 9.1.1)는 별도로 넣어야 한다.
4. **데드락 영구화 방어.** `xlocator_repl_force`는 lock 오류(`ER_LK_UNILATERALLY_ABORTED` 등)를 항목 단위로 넘기지 말고 즉시 반환해야 한다. gate가 맞으면 applier끼리의 행 lock 데드락은 생기지 않지만, 생겼을 때 `lock_add_WFG_edge`가 `DL_victim` 간선을 제외해 영구 멈춤이 되는 경로를 끊는다.
5. **C1.** commit-order 폴백 라벨은 frontier 비교로만 통과시켜야 한다(A1에서는 자동, A3에서는 `완료 범위 상한`에 넣는다).
