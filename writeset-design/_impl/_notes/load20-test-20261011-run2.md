## 결함 1 — 원인 확인: 워커가 들고 있는 로그 페이지 버퍼를 리더가 회수

이번 빌드에 넣은 로그가 세 번 모두 같은 그림을 보였다. 워커가 레코드를 읽은 버퍼에 **대상 LSA의 페이지가 아니라 이웃 페이지**가 들어 있었다.

| 대상 LSA | 버퍼 안 페이지 | 읽힌 레코드 타입 | 그때 리더 위치(final_lsa) |
|---|---|---|---|
| 68737\|2120 | 68736 | 28 | 68737\|13160 |
| 69889\|13080 | 69890 | -1 | 69890\|8624 |
| 74524\|9272 | 74523 | 67108864 | 74524\|14168 |

```
la_get_recdes: cannot get the log record at 68737|2120 (log page 68736, record type 28, error 0, data missing)
```

경로:
- `la_get_page_buffer`는 mutex 안에서 페이지 id를 확인하고 `fix_count++` 한다. 가져올 때는 맞는 페이지다.
- 교체(`la_cache_buffer_replace`)는 `fix_count == 0`인 버퍼만 고르므로 원래는 보호된다.
- 그런데 `la_invalidate_page_buffer`가 `fix_count = 0`으로 **강제 초기화**하고 해시에서 뺀다. 리더는 아직 다 써지지 않은 마지막 페이지를 다시 읽을 때(`log_lsa.c`의 final_lsa 페이지, `hdr.offset < 0` 등) 이 함수를 부른다(log_applier.c 11335, 11389, 11425, 11431, 11449, 11488, 11567, 4634).
- 같은 페이지를 막 가져간 워커는 보호를 잃고, 그 슬롯이 리더가 다음에 읽는 이웃 페이지로 재사용된다. 세 번 모두 리더가 워커 대상과 같은 페이지에 있었다.
- 덧붙여 `la_release_page_buffer`는 버퍼가 아니라 **페이지 id로 해시를 찾아** 해제한다. 무효화 뒤에는 못 찾거나, 같은 페이지를 다시 읽은 새 버퍼의 fix_count를 깎는다.

develop은 단일 스레드라 읽고 적용하는 순서가 겹치지 않아 이 문제가 없다. 병렬 워커가 들어오면서 생겼다.

**더 위험한 점(추정)**: 재사용된 버퍼의 바이트가 우연히 유효한 INSERT 레코드로 해석되면 실패하지 않고 **엉뚱한 행을 조용히 적용**할 수 있다. 이번에 잡힌 세 번은 레코드 타입 검사에서 걸린 경우다.

## 결함 3 — 재기동 뒤 복구 구간 재적용에서 워커끼리 deadlock

멈춘 두 트랜잭션은 trid 1561689(commit 74521|13872)와 1561679(74521|15432)다.
- 마스터에서는 서로 독립이다. 공유 WRITE 키 없음, 부모 테이블 REF 키만 공유(충돌 아님), 둘 다 dependency 74520|14928.
- **둘 다 01:46:09 실패 전 프로세스가 이미 적용·커밋·retire했다**(dispatch 21453, 21454).
- 재기동 시 리더 committed_lsa는 74503|1928, 워커 행 max_committed_lsa 최댓값은 74524|13888. 그 사이는 복구 구간이라 다시 적용됐다.
- 이미 반영된(그리고 뒤 트랜잭션까지 반영된) 슬레이브 상태 위에 다시 적용하니, 마스터 원래 순서에서는 안 겹치던 행에서 충돌한다. 마스터 라벨은 원래 상태의 충돌만 나타내므로 이 경우를 막지 못한다.
- deadlock 9건은 모두 재기동된 프로세스(pid 220377, 220390, 220405)의 워커끼리였고, 첫 실패 전 13분 동안은 0건이다.

## 결함 4 — deadlock 희생자가 락을 놓지 않음 (develop 원본, 미구현 노트 2-1)

서버의 deadlock 탐지는 동작했다. 01:46:15에 tran 8(`applylogdb(6)`)을 희생자로 골라 ER_LK_UNILATERALLY_ABORTED(-72)를 냈다. 그러나 락 덤프에서 tran 8은 **같은 01:46:15부터 다시 대기** 중이고 `Wait_for_secs = -1`(무한)이다. `xlocator_repl_force`가 항목별 오류를 `er_clear()`로 지우고 다음 항목으로 넘어가(locator_sr.c 6970 부근, 미구현 노트 2-1) 희생자가 트랜잭션을 끝내지 않고 다음 락을 다시 기다린다. 이후 탐지에서 같은 사이클을 다시 깨지 못해 영구 정지가 됐다.

```
tran 8 (applylogdb(6)) holds X on item_0 row (insert ID 229992), waits X on row held by tran 9  since 01:46:15
tran 9 (applylogdb(7)) holds X on item_0 row (insert ID 229993), waits X on row held by tran 8  since 01:46:14
```

## 연쇄 관계

결함 1(버퍼 회수) → 리더 종료·재기동 → 복구 구간 재적용 → 결함 3(워커 간 충돌) → 결함 4(희생자 미해제) → 슬레이브 영구 정지.

## 수정 방향 (결정 필요)

1. **결함 1**: `la_invalidate_page_buffer`가 다른 보유자의 fix_count를 지우지 않게 한다. 자기 fix만 내리고 해시에서 빼서 새 조회는 다시 읽게 하며, 버퍼는 fix_count가 0이 될 때까지 교체 대상에서 제외한다. 해제는 페이지 id가 아니라 버퍼 포인터로 하도록 바꾼다(`LOG_PAGE *`는 `LA_CACHE_BUFFER.logpage`에 들어 있어 포인터에서 버퍼를 역산할 수 있다).
2. **결함 3**: 복구 구간(committed_lsa ~ recovery_boundary_lsa) 트랜잭션은 병렬 dispatch하지 않고 commit 순서로 직렬 적용한다. 구간 길이는 워커 수 × 미커밋 폭 정도라 비용이 작다.
3. **결함 4**: 미구현 노트 2-1 방향대로 `xlocator_repl_force`에서 `ER_LK_` 계열 오류는 삼키지 말고 `exit_on_error`로 빠져 트랜잭션을 끝낸다. applier 쪽은 이미 deadlock 오류에 재시도 경로(`LA_RETRY_ON_ERROR`)가 있다.
