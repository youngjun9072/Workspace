# SYSOP_END 없는 부하 테스트 결과 (2026-10-08)

## 목적

[원인 분석 보고서](./dependency-root-cause-20261008.md)에서 확인한 역전 8건은 모두 SYSOP_END 조각이 엮인 경우였다. 원인 A(키별 후보 중 최댓값 하나만 남김)가 조각 없이도 선행 보장을 깨는지 확인하기 위해, 복제 항목을 가진 SYSOP_END가 생기지 않는 부하로 실행했다.

## 방법

- 실행 디렉터리: `sysop_runs/20261008T011634-20261006-78024`
- 명령: `--profile random --seed 20261006 --clients 4 --transactions 400 --tables 4 --preload-rows 50 --tx-weights long=50,single-explicit=30,autocommit=20 --outcome-weights commit=70,abort=30 --dml-weights insert=65,update=25,delete=10 --relation-weights dependent=75,independent=25 --long-statements 10:25 --long-delay-ms 5:40 --no-sysop`

## 판정

하니스 판정은 `DATA_DIVERGENCE`다. 실제로는 다음 두 가지가 함께 일어났다.

1. **slave applylogdb 멈춤.** applier 워커끼리 행 lock 데드락에 걸려 반영이 중단됐다. 행 수 차이는 이 중단 때문이다.
   - slave 카운터가 실행 중 조회한 값(insert 1708, update 417)에서 더 늘지 않았다.
   - 반영되지 않은 로그가 52페이지 남았다.
   - slave er_log는 10:16:41.261 이후 한 줄도 없다. 부하가 끝난 지 1초 뒤다.
2. **순서 역전 1건.** 행 100031에서 1861이 1806보다 먼저 slave에 커밋됐다. 1806이 데드락으로 멈춰 있어 아직 덮어쓰기는 일어나지 않았다.

두 가지 모두 원인 A에서 나왔다.

## slave 멈춤 상태

- applylogdb 워커 4개가 `la_flush_repl_items` → `locator_repl_force`에서 서버 응답을 기다린다. 나머지 워커는 작업 큐에서 대기하고, reader는 sleep 중이다.
- slave 서버 lock table(`cubrid lockdb`)에 applier 워커 트랜잭션 사이의 순환 대기가 있다.

| 행 (item_0 OID) | 보유 | 대기 |
|---|---|---|
| `0\|4929\|15` | tran 10 (X) | tran 9, tran 4 |
| `0\|4929\|32` | tran 4 (X) | tran 10 |
| `0\|4929\|12` | tran 10 (X) | tran 11 |

모든 applier 트랜잭션이 `Infinite wait`이고, 데드락 탐지 주기(1초)가 지나도 풀리지 않았다. 탐지기가 두 번째 순환을 풀지 못한 이유는 아래 "원인 체인 확정"에서 코드로 확인했다.

### 데드락 행 확정

**워커와 lock 트랜잭션의 대응.** 워커 세션 이름은 `db_restart_sub (sub_index)`가 `applylogdb(sub_index + 1)`로 만들고, `sub_index`는 워커 인덱스다. 따라서 lockdb의 `applylogdb(n)`은 워커 n-1이다.

| lock tran | 세션 이름 | 워커 | trid |
|---|---|---|---|
| 10 | applylogdb(8) | 7 | 1806 |
| 4 | applylogdb(4) | 3 | 1897 |
| 9 | applylogdb(7) | 6 | 2010 |
| 11 | applylogdb(9) | 8 | 2015 |

**해시를 id로 역산.** 쓰기 키 해시는 FNV-1a(클래스 OID 8바이트, 인덱스 VFID 6바이트, `or_pack_mem_value` 결과)다. BIGINT 키의 pack 결과는 builtin 도메인 워드 4바이트(`OR_DOMAIN_BUILTIN_FLAG | built_in_index << 16`, type 자리는 `DB_TYPE_NULL`), 정렬 패딩 4바이트, 값 8바이트(big endian)다. parent REF 해시 두 개가 parent_id 1, 5로 풀려 포맷을 확인했고, 4개 트랜잭션의 item_0 쓰기 해시 122개가 모두 id로 풀렸다. 트랜잭션과 하니스 tx 파일의 대응은 고유 INSERT id로 확인했다(1806=tx000275, 1897=tx000293, 2010=tx000352, 2015=tx000317). 공유 행에 대한 연산은 모두 `UPDATE … SET version_no=version_no+1`이다.

**OID와 행의 대응.** 이 테이블은 REUSE_OID라 SQL로 OID를 조회할 수 없다. 대신 각 트랜잭션이 lockdb에 보유한 행 수와 master의 연산 순서를 맞춰 확정했다. 행 수는 클래스 lock을 뺀 값이다.

| trid | 보유 행 수 | 순서상 다음 행 | 대기 OID | 결론 |
|---|---|---|---|---|
| 2010 | 8 (INSERT 8건) | 9번째 연산 100014 | `4929\|15` | `4929\|15` = 100014. 2010이 다른 트랜잭션과 공유하는 행은 100014뿐이다 |
| 2015 | 5 (기존 행 100000, 100004 + INSERT 3건) | 6번째 연산 100011 | `4929\|12` | `4929\|12` = 100011. 2015와 1806이 공유하는 행은 100011뿐이다 |
| 1806 | 14 (기존 행 100008, 100014, 100033, 100011 + INSERT 10건) | 15번째 연산 100031 | `4929\|32` | `4929\|32` = 100031. 1897이 보유한 기존 행 두 개(`4929\|13`, `4929\|32`)가 100031, 100012와 일치한다 |
| 1897 | 8 (기존 행 100031, 100012 + INSERT 6건) | master 순서로는 100008 | `4929\|15` (100014) | 아래 참고 |

**확정된 데드락.**
- 1806은 100014를 보유하고 100031을 기다린다.
- 1897은 100031을 보유하고 100014를 기다린다.
- 두 행 모두 master에서 1806과 1897이 함께 UPDATE한 행이다.
- 2010은 100014에서, 2015는 100011에서 1806을 기다리며 함께 멈춰 있다.

**맞지 않는 점 하나.** master SQL과 COLLECT 순서로는 1897이 100008을 100014보다 먼저 UPDATE한다. 그런데 1897은 100008을 보유하지 않은 채 100014를 기다린다. 100008은 1806이 보유하고 있다(`4929\|9` 또는 `4929\|34`). slave가 1897의 항목을 master 실행 순서와 다르게 적용했거나, 100008 UPDATE를 lock 없이 지나갔다는 뜻이다. 어느 쪽인지는 확인하지 못했다. 데드락 쌍과 행의 확정에는 영향이 없다.

## 결론

1. 원인 A는 SYSOP_END 조각 없이 일반 커밋만으로도 선행 보장을 깬다. 보장되지 않는 관계가 223건(전체 선행 관계의 30%)이다.
2. 이번 실행에서 실제로 드러난 결과는 세 가지다.
   - 동시 실행됐지만 행 lock이 순서를 맞춰 정상: 1243 → 1323.
   - 순서 역전: 1806 → 1861 (행 100031).
   - 데드락으로 slave 멈춤: 1806 ↔ 1897 (행 100014, 100031). 2010과 2015가 함께 멈춤.
3. 원인 B는 조각이 있어야 생기므로 이번 실행에서는 0건이다.
4. Run 2의 역전이 모두 조각과 엮여 있던 것은, 조각이 slave frontier를 기다리는 동안 선행 트랜잭션을 늦춰 타이밍 조건을 만들었기 때문이다. 이번 실행에서는 선행 트랜잭션 1806이 자기 선행(1791)을 기다리느라 늦어진 것이 같은 역할을 했다. 구조 결함(원인 A)은 조각과 무관하다.

### 데드락이 영구화된 경로

slave 서버 err 로그(`log/server/testdb_20261008_1015.err`)에 한 줄이 있다.

```
10:16:39.342 ERROR lock_manager.c:2308 CODE -72 Tran = 4 (applylogdb(4))
Your transaction has been unilaterally aborted by the system.
```

이 줄과 코드를 합치면 순서는 다음과 같다.

1. gate가 1806과 1897을 동시에 실행시켰다(원인 A).
2. 1897은 2번째 문장에서 100031을 잡았고, 1806은 3번째 문장에서 100008을 잡았다.
3. 1806은 15번째 문장에서 100031을 기다리고, 1897은 9번째 문장에서 100008을 기다렸다. 첫 번째 순환이다.
4. 서버 데드락 탐지기가 tran 4(1897)를 희생자로 골랐다. `lock_wakeup_deadlock_victim_aborted`가 `DL_victim = true`를 켜고(`lock_manager.c:2639`) 1897의 lock 요청에 `ER_LK_UNILATERALLY_ABORTED`를 돌려줬다(`:2308`).
5. 서버의 복제 반영 루프 `xlocator_repl_force`(`locator_sr.c`)는 항목 하나의 오류를 "그 항목만 실패"로 취급한다. 오류를 응답 영역에 적고, 그 항목의 topop만 abort한 뒤 **다음 항목으로 계속 간다**. 트랜잭션의 lock은 풀리지 않는다. 그래서 1897은 100008을 쥐지 못한 채 10번째 문장(100014)으로 넘어갔고, 거기서 1806을 다시 기다렸다. 두 번째 순환이다.
6. 탐지기는 두 번째 순환을 보지 못한다. `lock_add_WFG_edge`(`:4960`)는 `DL_victim`이 켜진 트랜잭션이 끼는 간선을 그래프에 넣지 않는다. 이 플래그는 트랜잭션이 끝날 때 `lock_clear_deadlock_victim`(`:9574`)에서만 꺼진다.
7. 1897의 클라이언트(applylogdb 워커)는 서버 응답을 기다리느라 abort를 부를 수 없다. 플래그는 영원히 켜져 있고, 순환은 영원히 풀리지 않는다. 다른 워커 2010, 2015도 1806을 기다리며 함께 멈췄다.

### 재시작 뒤

10:58:19에 당시 slave applylogdb(pid 207772)가 `ER_NET_SERVER_DATA_RECEIVE`(-186)로 종료됐고 heartbeat가 10:58:20에 새 프로세스(pid 208308)를 띄웠다. 이 시각은 분석자가 slave cub_server에 gdb를 붙인 시각과 겹친다. gdb가 서버를 잠시 멈춘 사이 클라이언트 수신이 실패한 것으로 본다(추정).

새 프로세스는 복구 구간을 다시 적용한 뒤 10:58:22에 같은 자리에서 다시 멈췄다(새 lock 대기, 10:58:23 데드락 희생자 또 발생). 라벨이 같으니 같은 동시 실행이 재현된다. 11:07 기준 행 수는 item_0 1566/1265, item_1 187/179, item_2 198/188, item_3 194/178(master/slave)이고, 행 100031의 version_no는 master 11, slave 7이다.

### 다른 가능성의 배제

- SYSOP_END 조각: 이 다섯 트랜잭션에는 master `SYSOP` 줄이 없다. 조각 처리로 항목 순서가 바뀐 경우가 아니다.
- 적용 순서 뒤바뀜: 1806, 2010, 2015가 쥔 행이 master 문장 순서와 정확히 맞으므로 slave는 항목을 순서대로 적용한다. 1897의 예외는 위 5번으로 설명된다.

## 해결안 비교 (trace 재생)

용어를 먼저 정한다. 라벨의 두 칸은 master가 적는 LSA 숫자다. `dependency`는 선행 후보 중 최댓값이고, `완료 범위 상한`은 그 외 선행 후보(REF 출처 포함) 중 최댓값이다. frontier는 slave가 completed set에서 계산하는 "빈틈 없이 끝난 마지막 LSA"로, master에는 없는 값이다. gate는 `dependency`를 completed set에서 찾고(개별 완료), `완료 범위 상한`은 `≤ frontier`인지 비교한다. 상한 이하의 선행은 모두 상한보다 작으므로, 상한이 frontier 이하이면 그 선행들은 전부 끝난 것이다.

`tools/gatesim.py`는 두 실행의 master 후보와 slave 작업 시간(`elapsed_usec`)으로 gate 규칙을 바꿔 가며 재생한다. 모든 작업이 처음부터 대기열에 있다고 보고(백로그 포화) 워커 10개로 돌린다. 절대 시간이 아니라 규칙 사이의 상대 비교용이다. "선행 완료 전 시작"은 작업이 자기 후보 트랜잭션보다 먼저 시작한 횟수다.

| 규칙 | 라벨 내용 | 판정 | no-sysop: 평균 동시 워커 / 선행 완료 전 시작 | Run 2: 평균 동시 워커 / 선행 완료 전 시작 |
|---|---|---|---|---|
| 현재 | 최댓값 하나 | 개별 완료 | 7.94 / **29** | 9.86 / **13** |
| 후보 전부 | WRITE 후보 전부 + REF 최댓값 | WRITE 후보마다 개별 완료, REF 최댓값은 frontier와 비교 | 6.79 / 0 | 9.30 / 0 |
| 상위 2개 | WRITE 상위 2개 + 나머지의 완료 범위 상한 | 2개는 개별 완료, 상한은 frontier와 비교 | 6.71 / 0 | 9.30 / 0 |
| A3: dependency + 완료 범위 상한 | WRITE 최댓값 + 상한(나머지 WRITE와 REF의 최댓값) | 최댓값은 개별 완료, 상한은 frontier와 비교 | 6.47 / 0 | 9.30 / 0 |
| frontier만 (MySQL 방식) | 최댓값 하나 | 최댓값을 frontier와 비교 | 5.20 / 0 | 7.65 / 0 |

현재 규칙의 높은 수치는 기다려야 할 작업을 먼저 보낸 결과이므로 비교 대상이 아니다. 건전한 규칙끼리 비교하면 A3는 후보 전부 방식과 Run 2에서 같고 no-sysop에서 5% 낮다. frontier만 쓰는 방식은 20% 이상 낮다.

WRITE 후보 수 분포(중복 LSA 제거): no-sysop {1:128, 2:59, 3:32, 4:34, 5:15, 6:13, 7:10, 8:3, 9:1, 12:1}, Run 2 {0:17, 1:354, 2:346, 3:28, 4:28, 5:11, 6:7, 7:3, 9:1}.

### 권고

(2026-10-08 결정: **A1 채택**, A3는 개선 TODO. 근거와 변경 범위는 [설계 노트 11장](11-dependency-label-design.md)에 있다. 아래는 결정 전 비교 시점의 권고 내용이다.)

**A3: dependency + 완료 범위 상한.** 라벨에 LSA 하나(완료 범위 상한)를 더 싣고, slave gate에 비교 하나를 더한다.

- master: 후보 중 최댓값을 `dependency`로, 나머지 WRITE 후보와 REF 후보의 최댓값을 `완료 범위 상한`으로 기록한다. 둘 다 history에서 나온 LSA 숫자다. 충돌 판정은 지금처럼 master가 한다.
- slave: `dependency`는 지금 규칙대로(completed set에 있거나 frontier 이하), `완료 범위 상한`은 자기 frontier와 비교해 이하일 때 통과. 두 조건을 모두 만족해야 출발한다. `la_gate_is_satisfied`를 `(dependency, is_ref=false)`와 `(상한, is_ref=true)`로 두 번 부르는 것과 같다.
- 기존 `is_ref` 판정 경로는 그대로다. REF 후보는 항상 완료 범위 상한 쪽에 들어간다.
- `prev_commit_lsa`로 낮추는 처리(원인 B)는 없앤다. 조각 LSA도 후보 그대로 싣는다. slave가 조각 작업의 완료를 그 LSA로 등록하는지는 코드로 확인해야 한다(미확인).

후보 전부 방식은 병렬성이 조금 더 높지만 라벨 길이가 가변이 된다. 두 방식의 차이가 5% 이내이므로 단순한 쪽을 권한다.

### 함께 고칠 것

- `xlocator_repl_force`: lock 오류(`ER_LK_UNILATERALLY_ABORTED`, `ER_LK_OBJECT_TIMEOUT`)는 항목 단위로 넘기지 말고 즉시 반환해야 한다. gate가 맞으면 applier끼리의 데드락은 생기지 않지만, 생겼을 때 영구 멈춤이 되지 않게 하는 방어다.
- 같은 trid의 조각 사이 순서(설계 9.1.1)는 이 수정과 별개로 남아 있다.

## 규칙 무작위 검사 (30분)

`tools/gatefuzz.py`는 설계 규칙을 모델로 옮겨 무작위 부하(트랜잭션 20~1500, 키 풀 3개부터, 트랜잭션당 키 1~12, REF 비율 0~80%, 조각 0~50%)와 무작위 slave 스케줄(워커 1~16, 작업 시간 무작위, reader 지연 포함)로 돌린다. 같은 키를 건드린 두 작업(둘 다 REF 제외)이 LSA 순서로 적용됐는지 모든 쌍을 검사한다. 프로세스 4개, 30분, 부하 1853개.

| 규칙 | 위반 부하 / 전체 | 위반 쌍 | 멈춤 |
|---|---|---|---|
| 현재 (최댓값 하나, 개별 완료, prev_commit 하향) | 1706 / 1853 | 1,323,189 | 0 |
| A3 (최댓값 개별 완료 + 나머지 최댓값을 frontier와 비교) | 0 / 1853 | 0 | 0 |
| WRITE 후보 전부 개별 완료 + REF 최댓값을 frontier와 비교 | 0 / 1853 | 0 | 0 |
| frontier만 (최댓값을 frontier와 비교) | 0 / 1853 | 0 | 0 |

현재 규칙에서 위반이 대량으로 나오므로 검사기는 문제를 잡아낸다. A3는 조각이 섞인 부하를 포함해 위반과 멈춤이 없었다. 이 검사는 설계 규칙의 모델이지 코드가 아니므로, 코드가 규칙과 다르게 동작하는 경우(게시가 lock 해제보다 늦는 경우 등)는 잡지 못한다.
