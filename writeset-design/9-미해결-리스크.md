# 9. 미해결 · 리스크

이 설계에서 아직 확정·검증되지 않은 항목을 모은다. 9.1은 정식 설계에서 다뤄야 하지만 PoC에 구현이 없어 본격 반영 전에 설계 확정과 구현이 남은 것이고, 9.2는 설계는 있으나 실측이 없어 반영 전에 검증해야 하는 것이다. 해결된 공백(G1 collation)은 여기 두지 않고 [충돌 식별자](./6-1-cubrid-마스터-writeset-설계.md#충돌-식별자)에서 다룬다.

## 9.1 미구현 — 정식 설계는 정했으나 PoC에 없는 것

### 9.1.1 LOG_SYSOP_END 별도 task 처리와 db_serial 갱신 순서

`LOG_SYSOP_END` 처리는 기능 브랜치에 구현되지 않았지만 정식 설계는 방안 A로 확정해 6장과 8장에 반영했다. 이 절에는 SQL 진입점부터 슬레이브 DB COMMIT·재시작까지 코드 경로를 추적해 확인한 변경 지점과, 아직 남은 구현·실측 항목을 기록한다.

**develop의 동작**

- 마스터는 sysop이 끝날 때 `NEED_FLUSH`로 표시된 복제 레코드만 먼저 로그에 기록하고 나머지는 COMMIT 앞에 기록한다. 이 표시를 쓰는 경로는 serial 갱신(AUTO_INCREMENT 포함), `INCR()`/`DECR()`, checksumdb 세 곳이다.
- 이 세 경로의 sysop은 독립 top operation이라 바깥 트랜잭션이 ROLLBACK돼도 마스터에 남는다.
- 슬레이브 `la_log_record_process()`는 `LOG_SYSOP_END`를 `LOG_COMMIT`과 같은 분기로 처리해, 그 위치까지 도착한 item을 바깥 트랜잭션의 COMMIT을 기다리지 않고 즉시 적용·영속한다.

**PoC의 상태**

- reader는 `LOG_SYSOP_END`를 디버그 로그만 남기고 무시한다. sysop의 item은 COMMIT까지 보류되고 COMMIT task에 접혀 들어간다.
- `LOG_ABORT`에서 그 트랜잭션의 item을 전부 폐기하므로 sysop item도 함께 버린다.
- `db_serial` 행은 writeset 키 수집 경로 밖이다. `serial_update_serial_object()`가 인덱스 갱신 경로를 거치지 않고 행을 직접 갱신하기 때문이다.

**문제**

- **(a) ABORT 시 마스터·슬레이브 불일치**: 마스터에는 serial 증가·click counter 변경이 남고 슬레이브에는 반영되지 않는다.
- **(b) `db_serial` 갱신 순서 미보장**: 같은 serial을 갱신하는 두 트랜잭션 사이에 dependency가 없어 worker가 어느 순서로든 적용할 수 있고, 갱신은 행 전체 이미지 교체라 나중에 적용된 값이 남는다. failover 뒤 AUTO_INCREMENT 값이 뒤로 가거나 중복될 수 있다.
- AUTO_INCREMENT는 serial cache 없이 호출되므로 insert마다 이 경로를 탄다. 드문 경우가 아니다.

**검토한 해결 방안과 채택 결과**

| 방안 | 내용 | 판정 |
|---|---|---|
| A | sysop item을 별도 task로 만들고, 마스터가 sysop 범위의 키로 라벨을 발행·publish한다. 같은 `trid`의 뒤 task는 앞 task 완료를 기다린다. frontier는 SYSOP_END LSA도 완료점으로 취급한다. | **가능 — 권장.** (a)(b) 모두 해결. 기존 gate·완료 집합·frontier를 그대로 쓰고 새 자료구조가 없다. |
| B | COMMIT까지 미루되 ABORT 때 sysop 이전에 기록된 item만 골라 적용한다. | (a)만 해결. 적용 시점이 ABORT로 밀려 (b)는 남는다. |
| C | 슬레이브가 `db_serial`을 현재 값보다 클 때만 반영한다. | **불가.** CYCLE serial은 값을 최소값으로 되돌리고, INCR/DECR은 양방향이다. |

A를 구현할 때 확인된 함정은 둘이다. 첫째, sysop 범위의 키를 publish한 뒤 트랜잭션의 writeset에서 그 키를 제거하지 않으면 COMMIT 때 같은 키가 다시 publish돼 다음 serial 갱신이 이 트랜잭션의 COMMIT을 기다리게 된다. 둘째, 현재 reader가 붙이고 worker가 비우는 트랜잭션 item 목록을 sysop task와 COMMIT task가 공유하면 경합하므로, sysop task는 dispatch 시점에 자기 item 조각을 떼어 소유해야 한다.

**정식 설계 — 방안 A의 처리 흐름**

아래 흐름을 정식 설계로 채택한다. sysop 안에서 수집된 writeset 부분을 **조각**이라 부른다.

마스터는 sysop 끝에서 COMMIT과 같은 방식으로 조각에 라벨을 붙여야 한다.

```text
sysop 시작
→ 현재 트랜잭션 writeset의 끝 위치를 조각 경계로 기록

sysop 끝
→ 먼저 기록할 복제 레코드(NEED_FLUSH)가 있는가?
   없음 → 라벨·publish 없이 SYSOP_END만 기록
   있음 → 경계 이후 키(조각)만으로 history probe
        → WS_LABEL 기록 (같은 trid의 SYSOP_END 바로 앞)
        → SYSOP_END 기록 → SYSOP_END LSA 확정
        → 조각을 SYSOP_END LSA를 seq로 publish
        → 조각을 트랜잭션 writeset에서 제거
→ 잠금 해제 (serial 페이지 latch, INCR 행 잠금은 sysop 커밋 뒤에 풀림 → publish가 앞선다)

COMMIT
→ 남은 writeset(조각 제외)으로 probe → WS_LABEL → COMMIT → publish  (기존과 같음)
```

조각을 제거하는 이유: 제거하지 않으면 COMMIT 때 같은 키가 COMMIT LSA로 다시 publish되어 다음 트랜잭션의 serial 갱신이 이 트랜잭션의 COMMIT 완료를 기다리게 된다. statement 복제(checksumdb)가 조각에 있으면 조각 라벨도 commit-order 폴백을 따르는 방안이다.

`db_serial` 행의 키는 serial 갱신 경로에서 WRITE로 수집하되 **sysop 조각에만** 들어가게 해야 한다.

```text
serial 갱신(sysop 안)에서 db_serial 행(serial 이름 키)을 WRITE로 수집
→ 조각 라벨에 포함 → SYSOP_END LSA로 publish → 조각 제거
→ 다음 트랜잭션의 같은 serial 갱신은 이 sysop task(한 행 UPDATE)만 기다림
→ 본 트랜잭션 task는 자기 sysop task만 기다리고 서로 병렬
```

키를 트랜잭션 전체에 붙이면 같은 테이블에 AUTO_INCREMENT insert를 하는 트랜잭션이 전부 한 줄로 직렬화되므로, 조각에만 두는 것이 이 방안의 핵심이다.

슬레이브 reader는 `LOG_SYSOP_END`도 task를 닫는 레코드로 다뤄야 한다.

```text
reader가 LOG_SYSOP_END를 읽음
→ 그 trid에 도착해 있는 복제 항목이 있는가?  (일반 항목은 COMMIT 직전에만 오므로, 이때 있는 것은 sysop이 먼저 기록한 것)
   없음 → 무시 (COMMIT 순서 FIFO에도 넣지 않음)
   있음 → 항목을 트랜잭션 변경 목록에서 떼어 task가 소유
        → 직전 같은 trid의 WS_LABEL을 선행 조건으로, SYSOP_END LSA를 commit_lsa로 task 완성
        → COMMIT 순서 FIFO에 넣고 gate 판정 → dispatch 또는 pending

같은 trid의 순서
→ 뒤 task(다음 sysop task 또는 COMMIT task)의 dependency
   = max(라벨의 dependency_seq, 같은 trid의 마지막 sysop task LSA), 대기 방식은 라벨 값
→ sysop task LSA는 WRITE 성격이라 개별 완료로 통과

LOG_ABORT
→ 아직 dispatch되지 않은 항목만 폐기. 이미 task가 된 sysop 항목은 마스터에도 남으므로 그대로 적용

worker·완료 경계
→ sysop task도 COMMIT task처럼 적용·DB COMMIT → 결과를 완료 집합에 등록
→ frontier와 committed_lsa가 SYSOP_END 위치를 가리킬 수 있음 (develop과 같음)
→ SYSOP_END task의 commit_lsa에도 error skip 창 판정을 같이 적용
```

위 흐름이 지키는 것: develop과 같은 시점 관계(sysop 항목은 SYSOP_END에서 반영, 바깥 트랜잭션의 ABORT와 무관)와, 같은 `db_serial` 행 갱신의 마스터 순서. 앞의 "A의 함정 둘"은 각각 마스터 흐름의 "조각 제거"와 슬레이브 흐름의 "항목을 떼어 task가 소유"에 대응한다.

**미확인**

- 런타임 실측이 없다. 판정은 모두 코드 경로 추적이다.
- PoC에서 SYSOP_END task를 제거한 변경의 이유가 기록에 없다. 이전 구현의 문제를 확인해야 한다.
- `NEED_FLUSH`를 만드는 경로가 세 곳뿐이라는 것은 호출부 검색 결과에 의존한다.
- 같은 키가 sysop 조각 안팎에 모두 있을 때(예: `INCR()` 뒤 같은 행 UPDATE) 어느 쪽을 남길지 규칙이 없다.
- 복제 레코드가 없는 `LOG_SYSOP_END`를 무시할 때, develop이 `committed_lsa`를 SYSOP_END 위치에 영속한 상태에서 정식 구현으로 기동하는 재시작 시나리오를 확인하지 않았다.
- SYSOP_END task의 DB commit이 error skip 창 판정과 어떻게 맞물리는지 코드 수정 전 재확인이 필요하다.

### 9.1.2 복합키 FK REF 매칭

복합키 FK의 REF 매칭은 PoC 범위 밖이라 PoC 단계에서는 검토되지 않았던 항목이다. AI를 통한 코드 경로 분석과 설계 검토 결과 해결 가능한 문제로 판정했다. 정식 설계 본문에는 방향만 있고([6-1.7](./6-1-cubrid-마스터-writeset-설계.md#복합-fk와-null-fk), [8-1.2.2](./8-1-cubrid-마스터-writeset-상세-설계.md#복합-fk)) 확정 반영은 아직이며, 아래 해결 방안이 후보다. 구현 전까지 PoC는 부모 PK가 MIDXKEY인 FK 참조를 수집하지 않고 `ws_overflow`로도 전환하지 않으므로, 복합키 FK 자식은 부모 변경과 순서 없이 병렬 적용된다.

**해결 방안(후보)**

자식 FK 값을 부모 PK와 같은 모양의 MIDXKEY로 만들어 REF로 수집하는 방안이다. 현재 REF 수집 경로에서 부모 PK domain이 `DB_TYPE_MIDXKEY`일 때 조기 반환하는 지점을 다음 처리로 바꾼다.

```text
자식 행의 FK 구성 컬럼 값 추출 (FK 선언 순서)
→ 구성 컬럼 중 하나라도 NULL → REF 없음, 폴백 없음 (기존 NULL FK 규칙)
→ 각 값을 부모 PK 구성 컬럼의 domain으로 변환 (단일 FK가 tp_value_cast로 하는 것과 같음)
→ 부모 PK의 컬럼 순서로 하나의 MIDXKEY 구성
→ 부모 PK 인덱스 키를 만드는 것과 같은 packing 경로로 직렬화 (바이트 동일성이 REF 해시 매칭의 전제)
→ 부모 class·부모 PK 식별자와 함께 REF로 수집 → 부모 PK WRITE와 같은 history 슬롯에서 만남
→ 변환·packing 실패는 폴백으로 숨기지 않고 오류로 전달 (불완전한 writeset으로 커밋되지 않게)
```

MIDXKEY를 값 배열에서 구성하는 함수와 부모 PK 인덱스 키 packing 경로가 같은지는 코드로 확인하지 않았다(개념 단계).

### 9.1.3 복구 구간 error skip 완료 조건

PoC는 재시작 시작점을 완료 경계로 되돌리지만, 복구 구간에서 재적용 때문에 생기는 오류와 `fail_counter` 증가를 건너뛰는 로직은 아직 완성되지 않았다. 정식 반영의 완료 조건 넷은 [1.6](./1-개요.md#16-현재-구현-상태와-완료-조건)에 있다. 남은 구현은 둘이다. 현재 복구 구간에서 건너뛰는 오류는 행 재적용의 INSERT 중복키와 UPDATE/DELETE 대상 없음뿐이며, statement/DDL 재적용 오류의 whitelist는 구현되지 않았다. 또 복구 skip으로 분류한 오류가 일반 restart/retry 검사로 다시 들어가지 않도록 제어 흐름을 분리해야 한다.

### 9.1.4 완료 집합 back-pressure

프론티어 위 홀 목록(완료 집합)은 고정 크기다. 한 worker가 오래 지연돼 그 위로 홀이 계속 쌓이면 상한을 칠 수 있다. 상한 초과 시 명시적 실패로 처리하나, back-pressure로 홀 윈도를 상시 제한하는 정책은 미채택 상태다([6-2.2.2절](./6-2-cubrid-슬레이브-병렬-적용-설계.md#6-222-핵심-lsa와-메모리-완료-상태)).

### 9.1.5 commit-order 폴백 라벨의 frontier 대기 플래그

정식 설계는 statement replication과 writeset 용량 초과 트랜잭션을 commit-order 폴백으로 격하하고, 그 라벨을 `dependency_is_read=true`로 기록해 슬레이브가 `prev_commit` 한 건의 개별 완료가 아니라 그 위치까지의 연속 완료 경계를 기다리게 하도록 정했다([6-1.7](./6-1-cubrid-마스터-writeset-설계.md#6-17-정상-계산을-할-수-없을-때의-보수-처리), [8-1 알고리즘 3](./8-1-cubrid-마스터-writeset-상세-설계.md#8-124-마스터-로컬-commit의-dependency-계산과-history-게시)). PoC 마스터는 `repl_log_insert_statement()`에서 `ws_overflow=true`를 설정하고 probe의 overflow 분기에서 `dependency_seq=prev_commit_lsa`를 반환하지만, `ws_dependency_is_read`는 `false`로 남긴다. 슬레이브 gate는 `is_read=false`이면 완료 집합의 개별 완료로 통과시키므로, 직전 COMMIT 하나만 먼저 끝나고 그 앞에 홀이 남아 있어도 폴백 트랜잭션이 실행될 수 있다. 예를 들어 아직 적용되지 않은 INSERT 앞에서 DROP TABLE이 실행될 수 있다. 남은 구현은 overflow 분기에서 이 플래그를 `true`로 설정하는 것이며, 8-1.2.2의 용량 초과 절에 같은 사실이 기록돼 있다.

## 9.2 검증 필요 — 설계는 있으나 실측이 없는 것

- **failover 실제 승격 시나리오**: 현재 크래시 검증은 같은 역할 재시작만 다룬다. 역할 변경 후의 연속 완료 경계와 drain 완료 조건은 실제 승격 실측이 남아 있다([6-2.7절](./6-2-cubrid-슬레이브-병렬-적용-설계.md#6-27-역할-전환-drain)).
- **failback 후 커밋 LSA 재사용**: 재구축 후 커밋 LSA가 실제로 재사용·충돌하는지는 정량 미확인이다([6-2.2.5절](./6-2-cubrid-슬레이브-병렬-적용-설계.md#6-225-영속과-재시작)).
- **`db_serial` 갱신 순서 역전 재현**: 9.1.1의 (b)를 두 세션이 같은 테이블에 AUTO_INCREMENT insert를 하는 워크로드로 병렬 적용해 재현해야 한다.
- **error skip 경계 테스트**: 1.6의 4항 — 재시작 로직에 맡길 오류와 계속 진행할 오류의 경계를 테스트로 고정해야 한다.
- **(정확성 무관) 게이트 3단 판정 vs LWM-only의 기여 분리**: 슬레이브 게이트의 세 번째 판정(프론티어 위의 의존을 완료 집합에서 직접 확인)은 MySQL의 LWM-only 방식보다 병렬성을 추가로 여는 장치지만, 실제 처리량 기여는 실측되지 않았다. MySQL·CUBRID 결합 실측([6-3](./6-3.%20FK%20병렬성%20실측%20%28headblock%2C%202026-09-12%29.md))은 두 구조의 차이를 보였으나 게이트 앞 대기 큐의 효과가 섞여 있어 세 번째 판정만의 기여로 분리되지 않는다. 분리하려면 세 번째 판정을 끈 빌드로 같은 워크로드를 A/B 실측해야 한다.
- **(정확성 무관) 복구 상태 관리 비용**: 완료 상태와 재적용 범위를 관리하는 비용은 별도 측정이 필요하며, 미채택된 완료 마커 방식의 비용과 구분한다.
