### 1. marker 테이블 DROP 뒤 slave applier 정지
링크: https://github.com/CUBRID/cubrid/pull/8052#discussion_r4489620911 (log_applier.c 3178)

문제
- marker 테이블 `ha_applied_tx_marker`가 DBA 소유 일반 테이블이라 master에도 있다. master에서 `DROP TABLE ha_applied_tx_marker;`를 하면 그 DROP이 slave로 복제된다.
- slave worker는 DROP을 적용한 뒤 같은 트랜잭션의 marker INSERT에서 실패해 롤백하고, 그 뒤로 아무것도 적용하지 못한다(2/2). fail_counter는 오르지 않는다.
- RENAME, 열을 바꾸는 ALTER도 같이 막힐 것으로 보이고, TRUNCATE는 marker 행을 지워 재시작 때 이중 적용이 될 수 있다고 함(형규님도 돌려 보지는 않음).
- 같은 이름의 사용자 테이블이 이미 있으면 `la_create_applied_tx_marker`의 `CREATE TABLE IF NOT EXISTS`가 조용히 넘어가고, `la_load_applied_tx_markers`의 SELECT가 실패해 `la_shutdown`으로 끝난다(민준님 r4490730939).

해야 할 일 (형규님 제안, 민준님 동의 r4490730939)
1. marker 테이블을 `_db_` 시스템 카탈로그로 옮긴다. 사용자 DDL이 닿지 않게 하고 이름 충돌도 함께 없앤다.
2. 적용 위치 행(`_db_ha_apply_info`)을 지우거나 새로 만드는 모든 코드에서, 같은 복사 로그 경로의 marker도 같은 트랜잭션에서 지운다. 지금 상태(코드 확인):
   - marker도 지우는 곳: `la_coordinator_commit_apply_info`(적용 위치 저장 뒤 `la_delete_applied_tx_markers(committed_lsa)`), `la_delete_ha_apply_info`(복사 로그 재초기화, `la_delete_applied_tx_markers(NULL)`)
   - marker를 남기는 곳(민준님 지적): `la_update_ha_last_applied_info`(UPDATE가 0행이면 `la_insert_ha_apply_info`로 행을 새로 만듦), `restoreslave`(util_sa.c, `delete_all_ha_apply_info` → `insert_ha_apply_info`, 또는 `delete_all_slave_ha_apply_info`)
   - marker를 남기는 곳(내가 찾음, 리뷰 지적 아님): `la_update_ha_apply_info_log_record_time`(UPDATE가 0행이면 `la_insert_ha_apply_info`)
   - 남은 marker의 위험(민준님, 확인 요청): 다음 시작 때 `la_load_applied_tx_markers`가 "새 적용 위치보다 뒤"인 옛 marker를 읽고, 새 로그 흐름의 커밋이 옛 marker와 같은 LSA에 오면 메시지 없이 건너뛸 수 있다. 실제로 그런지 확인한다.
3. 새 카탈로그를 unloaddb 제외 목록(`unload_object.c`, `_db_ha_apply_stat`이 있는 목록)에 넣는다.
4. 기존 DB에도 새 카탈로그가 생기도록 `cubrid upgradedb` 스크립트를 추가한다.
   - 절차: `upgrade/README.md` Workflow A. `upgrade/internal/cbrd27508.sql`을 만들고, debug 빌드에서 `cubrid upgradedb --apply-script-list <list> <db>`로 적용한 뒤 새로 만든 DB와 메타데이터가 같은지 확인한다.
   - 같은 스크립트에 `_db_ha_apply_stat`도 넣는다. `eea6a34b10`(10-24)이 이 카탈로그를 createdb와 unloaddb 제외에는 넣었지만 upgradedb 스크립트는 넣지 않았다(`upgrade/internal/` 디렉토리가 없음). 리뷰 지적은 아니고 내가 코드로 확인한 누락이다.
5. 하지 말 것(민준님): marker를 `_db_ha_apply_info`의 같은 행에 합치지 않는다. 워커가 커밋마다 그 한 행을 UPDATE하면 커밋까지 행 X 락을 쥐어 모든 워커 커밋이 한 줄로 선다. marker는 트랜잭션마다 다른 행을 넣는 별도 카탈로그로 두고, 2번처럼 지우는 시점만 적용 위치와 맞춘다.

현재 상태: 코드 수정 기록 없음. 답글 없음.

### 2. 롤백된 바깥 트랜잭션의 INCR fragment가 재시작 뒤 적용되지 않음
링크: https://github.com/CUBRID/cubrid/pull/8052#discussion_r4489620916 (log_applier.c 7307)

문제
- slave가 INCR의 SYSOP_END를 fragment로 떼어 따로 적용할 때, fragment의 `start_lsa`를 첫 item 위치로 잡았다.
- fragment가 앞선 commit을 기다리는 동안 바깥 트랜잭션이 롤백되면 slot이 풀려, 저장되는 `required_lsa`가 바깥 트랜잭션의 첫 레코드보다 위로 올라간다.
- 그 상태에서 applier가 재시작하면 item은 `la_set_repl_log`에서 버려지고 SYSOP_END는 `la_coordinator_complete_without_task`로 끝나, INCR이 오류 없이 slave에서 사라진다(3/3, test hook으로 앞선 commit을 붙잡음).

해야 할 일
1. 형규님 제안대로 `fragment->start_lsa`에 바깥 트랜잭션의 `start_lsa`를 넣는다. (완료)
2. 형규님 재현 절차(리뷰 본문 "재현 환경과 절차")로 수정 뒤 INCR이 slave에 적용되는지 확인한다.
3. 수정 커밋과 재현 결과로 답글을 단다.

현재 상태: `bdd1fd0a1`로 수정. 재현 확인 안 함. 답글 없음.

### 3. utf8_gen CHAR에서 비교는 같은 키, 해시는 다른 키
링크: https://github.com/CUBRID/cubrid/pull/8052#discussion_r4489620933 (writeset_key_hash.cpp 226)

문제
- expansion이 없는 콜레이션(`utf8_gen` 등)의 CHAR 비교는 끝의 weight 0 문자를 무시한다(`lang_strmatch_utf8` 끝의 `lang_str_utf8_trail_zero_weights`).
- 키 해시는 공백만 자르고 weight 0 문자도 해시에 넣는다(`mht2str`).
- 그래서 `'k1'`과 `'k1' || CHR(1)`은 master에서 unique 위반(같은 키)인데 해시가 달라, 앞 값을 지우는 트랜잭션과 뒤 값을 넣는 트랜잭션이 독립으로 라벨된다. slave에서 뒤 행이 -670으로 사라진다(20/20, workers=1은 20/20 유지).
- `a7a2871eb`가 `lang_uca_weight_key`에 넣은 규칙이 이 경로에는 없다고 함.

해야 할 일 (형규님 제안)
1. strip_space일 때 공백 대신, 비교가 쓰는 weight 표에서 weight가 0인 문자를 끝에서부터 잘라 낸다.
2. 같은 분기로 보이는 경우도 확인한다: VARCHAR에 `ignore_trailing_space=yes`, contraction만 있는 콜레이션.
3. `test_writeset.cpp`에 이 사례를 넣는다.
4. 키 동등성 판정은 HA pair 시험으로 확인한다(SA의 unique 위반만으로는 판정하지 않는다).

현재 상태: 기록 없음. 답글 없음.

### 5. history를 비우거나 큰 트랜잭션이 커밋할 때 서버 전체 로그 기록이 멈춤
링크: https://github.com/CUBRID/cubrid/pull/8052#discussion_r4489620946 (writeset_history.cpp 238), 민준님 재현과 요청 https://github.com/CUBRID/cubrid/pull/8052#discussion_r4490730602

문제
- 커밋하는 트랜잭션은 `prior_lsa_mutex`를 쥔 채 history의 `seq_lock`을 잡는다(`wset_history_lock_for_probe`, `wset_history_record_commit`). `prior_lsa_mutex`는 모든 DML과 커밋의 로그 기록이 거치므로, 이 두 락 안의 긴 작업은 서버 전체 로그 기록을 멈춘다.
- 형규님 지적: history 맵을 비우는 동안(`wset_history_publish_with_capacity`의 용량 초과, `wset_history_clear_for_commit_order`, 메모리 부족) 멈춘다.
- 민준님 재현: PK 하나와 UNIQUE 둘인 테이블에 32세션 자동 커밋 INSERT에서, 맵을 비우는 순간 모든 세션의 응답이 약 115ms 늘어난다. 17초마다 한 번 생긴다.
- 민준님이 찾은 같은 원인의 정지 두 곳:
  - 비운 직후 재등록: 비운 트랜잭션이 쓰기 락 안에서 자기 키를 다시 등록한다(90만 키에서 약 390ms). 비울 때 `history_start`가 이미 그 트랜잭션의 커밋 위치 이상으로 올라가 있어, 다시 등록한 키는 어떤 라벨에도 쓰이지 않는다.
  - 큰 트랜잭션의 키 탐색: `wset_order_find_dependency`가 `prior_lsa_mutex` 안에서 모든 키를 탐색한다(90만 키에서 약 200ms). 키 1~3개 일반 커밋은 커밋당 약 2µs라 문제없다.

해야 할 일 (민준님 요청)
1. history를 비울 때 락 안에서는 빈 맵과 교체(swap)만 한다. 옛 맵은 두 락을 놓은 뒤, 가능하면 커밋 스레드가 아닌 곳에서 해제한다.
2. 비운 직후 재등록을 뺀다.
3. 커밋할 때 키 탐색을 `prior_lsa_mutex` 앞(키가 더 바뀌지 않는 `log_append_repl_info_and_commit_log` 직전)으로 옮겨 가장 큰 후보와 REF 여부만 기억한다. mutex 안에서는 `seq_lock` 아래 `history_start`·`prev_commit_lsa`를 읽어 후보를 보정하는 O(1) 작업만 한다. `wset_overflow`면 지금처럼 커밋 순서 라벨.
   - 순서가 지켜지는 근거(민준님): 같은 키를 쓴 앞선 트랜잭션은 키를 등록한 뒤에야 행 락과 MVCCID 락을 놓으므로 뒤 트랜잭션은 항상 앞선 키를 본다. 탐색과 mutex 사이에 history가 비워져도 mutex 안에서 `history_start`를 다시 읽으므로 라벨은 더 보수적으로만 바뀐다.
   - 따로 맞춰야 할 곳: 2PC 경로 `log_complete_for_2pc`.
   - 9번(FK REF 틈)이 조금 넓어지므로 9번 수정과 함께 반영한다.
4. 수정 뒤 같은 부하로 정지가 사라졌는지 잰다.

현재 상태: 기록 없음(측정도 안 함). 답글 없음.

### 7. 리뷰 본문에만 있는 항목 (인라인 없음)
링크: 형규님 11-06 리뷰 본문(review id 5796501546)

7-1. barrier 뒤 read-ahead 메모리
- 문제: ring 크기가 worker 수 × 1024이고 coordinator는 ring이 찰 때만 읽기를 멈추므로, DDL처럼 커밋 순서를 강제하는 barrier 뒤에서 그만큼의 트랜잭션 item이 메모리에 머문다. 999행 트랜잭션, item 200~250바이트를 가정하면 N=8에서 약 1.8 GB. develop 직렬 applier는 DDL에서 읽기를 멈췄다.
- 해야 할 일: applier 메모리 한도(`ha_apply_max_mem_size`와 시작 시 크기의 2배 중 큰 값)를 넘는지 잰다. 넘으면 barrier 뒤 읽기를 제한한다.
- 현재 상태: 기록 없음.

7-2. 라벨 없는 로그의 운영 조건
- 문제: 업그레이드 전 backlog나 slave를 먼저 올리는 rolling upgrade에서는 라벨이 없는 로그가 온다. 그동안 serial과 INCR이 바깥 commit에 실려 commit 순서로 적용된다.
- 해야 할 일(형규님 제안): 이 동작을 PR 본문이나 매뉴얼에 운영 조건으로 적는다. 같은 주제로 민준님과 greptile은 "이 PR에서 고쳐야 한다"고 했으므로 16번과 함께 결정한다.
- 현재 상태: 기록 없음.

7-3. FK 스트레스에서 fail_counter 1~2 (자식 행 DELETE -711, workers=1과 4 모두)
- 문제: 형규님 시험에서 확인한 한 건이 자식 행 DELETE의 -711이었다. #8026이 리뷰 기준 커밋에 없어 원인을 판단하지 않았고, develop을 다시 머지한 뒤에도 남는지 보자는 것.
- 11-10 결론: 같은 모양을 우리 경합 시험(`ha_bench_tool/cases/cascade_race_20261110/run_race.sh`)에서 재현했다. 원인은 develop 결함 두 개가 겹친 것이다.
  - master cascade가 동시에 넣는 중인 자식을 놓친다. 열린 #8198(CBRD-27463)이 바로 이 자식 찾기 로직(`locator_satisfies_child_of_locked_parent`, `locator_wait_out_child_writer`)을 고치는 중이다(diff 확인).

### 9. FK 값을 바꾼 트랜잭션의 REF 키 등록 전 틈
링크: https://github.com/CUBRID/cubrid/pull/8052#discussion_r4490729779 (locator_sr.c 9058)

문제
- T1 `UPDATE c SET pid=2 WHERE id=10`(자식을 p(1)에서 p(2)로 옮김)과 T2 `DELETE FROM p WHERE id=1`(ON DELETE CASCADE)은 바꾸는 행이 다르지만 부모 키 p(1)에 함께 닿는다. 그래서 `locator_update_index`는 T1의 옛 부모 키 p(1)을 REF로 모으고, 이 REF가 T2의 WRITE p(1)과 충돌해야 slave에서 T2가 T1 뒤에 적용된다.
- `log_commit_local`이 `logtb_complete_mvcc` → 라벨과 COMMIT 기록 → `wset_order_publish_commit_keys` → `lock_unlock_all` 순서라서, T1이 커밋된 것으로 보이지만 REF p(1)을 아직 등록하지 않은 틈이 있다.
- 그 틈에 T2가 오면 T2의 p(1) 락은 T1과 충돌하지 않고, CASCADE 스캔은 스냅샷으로 T1을 커밋된 것으로 봐 지울 자식이 없다고 판단하며, T2 라벨에는 T1이 빠진다.
- slave에서 T2가 먼저 적용되면 c(10)이 아직 pid=1이라 CASCADE로 지워지고, T1의 UPDATE는 대상 행이 없다. master는 p(2), c(10, pid=2)가 남아 데이터가 달라진다.

해야 할 일
1. REF 키가 커밋이 보이기 전에 history에 반영되도록 순서를 고친다(수정 방법은 리뷰어가 정하지 않음).
2. 5번의 키 탐색 이동과 함께 반영한다(민준님 r4490730602: 탐색을 앞당기면 이 틈이 조금 넓어짐).
3. 리뷰의 T1/T2 순서를 HA pair에서 재현해 수정 전후를 확인한다.
