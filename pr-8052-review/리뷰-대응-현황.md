### 1. marker 테이블 DROP 뒤 slave applier 정지
- 링크: https://github.com/CUBRID/cubrid/pull/8052#discussion_r4489620911 (log_applier.c 3178)
- 지적: marker 테이블이 DBA 소유 일반 테이블이라 master에서 `DROP TABLE ha_applied_tx_marker;`가 slave로 복제된다. slave worker가 DROP을 적용한 뒤 같은 트랜잭션의 marker INSERT에서 실패해, 그 뒤로 아무것도 적용하지 못한다(2/2). fail_counter는 오르지 않는다. 제안: marker를 `_db_` 시스템 클래스로 두거나 이 테이블 대상 복제 문장을 걸러 낸다. RENAME, ALTER, TRUNCATE도 같은 문제로 보인다고 함.
- 리뷰 본문에서 "머지 전에 고쳐야 할 것"으로 분류.
- 추가 코멘트: 민준님 11-06 https://github.com/CUBRID/cubrid/pull/8052#discussion_r4490730939
  - `_db_` 시스템 클래스로 옮기는 방향에 동의. 마커 자체는 필요하다고 봄(워커는 각자 커밋하고 적용 위치는 coordinator가 나중에 저장하므로, "적용 위치 + 그 뒤의 마커"가 합쳐져야 어디까지 반영했는지 정해짐).
  - 옮길 때 요청 1: 적용 위치(`_db_ha_apply_info`)를 지우거나 새로 쓰는 모든 경로에서 같은 복사 로그 경로의 마커도 같은 트랜잭션에서 지울 것. 지금 마커를 지우는 곳은 `la_coordinator_commit_apply_info`와 `la_delete_ha_apply_info` 두 곳뿐이고, `la_update_ha_last_applied_info`(적용 위치 행이 없으면 `la_insert_ha_apply_info`로 다시 만듦)와 restoreslave(`delete_all_ha_apply_info` → `insert_ha_apply_info`, `delete_all_slave_ha_apply_info`도 마커는 안 건드림)는 옛 마커를 남긴다. 다음 시작 때 `la_load_applied_tx_markers`가 그 마커를 다시 읽어, 새 로그 흐름의 커밋이 옛 마커와 같은 위치에 오면 조용히 건너뛰는지 확인해 달라는 것.
  - 옮길 때 요청 2: 새 카탈로그를 `_db_ha_apply_stat`처럼 unloaddb 제외 목록에 넣고, 기존 DB 업그레이드 때 만드는 경로도 넣을 것.
  - 마커를 `_db_ha_apply_info`의 같은 행에 합치는 방법은 반대(커밋마다 한 행을 갱신하면 행 락으로 모든 워커 커밋이 한 줄로 섬). 별도 카탈로그로 두고 생명주기만 맞추자는 것.
  - 이름 충돌: 같은 이름의 사용자 테이블이 있으면 `la_create_applied_tx_marker`의 `CREATE TABLE IF NOT EXISTS`가 조용히 넘어가고 `la_load_applied_tx_markers`의 SELECT가 실패해 `la_shutdown`. `_db_`로 옮기면 함께 해결.

### 5. history를 비우는 동안 log append가 기다림
- 링크: https://github.com/CUBRID/cubrid/pull/8052#discussion_r4489620946 (writeset_history.cpp 238)
- 지적: commit 쪽이 `prior_lsa_mutex`를 쥔 채 seq_lock을 잡으므로, seq_lock을 쥐고 map을 비우는 동안 서버의 log append가 모두 기다린다. 용량 초과·메모리 부족 경로도 같다. 측정 제안: history를 한도 가까이 채운 상태에서 단일 행 autocommit INSERT 여러 세션의 지연을 보며 `CREATE TABLE x (a INT); DROP TABLE x;`로 fallback을 일으킨다. 길면 map을 떼어 내 락 밖에서 해제.
- 추가 코멘트: 민준님 11-06 https://github.com/CUBRID/cubrid/pull/8052#discussion_r4490730602
  - 재현 결과: 실제로 약 115ms 동안 서버의 모든 로그 기록이 멈춤. PK 하나와 UNIQUE 둘인 테이블에 32세션 자동 커밋 INSERT에서 17초마다 한 번 생김.
  - 같은 원인의 정지가 두 곳 더 있다고 함: 비운 직후 자기 키 재등록(쓰기 락 안, 90만 키에서 약 390ms, 비울 때 `history_start`가 이미 올라가 있어 다시 등록한 키는 어떤 라벨에도 쓰이지 않음), 큰 트랜잭션의 키 탐색(`wset_order_find_dependency`가 `prior_lsa_mutex` 안에서 모든 키 탐색, 90만 키에서 약 200ms). 키 1~3개 일반 커밋은 커밋당 약 2µs라 문제없고, 키 수에 비례하는 작업이 락 안에 있는 것이 문제라는 것.
  - 요청 1: history를 비울 때 락 안에서는 빈 맵과 교체(swap)만 하고, 옛 맵 해제는 두 락 밖에서(가능하면 커밋 스레드가 아닌 곳에서). 비운 직후 재등록은 뺀다.
  - 요청 2: 커밋할 때 키 탐색을 `prior_lsa_mutex` 앞(키가 더 바뀌지 않는 `log_append_repl_info_and_commit_log` 직전)으로 옮기고, mutex 안에는 `history_start`·`prev_commit_lsa`로 보정하는 O(1) 작업만 남긴다. 순서가 지켜지는 근거(앞선 트랜잭션은 키 등록 뒤 락을 놓음, mutex 안에서 `history_start`를 다시 읽어 라벨은 더 보수적으로만 바뀜)와 따로 맞춰야 할 곳(2PC `log_complete_for_2pc`)도 적었다. 락 없이 스냅샷으로 앞선 커밋을 보는 경로(9번 FK REF 틈)는 틈이 조금 넓어지므로 그 수정과 함께 반영해 달라고 함.
- 코드 대응: 기록 없음(측정도 안 함).
- 답글: 없음.

### 7. 리뷰 본문에만 있는 항목
- barrier 뒤 read-ahead 메모리: ring 크기가 worker 수 × 1024이고 coordinator는 ring이 찰 때만 읽기를 멈추므로, DDL 같은 barrier 뒤에서 그만큼의 트랜잭션 item이 메모리에 머문다(999행 트랜잭션, item 200~250바이트, N=8에서 약 1.8 GB 가정). `ha_apply_max_mem_size` 한도를 넘는지 재 보자는 제안. 코드 대응·측정 기록 없음.
- 라벨 없는 로그(업그레이드 전 backlog, slave 먼저 올리는 rolling upgrade): greptile 스레드(r4415536908)에서 후속으로 남긴 것은 확인했다고 함. 그때까지 serial·INCR이 바깥 commit에 실려 commit 순서로 적용된다는 점을 PR 본문이나 매뉴얼에 운영 조건으로 적자는 제안. 반영 기록 없음. 같은 스레드에 민준님과 greptile이 "후속이 아니라 이 PR에서 고쳐야 한다"는 코멘트를 달았다. 16번 참고.
- FK 스트레스 fail_counter 1~2(자식 행 DELETE -711, workers=1과 4 모두): #8026 머지 뒤에도 남는지 보자는 것. 11-10 우리 시험에서 같은 모양을 재현했고 원인은 develop 결함 두 개(master cascade 누락, slave cascade 재실행)로 판정했다. [[develop-결함]] 참고. 답글로 알리지 않음.

### 8. 마커 INSERT가 la_sql_compile_mutex로 직렬화됨 (리뷰 본문)
- 지적: worker가 트랜잭션마다 `la_insert_applied_tx_marker`를 SQL로 실행하며 모든 worker·coordinator가 공유하는 `la_sql_compile_mutex`를 쥔다. 처리량 상한이 워커 수와 무관하게 생기고, `la_delete_applied_tx_markers`가 마커를 몰아 지울 때 모든 worker가 멈추며(락 에스컬레이션 시 커밋까지 연장), 트랜잭션마다 쓰기가 늘어난다. 먼저 워커 1·4·8, 마커 유무로 작은 트랜잭션 처리량을 재 달라는 것. 개선 순서 제안: 마커를 `la_flush_repl_items` 경로로 기록 → mutex는 컴파일 때만 → 한 번에 지우는 행 수 상한 → PK에 짧은 식별자.
- 코드 대응: 기록 없음(측정도 안 함).

### 9. FK 값을 바꾼 트랜잭션의 REF 키 등록 전 틈

- 지적: `log_commit_local`이 `logtb_complete_mvcc` → 라벨·COMMIT 기록 → `wset_order_publish_commit_keys` 순서라서, FK 값을 바꾼 T1이 커밋된 것으로 보이지만 옛 부모 키 REF를 아직 등록하지 않은 틈에 옛 부모를 지우는 T2가 들어오면 T2 라벨에 T1이 빠진다. slave에서 T2가 먼저 적용되어 CASCADE/SET NULL로 데이터가 달라진다.
- 관련 코멘트: 민준님이 5번 스레드(r4490730602)에서 "키 탐색을 mutex 앞으로 옮기면 이 틈이 조금 넓어지므로 이 수정과 함께 반영"해 달라고 함.

### 13. serial_Cached_btid가 없을 때 별도 fallback 사유

### 16. 라벨 없는 SYSOP_END의 serial 갱신이 바깥 트랜잭션에 묶임 (greptile 스레드)
- 링크: https://github.com/CUBRID/cubrid/pull/8052#discussion_r4415536908 (log_applier.c, `la_coordinator_process_sysop_end`)
- 원래 지적(greptile, 10-29): slave는 라벨 있는 `LOG_SYSOP_END`만 fragment로 떼고, 라벨 없는 것의 항목은 바깥 트랜잭션에 남겨 바깥 ABORT 때 버린다.
- 내 답글(10-30, `fffda6ccd`): master가 복제 항목이 로그에 나간 SYSOP_END마다 종료 형태와 상관없이 라벨을 붙이도록 고침(checksumdb 41청크 시험). 라벨이 아예 없는 업그레이드 전 로그는 후속으로 남김.
- 추가 코멘트 1: 민준님 11-06 https://github.com/CUBRID/cubrid/pull/8052#discussion_r4490730263
  - 라벨 없는 SYSOP_END의 serial 갱신이 바깥 트랜잭션에 붙으면, 바깥이 커밋할 때 적용되어 slave serial 값이 역행할 수 있고(T1 NEXT_VALUE 11 라벨 없음 → T2 12 라벨 있음 먼저 적용 → T1 커밋 때 11 적용, failover 뒤 12 중복 발급), 롤백하면 master에서 확정된 증가가 slave에서 사라진다.
  - 경우 1, 같은 버전 master에서 라벨 쓰기 실패: `log_append_wset_label_with_lock`이 라벨 로그 노드를 할당하지 못하면 라벨 없이 돌아가고, `log_append_wset_label_and_sysop_end`는 SYSOP_END를 그대로 기록한다. 오류로 처리하거나 라벨 노드를 SYSOP_END 전에 미리 확보하자는 제안.
  - 경우 2, 업그레이드 때 slave에 남은 이전 버전 master 로그: 이전 버전은 라벨을 쓰지 않으므로 모든 serial 갱신에 위 문제가 생긴다. base applylogdb처럼 라벨 없는 SYSOP_END도 그 시점에 바깥에서 떼어 커밋 순서로 적용하자는 제안.
- 추가 코멘트 2: greptile 11-06(민준님 코멘트에 대한 봇 응답)
  - 두 경우 모두 정확성 문제로 봄. 라벨을 확보하지 못한 채 SYSOP_END가 성공적으로 기록되는 경로를 막아야 하고, 라벨 없는 종료도 항목이 있으면 fragment로 떼어 commit-order barrier task로 적용해야 한다. "후속 처리"가 아니라 이 PR의 필수 보완으로 봐야 한다는 의견.
